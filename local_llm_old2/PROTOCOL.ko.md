# 실험 계약 — v0.2.0

## 1. 연구 대상과 성공 기준

동일한 문제의 사실·규칙·목표를 고정하고, 서로 다른 역할이 표현 수준 A, 실제 지지 의존 깊이 D, 검토 대상 M을 구분하는 **유효한 형식 기록**을 생성하는지 관측한다. 이것은 미지의 답을 찾는 정답률 경쟁도, 모델의 은닉 상태를 직접 측정하는 실험도 아니다. 연구 방향은 기존 `docs/research_note.md`의 고정 결과·역할극·독립 재검사 범위를 유지한다.

요청 A/D/M 라벨은 출력 외부 메타데이터다. 출력 라벨을 측정값으로 읽지 않는다. 기존 `adm_minimal.verify(problem, trace)`가 원문 문제에 따라 증명·도식·검토를 재계산한다. 요청한 역할과 관측값의 일치 여부는 별도 비교한다.

**유효성**과 **역할 준수**는 다르다. 유효한 증명을 다른 깊이로 만들면 역할 미준수이지 무근거 증명은 아니다. 개별 단계가 맞아도 최종 참조, 고정 목표, 전체 지지 연결성 중 하나가 틀리면 유효한 전체 증명이 아니다.

## 2. 세 축의 구현 정의

A의 `instance`는 각 노드의 구체 원자를, `schema`는 해당 노드 및 지지 조상 부분 증명을 명제 변수로 일대일 치환한 보편 Boolean 도식을 요구한다. schema 역할에서는 사실 노드도 도식이어야 한다. 모든 사용 사실·규칙을 정확히 포함하고, 임의 전제 추가·누락·무근거 함의를 허용하지 않는다. 논문의 A0–A4 수준을 임의로 새 번호에 매핑하지 않는다.

D는 사실 깊이 0, 규칙 노드 깊이 `1 + max(부모 깊이)`로 계산한 최종 지지 깊이다. shallow/deep은 같은 문제에서 가능한 최소/최대 깊이를 요구한다. 참조 깊이는 별도 탐색으로 계산하며 LLM에 정답 깊이·선택 규칙·정답 증명을 제공하지 않는다. 유한한 비교를 위해 한 지지 경로에서 같은 원자의 반복을 금지하고 주어진 사실은 종단으로 둔다. 이는 기존 결정론적 생성기의 경로 규약을 맞추기 위한 추가 계약이며 모든 논리 증명의 보편 정의가 아니다.

M0은 검토 없음, M1은 최종 논증의 실제 근거 재검토, M2는 M1과 수락 기준에 대한 probe 검토다. argument 검토의 대상·evidence·used_rules·grounded를 재검사한다. M2는 정답 문자열만 비교하는 기준과 유효한 근거까지 확인하는 기준이 무근거 목표 주장에 대해 다른지 검사한다. 검사 코드를 호스트가 실행한 횟수를 모델 자신의 메타 추론 성과로 세지 않는다.

## 3. 전송 형식과 변환 경계

공통 전송 스키마는 `protocol_v2.TRANSPORT_SCHEMA`에 있다. 모든 통합 역할과 neutral에 같은 스키마를 제공하며 A/D/M 정답을 스키마의 역할별 상수로 고정하지 않는다.

```json
{
  "nodes": [
    {
      "node_id": "n0",
      "atom": "p",
      "rule_id": null,
      "parent_node_ids": [],
      "view": {"kind": "instance", "atom": "p"}
    }
  ],
  "selected_final_node_id": "n0",
  "verification_reviews": []
}
```

위 예시는 형식 예시일 뿐이다. p가 주어진 사실이면서 목표인 문제에서만 전체 증명으로 통과할 수 있다. 목표를 강제로 p로 바꾸지 않는다.

호스트의 변환은 노드·검토 필드명 변경, node 안의 view를 기존 views 맵으로 이동, bindings 배열을 일대일 맵으로 변경, 원문 문제 식별자·해시 부착으로 제한한다. 빈 바인딩, 중복, 누락, 모순을 채우지 않는다. final을 goal 원자에서 알맞은 ID로 찾아 바꾸거나, 부모를 추정하거나, 대안 노드를 잘라내거나, 검토의 Boolean 값을 뒤집지 않는다.

`canonical()`은 해시 계산에만 키 정렬을 사용하고 HTTP 전송은 순서 보존 `wire_json()`을 쓴다. `request.wire.json`은 실제 전송 직렬화와 같은 UTF-8 텍스트다. JSON 객체 키 순서가 논리적 의미를 바꾸지는 않지만, 모델·문법 변환기와의 상호작용 변수이므로 실제 전달 내용을 보존한다.

## 4. 공통 예시와 실험 조건 변경

v0.2는 두 개의 고정된 공통 예시를 system 메시지에 넣는다. 하나는 instance/shallow/M0, 하나는 schema/deep/M2다. 모든 역할과 neutral에 같은 예시가 들어가며 실제 평가 문제의 증명을 런타임 생성해 예시로 제공하지 않는다.

예시 그래프는 `chain_2`와 동형이고 원자·규칙 이름이 다르다. 따라서 예시에서 설명한 구조를 재현하는 과제도 포함한다. 이 실험의 성과는 공통 예시가 있는 조건에서 계약과 역할을 따르는 성과이며, 새로운 위상으로의 일반화나 무예시 성능이 아니다. 예시 제공 자체가 역할 간 의미 독립성을 증명하지 않는다.

v0.1 결과와 v0.2 결과는 조건 변경 전후의 별도 실험이다. 모델·샘플링은 유지하지만 필드명, 전송 순서, 바인딩 자료구조, 지시문, 예시를 함께 바꿨다. 개선이 관측되더라도 어떤 한 수정의 인과효과로 분리하려면 추가 절제 실험이 필요하다. 이 배포본은 먼저 동작 가능한 측정 절차를 회복하기 위한 수정본이다.

## 5. 분리 사전 진단

`calibrate`는 8회의 독립 요청으로 증명 생성 2, 도식화 1, 논증 검토 2, 기준 비교 3을 검사한다. 정답 라벨이 들어 있는 role_id, reference depth, 호스트 기대 판정은 모델 메시지에 넣지 않는다. 검토 과제에는 판정할 증명 또는 probe를 입력으로 제공한다.

증명 단독 진단에서 호스트가 검증 API를 호출하기 위해 instance view와 빈 reviews를 붙이지만 A/M 성과로 측정하지 않는다. 도식화·검토 진단에서는 호스트 제공 증명을 모델 생성 증명으로 기록하지 않는다. 진단의 부분 성공으로 원본 통합 실험 실패를 덮지 않는다.

각 진단은 최소한의 실패 위치 분리를 위한 것이며 충분한 통계적 능력 검정이 아니다. 예컨대 분리 과제는 통과하고 통합 과제는 실패하면 과제 결합·문맥·지시 상호작용을 후속 원인 후보로 삼을 수 있지만, 그것만으로 원인을 확정하지 않는다.

## 6. 판정·계수·분모

전체 판정은 입력 결합 → 전송 형식 → 지지 DAG/목표 → 도식 → 검토 → 역할 준수 순으로 수행한다. 첫 오류는 유지하고, 별도 `raw_diagnostics`가 원문에서 관측 가능한 참조/국소 규칙/빈 도식 문제를 추가 기록한다. 오류 범주는 겹칠 수 있다.

proof-only, representation-only, review-only 사본 검사는 실패 위치 확인용이다. 원문 의미 계약을 통과시키는 수리 절차가 아니다. 기본 증명이 틀리면 A/M의 의미 유효성은 null/assessable=false로 표시한다. 관측된 검토 대상 `M_target`은 검토 내용이 옳다는 보장이 아니다.

본 실험은 배정된 모든 조건을 분모에 남긴다. 실패·중단·미시작을 제외하지 않으며, completed failure의 자동 재시도나 가장 좋은 시드 선택을 하지 않는다. neutral은 지정 역할 준수율의 분모에서만 제외된다. full의 시드 반복은 독립된 새 문제 수가 아니다. 진단 8회, mock 시험, 검증기 변조 대조 횟수는 본 LLM 표본 수에 합산하지 않는다.

축별 대조는 같은 문제·시드·다른 역할 좌표를 맞춰 관측된 기록을 비교한다. 유효한 기록 쌍이 없을 때 0/N이라는 실패 수치는 측정된 효과가 0이라는 추정값이 아니다. 이 경우 역할 조작이 성공했다고 확인할 수 없다는 뜻이다.

## 7. 파일·환경·재현성

manifest에 조건표, 문제 원문, 모델 digest, 서버 버전, Python/OS, 추론 설정, 검증기/실행 소스 해시를 동결한다. 소스 스냅샷과 조건별 요청·응답·시간·모델 적재 정보를 보존한다. 기록의 파일 해시는 저장 후의 우발적 변경을 검출하기 위한 것이며, 모든 파일과 해시를 함께 고치는 공격자에 대한 외부 서명이나 원격 실행 증명은 아니다.

resume은 동일 동결 조건에서만 허용한다. 요청만 남은 경우 서버 실행 여부를 추정해 재요청하지 않는다. 모델 digest 변경, 통신 장애, 하네스 오류 시 대량 호출을 중단한다. API 실패 뒤 서버에서 남은 작업의 취소까지 보장하지 않으므로 사용자가 서버 상태를 확인해야 한다.

pilot/full은 재검증한 smoke 게이트 또는 명시적 ungated 실행을 요구한다. 게이트는 불필요한 반복 호출을 줄이는 운영 절차이며 연구 표본 선별을 숨기는 장치가 아니다. 어떤 경로를 사용했는지와 실패한 smoke를 함께 보고한다.

루프백 HTTP만 허용하고 외부 리다이렉트·환경 프록시 사용을 차단한다. 모델 다운로드·로그인·원격 API·출력된 코드 실행은 구현하지 않는다. 설치와 모델 준비는 사용자 측에서 수행한다.

## 8. 이번 배포에서 실제 확인한 범위

Linux/Python 3.13에서 오프라인 63개 시험, 자체 대조 21항목을 통과했다. 사용자가 제공한 v0.1 smoke 6건과 pilot 39건의 원문을 재검사해 모두 기존 상태와 첫 오류를 재현했다. 로컬 모델 호출, Windows 실행, 새 정확도·속도·토큰 수 측정은 하지 않았다. 그 경계는 `BUILD_STATUS.json`에 기록한다.
