# v048 원문 재검증 및 다음 단계 판단

## 1. 결론

v048 자료는 완결된 비교 자료이며, 저장된 요약과 두 가지 재검산 결과가 일치한다. 원식은 204/240(85%), 교환식과 실제 NOT→AND 연결식은 각각 240/240(100%)이다. 연결식의 중간값까지 포함한 성공은 240/240이다.

핵심 갱신은 **원식의 실패도 seed에 따라 달라진다**는 점이다. 새 seed 10개 중 6개에서는 v047의 항상 false 패턴이 재현됐고, 4개에서는 원식도 전부 맞았다. 따라서 “원래 표현은 모든 seed에서 실패한다”가 아니라 “등록한 seed 집합에서 원식은 seed에 민감했고, 교환식과 연결식은 모두 성공했다”가 현재 결과에 맞는다. 기존 사용자 주장을 더 강하게 바꾼 것이 아니라, 현재 성과의 정확한 범위를 기술한 것이다.

## 2. 확인 자료와 재검증

입력은 사용자 제공 `v048_seed_01_evidence.zip`이다. ZIP 자체는 변경하지 않았다. ZIP의 1,955개 manifest 대상 파일이 목록·SHA-256과 일치했다. 동봉된 외부 계획과 결과 snapshot도 일치하며, 계획 해시는 `97c9940f083ace13fe9b8a057cafa29316661096f2d6294ef6b82a583596c411`이다.

배포했던 Windows 수정판 v048 감사기로 원문을 재계산했다. 재계산한 전체 report 객체는 저장된 `summary.json`과 일치했다. 실행 코드 snapshot은 고정 배포 코드의 fingerprint와 일치했다. 실행 전·반복 경계·실행 후 7개 모델/서버 식별 점검이 모두 일치했다.

별도로 `independent_check.py`를 작성했다. 이 코드는 기존 감사기와 기존 정답표를 import하지 않는다. 기존 재귀하강 파서와 다른 shunting-yard 방식으로 실제 전송 expression을 계산하고, 수동 명시 진리표와 대조했다. 960건의 요청·응답 원문, event 해시 연결, 엄격한 bool, 실제 부모값 전달 240건, 대응 직접 요청 240쌍을 확인했다. 원식/교환식 요청은 expression 이외 필드가 동일했다.

관측된 정상 연산 응답 924개의 bool을 뒤집으면 정답으로 인정되지 않는다. 네 입력의 중간·최종값 8비트 전체 256조합에서도 모든 중간·최종값이 맞는 한 조합만 전체 경로 성공이다. 최종 네 값만 맞고 중간값이 틀린 15조합은 경로 성공이 아니다. 이 합성 검사는 새 LLM 표본으로 세지 않는다.

이 검토에서 실제 Ollama 추론은 새로 실행하지 않았다. 동봉된 외부 계획은 결과 snapshot과 분리된 원본의 보존·일관성을 확인하는 자료이지, 모든 파일을 함께 바꾸는 공격이나 실제 서버 실행을 독립적으로 인증하는 서명은 아니다.

## 3. 결과

| 입력 (a,b) | 정답 | 원식 | 교환식 | 연결식 최종 |
|---|---|---:|---:|---:|
| false,false | false | 60/60 | 60/60 | 60/60 |
| false,true | false | 60/60 | 60/60 | 60/60 |
| true,false | true | 24/60 | 60/60 | 60/60 |
| true,true | false | 60/60 | 60/60 | 60/60 |
| 합계 | | 204/240 | 240/240 | 240/240 |

원식의 오류 36건은 모두 양성 입력 `(true,false)`에 모여 있다. 양성 조건 정답률은 원식 40%, 나머지 두 조건 100%이다. 음성 정답률은 모두 100%이다. 원식의 balanced accuracy는 (0.4+1)/2=0.7이다. 전체 정확도만 보면 양성 조건의 약점이 덜 드러난다.

교환식−원식과 연결식−원식은 각각 +15%p, seed 기준 6승·4무·0패다. 연결식−교환식은 0%p, 10무다. v047의 +25%p보다 수치가 작아진 것은 새로운 seed 중 원식도 성공하는 조건이 포함됐기 때문이며, 교환식이나 연결식의 정확도가 낮아진 것이 아니다.

NOT 240/240, 실제 NOT 반환값 전달 240/240, 공급된 값에 대한 AND 240/240이 모두 확인됐다. 중간값이 틀린 상태에서 최종값만 우연히 맞은 관측 파이프라인은 없다.

동일 요청 본문은 160종이고, 각각 6회 응답 content가 같았다. 따라서 960회 요청을 960개 독립 논리 문제나 독립 성공확률 표본으로 계산하지 않는다. 이번 단계의 새로운 축은 10개 생성 seed이며, 문제는 여전히 같은 진리표 하나다. Ollama 문서의 seed 설명과도 같은 seed·prompt에서 같은 응답을 반복하는 관측이 맞는다.[1]

## 4. 비용

| 지표 | 원식 | 교환식 | 연결식 |
|---|---:|---:|---:|
| 호출 | 240 | 240 | 480 |
| 입력 토큰 | 36,480 | 36,480 | 71,760 |
| 출력 토큰 | 1,440 | 1,440 | 2,880 |
| 경로 HTTP시간 중앙값 | 202.376ms | 203.479ms | 413.914ms |
| 경로 HTTP시간 평균 | 211.039ms | 209.964ms | 443.902ms |

연결식은 교환식 대비 호출·출력 토큰 2배, 입력+출력 토큰 약 1.97배를 사용했다. 이번 식의 최종값만 필요하면 교환식이 더 경제적이다. 연결식의 확인된 기능적 이점은 중간 결과를 관측하고 검증할 수 있다는 점이지, 이 식에서의 비용 절감이나 직접식 대비 추가 정확도가 아니다.

배치의 첫 NOT 호출은 약 4.814초였다. 비용을 사후에 삭제하지 않고 전체 집계에 포함했으며, 통상 응답시간 해석에는 중앙값과 로딩 필드를 함께 사용했다. 입력 캐시 사용량도 경로마다 다르므로 토큰 수가 같다는 것을 실제 FLOPs가 같다는 주장으로 바꾸지 않는다. 시간·캐시·토큰 필드의 의미는 Ollama 공식 API 정의를 따른다.[2][3]

## 5. 제3자 관점의 논쟁과 합의

외부 심사자나 독립 에이전트를 호출하지 않았다. 아래는 서로 다른 심사 기준을 같은 자료에 적용한 검토다. 독립성의 실제 근거는 별도 파서·수동 표·오류 주입이지, 심사자 역할명이나 다수결이 아니다.

| 관점 | 반론/질문 | 증거에 따른 판정 |
|---|---|---|
| 형식 검증 | 요약만 맞고 원문 집계가 틀린 것 아닌가? | manifest·계획·원문·기존 재감사·별도 계산이 일치한다. 현재 결과는 인정한다. |
| 통계·재현 | 240/240이면 일반적인 무오류가 입증됐나? | 등록 seed·입력의 결과는 전부 정답이다. 같은 요청 6회를 독립 문제로 세지는 않는다. |
| 모델 행동 | 작은 모델은 이 복합식을 못 하나? | 교환식뿐 아니라 원식도 4개 seed에서 성공했다. 연산 불가능 설명은 더 이상 맞지 않는다. |
| 인과 해석 | seed 하나의 우연으로 발견한 해법인가? | 발견 seed 밖 10개에서 두 해법이 모두 성공했고 6개에서 차이가 재현됐다. 외부 표현의 효과는 강화됐지만 내부 메커니즘은 관측하지 않았다. |
| 비용·시스템 | 연결식이 고성능·고효율이라는 증거인가? | 교환식과 정확도는 같고 호출/토큰은 더 많다. 중간값 검증의 기능적 차이를 별도로 인정한다. |
| 연구 로드맵 | 계속 seed만 늘리거나 큰 모델로 가야 하나? | 당면한 재현 질문은 충족됐다. 다음에는 표현 요소를 분리하고, 이후 전체 판단 작업과 ADM 본 가설로 돌아간다. |

**합의:** v048을 성공한 생성 조건 확장 실험으로 보존한다. 원식의 seed 의존성을 새 사실로 반영한다. 다음 단계는 동일 모델·전체 seed를 유지한 표현 2×2 대조다. 연구 질문을 “단계 분해만이 답”으로 만들거나 교환식 대조군을 제거하지 않는다.

## 6. v049 방향

비교할 네 직접식은 다음과 같다. 모두 동일한 최종 진리표를 가지며, NOT b 자체의 괄호는 유지한다.

| 피연산자 순서 | 바깥 괄호 있음 | 바깥 괄호 없음 |
|---|---|---|
| a 먼저 | `(a AND (NOT b))` | `a AND (NOT b)` |
| NOT b 먼저 | `((NOT b) AND a)` | `(NOT b) AND a` |

기존 NOT→AND 연결식은 다섯 번째 대조 경로다. NOT의 괄호까지 동시에 제거하거나 변수 이름·시스템 지시·모델을 바꾸지 않는다. 하나의 변경으로 여러 해석을 섞지 않기 위한 선택이다.

v048의 전체 10개 seed를 성공/실패 여부와 무관하게 재사용한다. 이것은 새 seed 검증이 아니라 같은 seed에서 새 표현의 대응 비교다. 두 반복에서 각 입력별 전체 seed의 경로 위치와 블록 내부 직전 조건을 균형화한다. 반복을 6회에서 2회로 줄인 것은 v048에서 동일 요청의 불안정성이 관찰되지 않았고, 이번에는 표현 대조를 늘렸기 때문이다. 2회는 새 표본이 아니라 반복 확인이다.

호출 수는 `10 seed × 4입력 × 2반복 × (직접식4회 + pipeline2회) = 최대480회`다. 각 seed 안에서 모든 120가지 순서를 검사하는 설계는 아니다. 위치·직전 조건 균형은 전체 seed에 걸친 경로 수준이며 실제 HTTP 호출 위치와는 구분한다.

실험이 끝나면 바깥 괄호가 있을 때/없을 때의 순서 차이와 그 차이의 차이를 함께 본다. 네 직접식 중 최고 성능만 사후 골라 하나의 100% 점수로 합성하지 않는다. pipeline도 네 직접식 각각과 비교한다.

## 7. v049 이후의 출구

순서 차이가 두 괄호 조건에서 유지되면 바깥 괄호만으로 설명되지 않는 표현 효과로 기록한다. 바깥 괄호를 제거했을 때만 차이가 사라지면 순서×표현 경계의 상호작용으로 기록한다. 이전 anchor 결과부터 바뀌면 실행 조건의 재현 변화와 새 표현의 효과를 분리한다. 어느 경우든 내부적으로 NOT를 먼저 계산했다는 결론은 출력만으로 도출하지 않는다.

자료가 완결되면 이 구성요소 연구의 결과를 정리하고, 원래 전체 판단 작업에 재통합해 고정 문제·목표 아래 A/D/M 축을 실제 조작하는 실험으로 진행한다. 표현을 무한히 늘리는 것은 이번 코드의 목표가 아니다. ADM의 추가 효과는 일반적인 primitive 분해 대조와 구분해 측정해야 한다.

## 자료

- `legacy_reaudit.json`: ZIP 목록·기존 감사기 재검산.
- `independent_check.py`, `independent_verification.json`: 독립 재채점 소스와 결과.
- `calls_independent.csv`, `trials_independent.csv`: 호출/판단별 원문 재집계.
- 본 분석의 수치는 사용자 ZIP에서 계산했다. 합성 코드 시험을 새 LLM 성과로 합산하지 않았다.
