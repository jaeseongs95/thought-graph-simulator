# v050 사전 실험 계약: 원래 기준 판정 과제 재통합

## 목적과 선택 이유

v049에서는 `NOT b`가 앞에 있는 두 직접식과 실제 단계 연결이 모두 성공했다. 따라서 다음은 표기 변형을 더 찾는 실험이 아니라, 원래 `criterion_witness`의 입력 읽기·판정 출력에 이 성공 경로를 붙여도 작동하는지 확인하는 실험이다.

고정 목표·역할별 경로를 다루는 원래 A/D/M 정의는 유지한다. A는 표현의 구체성/일반화, D는 실제 지지 깊이, M은 검토 대상이다. 이 모듈에서는 그 축을 조작하지 않으며, A/D/M을 세 bool의 곱으로 대체하지 않는다.

## 고정 과제

문제 K01은 facts=[Ca], goal=Cc와 규칙 Ca→Cc, Ca→Cb, Cb→Cc를 가진다. K11은 같은 목표에 초기 사실 Cc를 추가한 대조다. Cz, Ca, Cc를 probe로 사용하여 목표 동일성×초기 사실 소속 네 경우를 모두 검사한다. probe에는 rule=null, parents=[]를 준다.

이 과제는 해당 단독 주장이 지지되는지 판단한다. Ca에서 Cc를 새로 증명하라는 과제가 아니므로, 목표 Cc가 규칙으로 도달 가능하다는 사실을 단독 Cc 주장의 부모·규칙이 존재한다는 증거로 바꾸지 않는다.

원래 `local_llm/micro_probe.py`와 `calibration_v4.py`의 과제 의미를 재구성했다. 과거 v042 HTTP 바이트를 동일하게 재실행했다는 뜻은 아니다. v050 내부에서 두 oneshot의 나머지 메시지와 출력 schema는 동일하며 gap의 식 순서만 다르다.

## 네 경로

| 경로 | 작업 | 경로당 호출 |
|---|---|---:|
| oneshot_original | 입력부터 observed, primitives, 세 finding을 한 번에 작성. gap=a AND NOT b | 1 |
| oneshot_commuted | 같은 과제·출력 형식. gap=(NOT b) AND a만 변경 | 1 |
| staged_commuted | 실제 추출 응답 → proof AND → 교환식 gap | 3 |
| staged_pipeline | 같은 실제 추출 응답 → proof AND → NOT → 실제 반환값을 받는 gap AND | 4 |

staged 두 경로는 extract와 proof AND 호출을 공유한다. 실제 실행 그래프는 다음과 같다.

```text
문제·단독 주장
├─ oneshot_original → 전체 witness
├─ oneshot_commuted → 전체 witness
└─ extract → observed + 실제 a/b
   ├─ a 그대로 전달 → answer_only_accepts
   ├─ AND(a,b) 실제 응답 → proof_and_goal_accepts   [공유]
   ├─ ((NOT b) AND a) 실제 응답 → 직접 경로 gap
   └─ NOT(b) 실제 응답 → AND(a,실제 NOT값) → 연결 경로 gap
```

호스트가 수행하는 것은 작업 배정·전달·기록·이미 받은 필드의 조립이다. answer_only에는 모델이 추출한 a를 그대로 연결한다. 누락된 필드, 잘못된 a/b, NOT 또는 AND를 정답으로 보충하지 않는다. 관측 의미가 틀려도 형식이 유효하면 그대로 전달한다.

## 호출 예산

v049의 10 seed 전체 × 네 입력 × 두 반복 = 80개 대응 블록이다. 각 블록에서 고유한 호출은 7회이므로 최대 560회다. 각 경로를 별도로 합산한 1+1+3+4=9회에는 공유 호출 두 개가 중복되므로 실제 총 호출로 사용하지 않는다.

extract 형식이 유효하지 않으면 네 하위 계산 호출을 생략한다. NOT 형식이 유효하지 않으면 그 AND만 생략한다. 생략은 event로 남고 해당 통합 경로는 성공하지 못한 것으로 기록된다. 실행 자체의 통신 오류는 재시도 없이 미완료로 끝낸다.

## 비교 계약

모델 이름·digest·show 메타데이터·서버 버전과 generation options는 v049 기준선을 유지한다. seed는 전체를 재사용한다. 성공 seed만 선택하지 않는다. 모델/temperature/표현/출력 스키마를 결과를 본 뒤 바꾸어 같은 실행으로 합치지 않는다.

oneshot 두 경로 사이의 대조는 gap 식 순서의 대응 대조다. oneshot 대 staged는 프롬프트·출력 schema·호출 구성·호스트 연결을 포함한 묶음 비교다. 이를 순수한 호출 횟수 효과라고 해석하지 않는다.

세 실행 묶음(original, commuted, split)의 순열을 결과와 무관하게 배정하고, 두 번째 반복은 첫 번째의 역순으로 한다. split 내부의 proof/direct/pipeline 분기 순서도 바꾸되 부모→자식 의존성은 유지한다. HTTP 요청 위치까지 완전히 균형 있게 통제한 설계는 아니다.

통계는 seed별 기술통계와 대응 차이를 사용한다. 공통 추출을 사용하는 두 staged 경로를 독립 실행으로 세지 않는다. 같은 seed의 반복이나 같은 문제의 네 표현을 새 논리 문제 표본으로 세지 않는다.

## 성공 지표

각 층을 독립적으로 읽는다.

1. observed: probe.atom, goal, facts를 정확히 읽었는가?
2. primitives: 같은 문자열인지와 초기 facts 소속 여부를 맞혔는가?
3. finding: 세 최종 판정이 모두 맞는가? gap 하나의 정답률도 따로 기록한다.
4. 전체 경로: 앞의 모든 층이 맞고, pipeline은 NOT 중간값까지 맞는가?

뒤 단계 형식 오류가 앞서 성공한 추출을 지우지 않는다. 아직 실행하지 않은 단계는 null로 남기며, 일부 자료만으로 최종 대응 차이를 계산하지 않는다. 무결성 PASS는 위 모델 정답률과 별도다.

## 비용

실제로 기록한 고유 호출의 총비용과 경로별 참조 호출 비용을 분리한다. 경로별 비용은 해당 경로에 필요한 공유 호출을 한 번씩 포함한 실측 합산이다. 별도의 독립적인 종단 간 실행을 실측했다는 뜻이 아니다. 캐시·로딩·입출력 토큰의 누락은 null이며 0으로 바꾸지 않는다.

Ollama의 `/api/chat`에서 제공하는 prompt_eval_count, prompt_eval_cached_count, eval_count 및 duration 필드를 사용한다. JSON Schema는 출력 형식 계약으로만 사용하고 const/enum으로 정답을 지정하지 않는다.

## 후속 판단

- 전체 witness까지 안정적으로 통과한 경로가 있으면 그 경로를 통합 기준선으로 보존하고 기존 증명 그래프·도식·검토 과제 연결로 이동한다. 잘 작동하는 oneshot이 있으면 단계 연결만 고집하지 않는다.
- 입력 읽기·primitives가 실패하면 해당 출력층을 먼저 고친다. 불리언 연산이 성공했다는 과거 기록으로 추출을 통과 처리하지 않는다.
- 추출은 맞고 계산이 실패하면 실제 하위 호출의 입력·응답을 보며 실패 위치를 분리한다.
- 최종값은 맞고 앞 단계 또는 NOT가 틀리면 전체 성공으로 세지 않는다.

이 실험으로 확인할 것은 기준 판정 구성요소의 재통합이다. 본 A/D/M 효과의 수치는 이후 실제 축별 조작·고정 목표·실제 지지 경로 검증에서 구한다.
