# v049 표현 대조: 원문 검증과 다음 단계

## 결론

v049 결과는 유효하다. 원식과 교환식의 차이는 바깥 괄호가 있는 조건과 없는 조건 모두에서 유지됐다. 바깥 괄호 제거는 원식의 실패를 해결하지 않았고, 오히려 원래 성공하던 네 seed에서도 양성 조건을 실패하게 했다. 따라서 이 표기 집합에서는 `NOT b`가 앞에 오는 두 직접식과 실제 NOT→AND 연결을 성공 기준선으로 유지하는 것이 맞다.

다음 실험은 괄호 변형을 계속 늘리는 것이 아니라, 원래 단독 사실 주장 과제의 **입력 읽기 → 두 원자 판정 → 세 최종 finding**에 성공한 계산 경로를 재통합하는 v050이다. 이것은 기존 criterion_witness 과제로 돌아가는 단계이며, A/D/M을 새롭게 Boolean 축으로 정의하는 작업이 아니다.

## 1. 수행한 검증

첨부 `v049_expression_01_evidence.zip`의 SHA-256은 `088502064bb751a8f186de60caf919eef30abf9adf2371d72e7dbe9d6dc62b90`이다. manifest 대상 1,000개 파일을 목록·해시로 검사했다. manifest 자체를 포함한 ZIP 항목은 1,001개다.

배포했던 고정 v049 감사기로 동봉 외부 계획과 실행 원문을 재감사했다. 재계산된 report 객체 전체가 저장된 summary.json과 일치했다. 첨부된 source_snapshot의 코드를 실행한 것이 아니라, 기존 배포 소스를 사용하고 snapshot 지문을 대조했다.

그다음 별도 `independent_check.py`를 작성했다. 이 코드는 기존 감사기·정답표를 import하지 않는다. 직접 작성한 재귀 하강 식 해석기와 별도 수동 진리표를 대조하고, 실제 요청과 응답 480건을 재채점했다. 실제 부모값 전달 80건, 식 문자열을 제외한 요청 구조의 동일성 80개 블록도 확인했다. 모두 저장된 집계와 일치했다.

별도 수입한 v048 ZIP과 v049 ZIP의 요청 바이트 해시를 비교한 결과, v048의 서로 다른 요청 160종이 모두 v049에도 있었다. 이 160종의 응답 content 집합도 각각 동일했다. 이 비교는 과거에 동일하게 실패하던 seed와 성공하던 seed의 행동이 그대로 재현됐음을 뒷받침한다. 관측을 새 문제 표본으로 합산하지는 않는다.

## 2. 실제 결과

| 조건 | 최종값 정답 | 양성 조건 정답 | seed별 전체 진리표 성공 | 중간값 포함 성공 |
|---|---:|---:|---:|---:|
| original: `(a AND (NOT b))` | 68/80 (85%) | 8/20 | 4/10 seed | 해당 없음 |
| commuted: `((NOT b) AND a)` | 80/80 | 20/20 | 10/10 seed | 해당 없음 |
| original_open: `a AND (NOT b)` | 60/80 (75%) | 0/20 | 0/10 seed | 해당 없음 |
| commuted_open: `(NOT b) AND a` | 80/80 | 20/20 | 10/10 seed | 해당 없음 |
| pipeline: 실제 NOT → AND | 80/80 | 20/20 | 10/10 seed | 80/80 |

각 seed·입력은 두 번씩 실행됐다. 원식의 오류 12건과 괄호 없는 원식의 오류 20건은 모두 `(a=true,b=false)`에서 false를 출력한 경우다. 괄호 없는 원식은 80회 모두 false였다. 이 입력 집합에서는 무조건 false를 출력해도 75%가 되므로, 그 점수를 양성 판별 능력으로 읽지 않는다.

원식에서 네 입력을 모두 맞힌 seed는 1790124989, 267101868, 223674688, 68285180이다. 나머지 여섯 seed에서는 양성 조건을 두 번 모두 실패했다. 교환식 두 조건과 연결식은 모든 seed에서 성공했다.

연결식에서는 NOT 80/80, 실제 반환값 전달 80/80, 전달된 입력에 대한 AND 80/80이었다. 잘못된 NOT를 호스트 정답으로 교체하거나, 중간 오류가 최종 정답으로 가려진 관측 사례는 없었다.

## 3. 2×2 대조를 어떻게 읽는가

바깥 괄호가 있으면 교환식−원식의 정확도 차이는 +15%p이고, 없으면 +25%p다. 원식에서 바깥 괄호가 주는 차이는 +10%p이며, 교환식에서는 0%p다. 등록한 차이의 차이 `(commuted-original)−(commuted_open-original_open)`는 −10%p다.

이 결과는 **바깥 괄호만의 문제라는 설명으로는 부족하며, 피연산자 순서의 차이가 두 괄호 조건에서 모두 유지된다**는 판단을 지지한다. 동시에 괄호가 전혀 무관한 것도 아니다. 원식에서는 그 유무가 네 seed의 성패를 바꾸었다.

외부 입력 문자열을 바꾼 효과와 모델 내부 실행 순서는 다른 수준의 설명이다. 교환식에 NOT가 앞에 쓰였다는 것은 확인했지만, 모델 내부에서도 NOT부터 계산했다고 관측한 것은 아니다. 다음 작업에는 확인된 성공 경로를 사용할 수 있으며, 그 사용을 위해 내부 메커니즘의 완전한 해명을 기다릴 필요는 없다.

서로 다른 요청 240종의 두 반복은 모두 동일한 응답 content를 냈다. 이번 실험은 동일 식의 네 입력·열 seed·표현 네 종류의 대응 대조이지, 서로 다른 논리 문제 480개를 검증한 자료는 아니다.

## 4. 비용

| 조건 | 실제 호출 | 입력 토큰 | 출력 토큰 | 판단 경로 HTTP시간 중앙값 |
|---|---:|---:|---:|---:|
| original | 80 | 12,160 | 480 | 226.330ms |
| commuted | 80 | 12,160 | 480 | 225.552ms |
| original_open | 80 | 12,080 | 480 | 228.190ms |
| commuted_open | 80 | 12,080 | 480 | 230.371ms |
| pipeline | 160 | 23,920 | 960 | 459.715ms |

연결식 시간은 실제 두 HTTP 요청시간을 합산한 것이다. 호스트 파일 저장 등을 모두 포함하는 종단 간 시간이나 FLOPs는 아니다. 첫 로딩과 캐시 통계는 원문에 그대로 남아 있으며, 경로 비교에서 비용을 감추려고 실패 호출을 제외하지 않았다.

최종 bool만 필요한 현재 과제에서는 교환식이 연결식과 같은 정확도를 더 적은 호출·토큰으로 달성했다. 연결식의 기능적 차이는 중간 결과를 관측·검증할 수 있다는 점이다. 다음 통합 실험에도 개선된 직접 경로를 반드시 남겨야 한다.

## 5. 다각도 논쟁과 합의

별도 외부 에이전트나 외부 심사자를 호출한 것은 아니다. 아래는 서로 다른 심사 기준을 적용한 반론과, 실제 자료에 근거한 판정이다. 기술적 독립성은 별도 계산기·원문 대조·반례 시험으로 확보한 범위만 뜻한다.

| 관점 | 검토한 쟁점 | 합의 |
|---|---|---|
| 실행·형식 | 요약이 실제 응답과 일치하는가? | 전체 report 재계산과 별도 해석기가 일치한다. 현재 성공은 인정한다. |
| 모델 행동 | 연산 능력 부족인가, 표현에 따른 수행 차이인가? | 같은 연산을 교환식에서 모두 성공했다. 현재 관측의 설명은 표현·seed 조건에 따른 차이다. |
| 인과 | 괄호를 없애면 해결되는가? | 원식은 오히려 더 실패했다. 순서 효과는 양쪽 괄호 조건에서 유지된다. |
| 효율 | 연결식만 다음 단계로 가져가도 되는가? | 아니다. 잘 작동하는 직접 경로와 전체 판정 비용도 함께 비교한다. |
| 연구 진행 | 표기 변형을 계속 추가해야 하는가? | 지금은 원래 criterion_witness 과제에 재통합하는 편이 더 직접적이다. |
| 공정성 | 통합 경로는 공통 추출값을 공유해도 되는가? | 분기 비교 목적에는 적합하다. 대신 공유 사실을 표시하고 독립 실행·총비용으로 중복 계산하지 않는다. |

## 6. v050의 연구 질문

원래 과제에서 `a`는 제출된 단독 주장이 목표와 같은 문자열인지, `b`는 그 주장이 초기 facts의 원소인지를 뜻한다. probe는 rule=null, parents=[]인 단독 주장이다. 주어진 규칙으로 새 증명을 만드는 과제와 구별한다.

- answer_only_accepts = a
- proof_and_goal_accepts = a AND b
- gap_detected = a AND NOT b

v050에서는 observed의 입력 복사, primitives의 문자열 동일성·배열 소속 판단, 세 finding의 일치를 함께 재검사한다. 원래 witness를 한 호출로 만드는 두 조건과, 실제 추출 응답을 계산 경로에 연결하는 두 조건을 비교한다.

이 단계에서 전체 witness가 정상 작동하면, 기존 증명 그래프·도식·검토 과제와 연결하고 고정 문제·목표에서 A/D/M 축별 조작으로 넘어간다. 단순 표현 비교만 계속 증식시키거나, 이 결과를 전체 A/D/M 성과로 먼저 합산하지 않는다.

## 파일

- `reaudit.json`: 기존 감사기 재실행 판정.
- `recomputed_report.json`: 원문에서 재계산한 전체 report.
- `independent_check.py`, `independent_verification.json`: 별도 계산기와 결과.
- `calls_independent.csv`, `trials_independent.csv`: 호출·판단별 독립 집계.
- `cross_v048_v049.json`: 동일 요청 바이트와 응답 content의 교차 실행 대조.

이번 작업에서 새 사용자 LLM 추론은 실행하지 않았다. 실제 연구 결과 분석 대상은 첨부된 v049 원문이다.
