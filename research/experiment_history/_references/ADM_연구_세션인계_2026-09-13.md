# Thought-Graph / A-D-M 연구 세션 인계 문서

작성 시점: 2026-09-13 KST

이 문서는 새 ChatGPT/Codex 세션에서 현재 연구를 끊김 없이 이어가기 위한 인계용 요약이다. 대화 원문 전체를 복제하는 문서가 아니라, **연구 질문, 검증 기준, 누적 결과, 버전별 의사결정, 현재 최신 상태, 다음 실행 절차**를 보존하는 것이 목적이다.

---

## 1. 연구의 원래 목표

핵심 연구 질문은 단순한 정답률 개선이 아니다.

같은 문제와 같은 목표를 고정한 상태에서 사고/출력 구조를 다음 세 축으로 조작했을 때, **실제 유효한 산출물의 구조가 선택적으로 달라지는지**를 검증하려는 연구다.

- **A = Abstraction / 표현·추상화 수준**
- **D = Decomposition / 실제 지지 의존 구조의 깊이**
- **M = Modality / Method / 검토 대상 수준**

중요한 구분:

1. simulator에서 A/D/M 구조를 결정론적으로 정의·구성·검증할 수 있다는 것.
2. 실제 LLM이 지정된 A/D/M 구조를 직접 생성할 수 있다는 것.
3. 같은 문제·목표에서 A/D/M 요구만 바꾸어 실제 유효한 구조를 선택적으로 바꿀 수 있다는 것.
4. 그 현상이 새로운 문제·모델·예산 조건에서도 재현되는지.

1번이 성공했다고 2~4번이 자동으로 입증되는 것이 아니다.

---

## 2. 반드시 유지해야 하는 검증 원칙

이 연구에서 계속 유지한 기준은 아래와 같다.

### 2.1 성공 판정

- 역할 이름을 요청했다고 성공으로 세지 않는다.
- `shallow`, `deep`, `A1`, `M2` 등의 라벨을 모델이 출력했다고 성공으로 세지 않는다.
- **실제 산출물에서 구조를 다시 측정**한다.
- D는 설명 길이가 아니라 실제 goal 지지 DAG의 dependency depth로 계산한다.
- 규칙 ID만 맞았다고 전체 증명 성공으로 세지 않는다.
- 전체 증명에서는 사실·rule·premise·parent·goal·ancestry·불필요 노드 등을 검증한다.

### 2.2 무보정 원칙

모델이 틀리면 호스트가 다음을 해서는 안 된다.

- 잘못된 rule ID를 정답 ID로 교체
- parent ID 수정
- 누락 fact 추가
- 원하는 경로만 사후 선택
- 불필요 노드 삭제 후 기존 실패를 성공으로 재채점
- 최종 노드 문자열을 올바른 node ID로 추정

호스트가 실행 순서와 인터페이스를 제공하는 것과 **정답을 대신 만들어 주는 것**을 구분한다.

### 2.3 단계형 실행

단계형을 사용할 경우:

- 모델의 실제 원응답을 다음 단계로 전달한다.
- 잘못된 중간값도 형식상 전달 가능하면 그대로 전달한다.
- 단계별 성공과 종단 성공을 분리한다.
- 마지막 답이 우연히 맞아도 앞 단계가 틀렸으면 전체 경로 성공이 아니다.

### 2.4 미관측/오류 처리

서로 구분한다.

- 논리적으로 틀린 응답
- JSON/스키마 파싱 실패
- 미실행
- HTTP/transport 오류
- 모델 identity 오류
- generation budget 초과
- 부분 실행/pending action

미실행을 오답이나 D=0으로 채우지 않는다.

### 2.5 감사 순서

기본 검증 흐름:

`원문 evidence 확인 → 생산 감사 재계산 → 생산 채점기와 독립된 검산기 → 변조/반례 시험 → 상충 해석 비교 → 다음 실험 결정 → 코드 작성 → 새 코드 공격적 재검증 → 필요 시 교정 → 전달`

코드 테스트 통과와 연구 가설 지지를 같은 의미로 사용하지 않는다.

## 3. 초기 성공 기준선과 연구 복귀 전 흐름

### v046~v050: Boolean 구성 실험

작은 Qwen 모델에서 다음 현상이 확인됐다.

- 원식 `(a AND (NOT b))`는 특정 조건에서 실패.
- 동치 교환식 `((NOT b) AND a)`는 성공.
- 실제 `NOT(b) → 반환값 → AND(a,c)` 단계 연결도 성공.
- 연결식에서는 실제 NOT 반환값이 다음 호출에 그대로 들어갔음을 검증.

v047에서는 같은 배치에서 원식 실패와 교환식·pipeline 성공을 재현.
v048에서는 새 seed 10개로 확장하여 교환식·pipeline은 유지되고 원식은 일부 seed에서 성공/실패가 갈림.
v049에서는 표현 구성 요소를 분리했고, NOT가 앞에 있는 직접식들이 안정적으로 성공하는 패턴을 확인.
v050에서는 원래 criterion 판단 작업으로 재통합했지만, 핵심 양성 gap 조건에서 통합 판단이 실패했다.

이 구간의 결론:

- 작은 모델이 복합 논리를 전혀 못 하는 것은 아님.
- 표현과 실행 구조에 따라 성패가 바뀜.
- 성공한 Boolean 하위 경로가 있다고 A/D/M 본 가설이 자동 입증되는 것은 아님.

## 4. A/D/M 직접 실험으로 복귀한 이후

### v051 — 첫 A/D/M 통합 pilot

- 같은 문제/목표에서 A×D×M 12역할을 실제 LLM에 요구.
- 전체 성공 0/240.
- 다만 노드별 사실·규칙 적용은 다수/전부 정상인 부분이 있었음.
- 모델은 `final` 필드에 node ID 대신 목표 문자열을 쓰고, shallow/deep 두 경로를 함께 출력하는 등 통합 구조 작성에 실패.
- M2 평가 기준 판정도 실패.

핵심 판단:

- simulator의 구조적 가능성과 실제 LLM 제어 성공은 별개.
- “이론이 틀렸다”로 바로 갈 수 없음.
- 형식 실패, 경로 선택 실패, 증명 구성 실패, 검토 실패를 분리해야 함.

### v052~v054 — D 단독 진단

- D 축을 따로 보기 시작.
- 깊이 정의를 더 명시해도 선택적 D 제어는 살아나지 않음.
- 규칙 제시 순서를 바꾸면 모델 선택은 달라졌지만 shallow/deep 지시 자체에는 반응하지 않는 패턴 확인.

### v055 — Qwen vs Gemma

- Qwen: 유효한 증명은 많이 만들지만 D 지시에 따른 선택적 제어 실패.
- Gemma: 증명 구성 자체에서 다수 실패.
- 두 모델의 `0/40`을 같은 원인으로 묶지 않음.

### v056 — system/user split vs merged

- 메시지 배치를 합쳐도 D 제어가 살아나지 않음.
- Qwen/Gemma 모두 선택적 D 제어 0.

### v057 이후 — 경로 선택과 전체 증명 생성 분리

- “전체 증명 작성이 어려운가?”와 “경로 선택부터 실패하는가?”를 분리하는 실험으로 전환.
- 이후 v058~v063에서 규칙 순서, terminal 선택, shallow/deep 지시, 지정 규칙 등을 단계적으로 분해.

## 5. v058~v063의 중요한 결론

### v058

- Qwen에서 얕은 graph 생성 성공 기준선이 있었음.
- 작은 선택 과제와 전체 graph 생성 성능이 같지 않음을 확인.

### v059~v060

- 규칙 배열에 따라 선택이 변함.
- 처음에는 “목록 두 번째”와 “첫 goal 도출 규칙” 설명이 겹쳐 구분 불가.
- v060에서 두 설명이 서로 다른 답을 예측하도록 배열을 바꾸자, 첫 goal 도출 규칙 쪽과 일치.
- 단, 내부 메커니즘을 발견했다고 확대하지 않음.

### v061

- 규칙 순서를 고정하고 shallow/deep 지시만 바꿈.
- 40회 모두 같은 규칙 선택.
- shallow는 맞고 deep는 실패.
- 깊이 지시 자체가 선택을 바꾸지 못함.

### v062

- 마지막 규칙을 명시해서 전체 증명을 만들게 함.
- 규칙 이름은 거의 맞췄지만 전체 증명은 0/40.
- “외부 지시를 전부 무시한다”는 설명은 부정확해짐.

### v063

- 새 모델 호출을 중단하고 v062 실패를 오프라인 진단.
- 같은 K01/Gemma 문구·규칙 위치 변형을 계속하는 분기를 종료.
- 연구 전체 종료가 아니라 **국소 진단 분기 종료**.

## 6. 연구 복귀 결정

이후 핵심 판단:

> 실패 원인을 계속 더 잘 설명하는 작업이 원래 연구를 대신하면 안 된다.

따라서:

- Gemma/K01 진단을 종료.
- 실제 유효 graph 생성 이력이 있는 Qwen에서 다시 D를 직접 시험.
- A/M은 이번 단계에서 섞지 않음.
- 성공/실패/종료 기준을 결과 전에 동결.
- 새 문제 구조를 추가하되 독립 holdout이라고 과장하지 않음.

이 결정으로 v064 이후가 시작됐다.

## 9. v066 — direct vs staged 계획→증명 구조

### 목적

같은 지정 구성 실패를 문구만 고쳐 반복하지 않고,

- direct: 한 번에 전체 증명 생성
- staged: 모델이 규칙 경로를 먼저 계획 → 그 실제 원응답을 다음 호출에 전달 → 전체 증명 생성

을 비교.

### 설계상 핵심

- planner의 원응답을 그대로 후속 호출로 전달.
- 호스트가 규칙 목록을 고치지 않음.
- 잘못된 계획 뒤 최종 증명이 우연히 맞아도 전체 staged 성공이 아님.
- 동일 문제/seed/조건에서 direct/staged 비교.

### 실제 실행 상태

- live / complete
- inference_calls = 36
- completed_actions = 48
- differences = []
- independent verified = true fileciteturn4file0L5-L10

### 실제 결과

- direct strict 증명: 일부 성공(T02 중심).
- direct 선택적 D 제어 pair: 0/6.
- staged planner 계획 유효: **0/12**.
- staged 종단 성공: **0/12**.
- 후속 graph 중 일부는 잘못된 계획을 그대로 따랐지만 전체 유효 증명은 아님.

문제별 planner 패턴:

- T02: `r83, r69` 같이 서로 이어지지 않는 terminal 규칙 조합.
- E01: 중간 규칙을 만들지만 마지막 규칙이 그 중간 결과를 사용하지 않는 조합.
- E02: `Pw`까지 만들지만 최종 `Pg` 규칙이 빠진 계획.

### 판단

- 원응답 전달 과정의 결함으로 설명할 수 없음.
- planner가 애초에 유효한 완전 경로를 만들지 못함.
- 따라서 기존 `모델 계획 → 증명` staged 구조는 종료.
- 하지만 **정상 계획을 입력받은 generator 자체의 능력은 아직 미확인**.

## 10. 현재 최신 상태: v067 준비 완료, 아직 실제 실행 전

### v067의 목적

**정상적인 참조 규칙 경로를 실험자가 제공했을 때, 모델이 전체 증명 graph를 재구성할 수 있는가?**

이것은 양성 대조(positive control)다.

중요:

- 정답 규칙 경로를 명시적으로 제공한다.
- 따라서 성공해도 자율 D 제어가 아니다.
- 전체 graph/노드 ID/parent ID/final_node_id 정답은 제공하지 않는다.
- 모델이 실제 graph를 직접 작성한다.
- 호스트는 잘못된 graph를 수정하지 않는다.

### 제공할 참조 경로

- T02 short: `r83`
- T02 long: `r21 → r57 → r04 → r69`
- E01 short: `n52`
- E01 long: `n08 → n91 → n37`
- E02 short: `m18 → m76`
- E02 long: `m33 → m05 → m84 → m41`

### 규모

- 3문제 × 2seed × 2참조 경로 = **12회**
- planner 호출 없음.

### 결과 해석

- 12/12: 정상 계획을 공급하면 재구성이 가능한 generator 기준선 확보.
- 0/12: 현재 모델/전체-DAG 출력 계약에서 양성 대조도 실패. 같은 문구 변형 반복 금지.
- partial: 성공/실패 범위를 그대로 보고.
- 미완료/파싱불가: 전체 gate null.

## 11. 새 세션에서 바로 해야 할 일

사용자가 v067을 아직 실행하지 않았다면 다음 순서다.

### 11.1 PowerShell 하나만 실행

PC의 다운로드 폴더에 `Run-v067-Auto.ps1`을 저장한 뒤:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Run-v067-Auto.ps1"
```

이 자동화는:

`소스 무결성 → 설치 → 자체시험 → v066 evidence 해시/감사 → Qwen identity → 12회 양성 대조 → evidence ZIP → independent JSON`

순으로 진행한다.

모델 다운로드/갱신/서버 자동 시작은 하지 않는다. Ollama와 기존 Qwen은 사용자가 켜 둬야 한다.

### 11.2 새 세션에 올려야 할 결과

실행 완료 후 최소 다음 두 파일을 올린다.

- `v067_reference_<실행시각>_evidence.zip`
- `v067_reference_<실행시각>_independent.json`

가능하면 PowerShell 실행 로그도 함께 올린다.

### 11.3 새 세션에서 요청할 문장

다음처럼 요청하면 된다.

> 첨부한 v067 evidence와 independent 결과를 이 인계 문서의 검증 원칙대로 원문부터 재검산해줘. 결과를 관찰/추론/원인 가설로 나누고, 사전 종료 기준에 따라 다음 실험 방향을 결정해줘. 다음 소스를 만들 필요가 있다면 구현 후 반례·회귀·독립 검산까지 한 뒤 전달해줘. 기존 실패를 보정하거나 성공으로 재채점하지 마.

## 12. v067 이후 의사결정 가이드

### 경우 A — v067 12/12 성공

확인되는 것은:

> 정상 규칙 경로가 주어지면 모델이 전체 증명을 구성할 수 있다.

확인되지 않는 것은:

- D 지시만으로 경로를 자율 선택
- A/M 제어
- internal hidden-layer control
- 비용 우월성
- 새로운 문제에서의 일반화

그 다음 연구 질문은:

> D 요구만 보고 **경로 선택**을 수행한 모델 원값을, 검증된 generator에 무보정 전달하면 종단 증명이 선택적으로 달라지는가?

즉 planner를 그냥 다시 쓰는 것이 아니라, **선택 모듈 자체의 출력 계약을 더 단순하고 검증 가능하게 한 뒤 positive-control generator와 연결**하는 별도 실험을 설계할 수 있다.

### 경우 B — v067 0/12

의미:

- 경로 선택 문제를 제거해도 현재 전체-DAG graph 생성 계약에서 증명 구성에 실패.
- 같은 문구/예제/경로 ID 반복은 종료.

다음 후보:

- 더 단순한 출력 계약(예: 한 노드씩 append-only)과 전체-DAG direct 비교.
- 다른 모델에서 동일 positive control.
- D 생성 경로와 별개로 A/M 단독 실험을 병렬로 재설계.

단, 모델 하나의 실패를 전체 A/D/M 이론 실패로 확대하지 않는다.

### 경우 C — 일부 성공

- 문제별/short-long별/seed별 범위를 보존.
- 성공 조건만 골라 전체 성공으로 만들지 않는다.
- 성공/실패 구조 차이가 다음 결정을 실제로 바꾸는 경우에만 한 번의 제한된 진단을 설계.

## 13. 연구 방향에 대한 현재 총평

현재까지 연구 방향은 다음 이유로 유지할 가치가 있다.

1. 실패를 성공처럼 보정하지 않았다.
2. 규칙 선택, 증명 작성, 메시지 배치, 계획 생성, 전달, strict graph 구성 등을 차례로 분리했다.
3. simulator 성공과 실제 LLM 성공을 구분했다.
4. 원문·생산 계산·독립 계산을 반복 대조했다.
5. 사전 종료 기준을 실제로 적용해 같은 분기를 끊었다.

하지만 현재까지 **선택적 D 제어 자체는 성공하지 않았다.** 따라서 논문의 핵심을 이미 입증했다고 표현하면 안 된다.

현재 가장 정확한 상태는:

> **A/D/M 가설을 직접 검증하기 위한 측정·실행 인프라와 실패 분해는 상당히 진행됐지만, 실제 LLM에서 D를 선택적으로 제어하는 성공 기준선은 아직 확보하지 못했다. v067은 경로 선택을 제거한 positive control로, generator 단계 자체가 가능한지 확인하는 다음 분기점이다.**

## 14. 새 세션의 Assistant/Codex에게 요구할 작업 방식

새 세션에서도 아래 방식을 유지한다.

- 사용자가 올린 summary만 보고 결론내리지 말고 evidence 원문을 본다.
- 기존 independent PASS를 새 독립 증거로 중복 계산하지 않는다.
- 생산 채점 결과를 그대로 읽는 검산기를 독립 검산이라고 부르지 않는다.
- 관찰 → 가능한 설명 → 설명을 구분하는 증거 → 현재 가능한 결론 순으로 쓴다.
- 내부 모델 원인은 원문으로 직접 구분되지 않으면 가설로만 둔다.
- 성공과 실패를 모두 보존한다.
- 실행하지 않은 것을 실행했다고 쓰지 않는다.
- actual model inference, synthetic HTTP, code unit test, offline re-audit를 명확히 구분한다.
- 새 소스는 기존 버전을 덮어쓰지 않고 새 버전으로 추가한다.
- 실패 시 자동 재시도/새 RunName 반복 금지.
- 모델 다운로드·갱신·서버 시작 자동화 금지.
- 사용자 PC에서 실행하기 쉽게 PowerShell 자동화 1개를 제공하는 것을 기본으로 한다.
- 소스 작성 후 반례, 부분 실행, 변조, 잘못된 중간값, 한국어 보고서 변조, request drift를 검사한다.
