### 4.1 H01: 규칙 수가 같은 실제 양방향 종단 성공

문제·목표·seed·후보 순서를 고정하고 shallow/deep 요구만 바꾼 쌍이다.

| seed | shallow 시행 | 실제 D / 규칙 수 | deep 시행 | 실제 D / 규칙 수 |
|---:|---|---:|---|---:|
| 64001001 | t002_explicit_rule | 2 / 3 | t003_explicit_rule | 3 / 3 |
| 64001002 | t009_explicit_rule | 2 / 3 | t008_explicit_rule | 3 / 3 |

최초 사실은 J64, J96이고 목표는 J32로 동일하다.

```text
작은 D 요구의 실제 증명:
J64 → J11
J96 → J39
J11 AND J39 → J32
규칙 수=3, 실제 D=2

큰 D 요구의 실제 증명:
J64 → J20
J20 AND J96 → J54
J54 → J32
규칙 수=3, 실제 D=3
```

따라서 이 성공은 규칙을 더 많이 출력했다는 의미가 아니라, 규칙 수가 같은 상황에서 목표를 지지하는 의존 깊이가 실제로 달라진 것이다. 성공은 작은 D 후보가 먼저 놓인 순서에서 관찰됐다. 반대 후보 순서에서는 선택기가 두 요구 모두 큰 D 경로를 골라 양방향 제어가 성립하지 않았다.

이 두 seed는 **한 구조의 반복 관찰**이다. 두 개의 독립 구조나 새 holdout 성공으로 세지 않는다.

### 4.2 H04: 증명 구성은 모두 성공하지만 선택은 고정

명시군은 본실험 8/8, 참조 4/4의 증명을 구성했다. 규칙 5개·D=3의 병렬 구조와 규칙 4개·D=4의 의존 구조 모두 유효하게 만들 수 있었다. 그러나 shallow/deep 요구가 바뀌어도 같은 첫 후보를 선택하여 양방향은 0/4다.

생성 성공과 선택 제어가 분리되는 직접적인 사례다. H04의 네 종단 실패는 명시군에서 생성 오류가 아니라 선택 오류다.

### 4.3 H03: 유효한 역방향 D 쌍 두 개

명시군에서 두 seed 모두 작은 D 후보가 먼저 놓인 조건은 다음과 같았다.

```text
shallow 요구 → 유효 D=3, 규칙 수=3
 deep 요구 → 유효 D=2, 규칙 수=4
```

실제 증명은 맞지만 요구 방향은 반대다. 이러한 reversed 쌍은 2개이며 성공에 합산하지 않는다. 생성 개선으로 기존 선택 오류가 더 충실히 최종 graph에 반영된 것이지, 생성기가 올바른 선택을 역전시킨 것이 아니다. 규칙 수 혼동이라는 행동 해석과 일치하는 조건이지만 전체 선택 실패의 내부 원인은 특정하지 않았다.

## 5. 왜 형식 개선이 아니라 실제 연결 개선인가

두 군은 같은 모델·출력 스키마·API 옵션·seed·공유 선택을 사용한다. base에도 현재 규칙 ID와 전체 규칙 목록이 있다. 명시군에서 규칙 단계에 추가한 것은 해당 규칙 객체의 중복 표시뿐이다.

```json
{"requested_rule":{"id":"u70","premises":["J20","J96"],"conclusion":"J54"}}
```

이미 problem.rules에 있는 내용이며, 정답 부모 ID·완성 graph·binding·후보 D를 추가한 것이 아니다. 후속 이력은 각 군이 실제 작성한 원응답 그대로다. 호스트가 잘못된 부모를 고치거나 올바른 중간값으로 대체한 흔적은 없다.

원요청 274짝에서 API·출력 스키마·지시문이 같음을 확인했다. 각 군의 실제 history 차이를 별도로 보존하고 현재 규칙 객체를 제거하면 나머지 구조적 입력은 동일했다.

### 5.1 같은 실제 history에서 부모 누락이 해결된 예

`t003_*_rule_01`은 두 군의 이전 응답 문자열까지 동일하다.

```text
기존 노드:
n001=J64, n002=J96, n003=J20
적용 규칙:
u70: J20 AND J96 → J54

base node.parents:          [n003]       → J20만 연결, 실패
explicit_rule node.parents: [n003, n002] → J20·J96 연결, 성공
```

이 조건에서는 현재 규칙 재표시 외에 실제 입력 이력이 달라진 것으로 설명할 수 없다. 이 규칙의 본실험·참조를 합친 결과는 0/8 → 8/8이다.

명시군의 종단 실패 18건 중 16건은 이미 선택을 잘못한 조건이다. 그중 3건에는 생성 오류도 함께 있으므로 실패 원인을 서로 배타적으로 단순 합산하면 안 된다. 나머지 2건은 올바른 선택 이후 생성에 실패한 H02 `t019`, H03 `t028`이다.

**현재 선택 원응답을 바꾸지 않는다는 조건**에서는 생성만 개선하여 추가할 수 있는 종단 성공은 최대 2건이다. 양방향 2/16 상한은 이미 달성했다. 이 상한은 미래의 선택기를 변경한 실험 전체에 적용하는 것이 아니다.

### 6.2 명시군의 잔여 규칙 오류 9개

| 규칙 | 잔여 오류 | 내용 |
|---|---:|---|
| H02 v15 | 5건 | K36·K98이 필요한데 K47·K98을 연결하거나 K98 누락 |
| H02 v19 | 1건 | K41 대신 K47을 연결 |
| H03 w04 | 3건 | L76 하나가 필요한데 L54·L50을 연결 |

본실험에서 생성 실패 5건, 참조에서 3건이다. `t018`에 규칙 오류 두 개가 있으므로 규칙 오류 9개가 실패 증명 9개를 뜻하지 않는다. H01과 H04에는 명시군 규칙 오류가 없었다. 부모 부족 1건, 과다 3건, 개수는 같지만 원자가 틀린 경우 5건이며 모두 premise_counter_mismatch다.

특히 `w04: L76 → L96`에서는 올바른 L76 노드가 이미 있는데도 그 부모인 L54·L50을 직접 연결한 응답이 남았다. 단일 전제 연결도 전수 안정화되지는 않았다. 이 오류를 호스트가 고쳐 성공 처리하지 않는다.

## 7. 재현성과 해석상 실제 한계

### 7.1 동일한 요청·seed에서 응답이 달라진 사례

두 군의 초기 사실 요청은 48짝 모두 바이트 단위로 같다. 그러나 원응답 content가 4짝에서 달랐다. 그중 한 짝은 공백·개행만, 세 짝은 유효한 사실 노드의 ID까지 달랐다. 초기 사실 정답률은 모두 유지됐다.

본실험의 유일한 생성 악화 `t030`은 base에서 `node_L69` 같은 원자형 ID, 명시군에서 `n001` 같은 순번형 ID를 사용했다. 이 차이는 현재 규칙 객체가 처음 추가되기 전의 동일 사실 요청에서 이미 생겼다. 따라서 t030을 국소 규칙 표시 하나가 직접 악화시켰다고 단정하지 않는다. 관측된 생성 성패 차이는 그대로 기록한다.

이 사실로 전체 개선을 지우지도 않는다. 실제 history가 같은 규칙 단계에서 21건의 명시군-only 개선이 있었고, 전반적인 생성·참조 짝비교도 개선 방향이다. 응답 차이의 하드웨어·서버·내부 원인은 이번 자료에서 식별되지 않았다.

### 7.2 실행 순서

base를 먼저 실행한 단위와 명시군을 먼저 실행한 단위는 각각 24개다. 본실험만 보면 base-first 16조건의 생성은 base 3/16, 명시군 12/16이며, explicit-first 16조건에서는 base 6/16, 명시군 15/16이다. 어느 군이 먼저인 층에서도 명시군이 더 많이 성공했다.

이는 실행 순서 단독 설명을 점검한 기술통계이며 캐시·하드웨어 효과를 분리한 실험이나 독립 재현은 아니다.

### 7.3 v078은 과거 대조가 아니라 보존할 이전 배치

이번 base 참조는 4/16이고 v078 base 참조는 5/16이었다. 실제 차이는 `t034_base`의 생성 성공 → 실패다. 두 버전의 base 및 공유 선택 306개 요청 가운데 실제 bytes가 같은 요청은 265개다. 나머지는 이전 모델 응답이 달라져 history가 달라진 경우다. 같은 요청 265개 중 16개에서 response.content가 달랐고, 그중 8개는 JSON 값도 달랐다.

이번의 생성 개선 효과는 **v079 내부의 9→27, 4→13 짝대조**로 판단하며 v078의 5/16을 이번 base 점수로 대신 쓰지 않는다. 기존 v078 보고서와 evidence는 수정하지 않았다.
