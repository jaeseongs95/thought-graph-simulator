## 3. 설계한 구조와 요청이 실제로 맞는가

원 규칙에서 모든 목표 증명 대안을 재귀적으로 열거하고, 공유 노드의 규칙 수는 집합으로 계산하고, 경로별 D는 전제의 최대 깊이로 다시 계산했다.

| 문제 | 작은 D / 규칙 수 | 큰 D / 규칙 수 | 관계 |
|---|---:|---:|---|
| H01 | 2 / 3 | 3 / 3 | 규칙 수 동일 |
| H02 | 3 / 4 | 4 / 4 | 규칙 수 동일 |
| H03 | 2 / 4 | 3 / 3 | 규칙 수-D 역전 |
| H04 | 3 / 5 | 4 / 4 | 규칙 수-D 역전 |

네 문제 모두 동결 metadata와 실제 계산이 일치한다. 제공 후보는 각각 목표에 도달하며, 각 후보의 모든 규칙과 초기 사실이 목표를 지지한다. 전제 누락이나 미사용 초기 사실 때문에 원래부터 성공 불가능하게 만들어진 후보를 발견하지 않았다.

16개 선택 비교 쌍에서는 실제 요청 bytes가 shallow 요구 문자열을 deep 요구 문자열로 바꾼 것 외에 동일함을 확인했다. 문제·목표·후보·순서·seed·API 설정이 쌍 안에서 유지됐다. 선택 결과는 후보표에 그대로 대응되고, 후속 요청의 `selection_original.content`와 `history.content`는 원응답과 일치한다. 잘못된 경로 선택을 올바른 경로로 고친 흔적은 없다.

v077과 대조하면 현재 사용하는 7개 header, API 기본 설정, seed, 생성/선택 스키마가 동일하다. `measure.py`, `stages.py`, `audit_graph.py`도 바이트 단위로 동일하다. header 객체 전체가 다른 이유는 사용하지 않는 `binding_rule` header가 제거됐기 때문이며, base header가 바뀐 것은 아니다. 모델 identity 계약도 동일하다.

**검토한 범위에서는 이번 0/16을 만들어 낸 생산 채점·후보 매핑 오류를 발견하지 않았다.** 다만 이는 실험 설계가 원인들을 각각 분리했다는 뜻과는 다르다. 이름과 규칙 나열의 독립 효과는 이번 설계에 포함되지 않는다.

근거: `additional_metrics.json`, `raw_audit_result.json`의 `designs`, 번들 `source/design.py`, `source/report.py`.

## 5. 선택 16/32의 내부 패턴

### 5.1 전체 정답률보다 양방향 패턴이 중요하다

후보 `route_0`은 항상 첫 번째 위치다. 모델은 32회 중 **28회 첫 후보/route_0을 선택**했다. 이 설계만으로 위치 선호와 ID 선호를 분리할 수 없다.

16개 쌍의 분포:

| 선택 패턴 | 쌍 수 |
|---|---:|
| D 요구가 바뀌어도 같은 후보 | 12/16 |
| 요구 방향에 맞게 두 후보를 바꿈 | 2/16 |
| 요구와 반대 방향으로 두 후보를 바꿈 | 2/16 |

이 배정에서는 첫 후보를 항상 선택해도 전체 선택 정답이 16/32가 된다. 따라서 이번 총계 50%만으로 D 이해/제어가 작동했다고 판단할 수 없다. 그렇다고 응답 전체를 첫 후보 고정 하나로 설명할 수도 없다. 아래 예외가 실제로 존재한다.

### 5.2 후보 순서에 따른 구체적인 선택

아래 선택 패턴은 두 seed에서 동일했다. 각 행의 shallow/deep 값은 후보가 가진 실제 D다.

| 문제 | 후보 나열 | shallow 요구 시 선택 D | deep 요구 시 선택 D | 해석 |
|---|---|---:|---:|---|
| H01 | 작은 D → 큰 D | 2 | 3 | 양방향 정답 |
| H01 | 큰 D → 작은 D | 3 | 3 | 같은 후보 고정 |
| H02 | 작은 D → 큰 D | 3 | 3 | 같은 후보 고정 |
| H02 | 큰 D → 작은 D | 4 | 4 | 같은 후보 고정 |
| H03 | 작은 D → 큰 D | 3 | 2 | 양방향 역전 |
| H03 | 큰 D → 작은 D | 3 | 3 | 같은 후보 고정 |
| H04 | 작은 D → 큰 D | 3 | 3 | 같은 후보 고정 |
| H04 | 큰 D → 작은 D | 4 | 4 | 같은 후보 고정 |

H01은 규칙 수가 같아도, 작은 D 후보를 먼저 놓은 순서에서는 요구에 맞는 선택이 가능했던 사례다. 이 선택 단계의 부분 효과는 보존한다. 하지만 후보 순서를 뒤집었을 때 유지되지 않았고, 올바르게 선택한 deep 증명의 생성도 실패했다.

### 5.3 핵심 반례: 유효한 증명 두 개가 실제로 반대 방향으로 생성됨

H03, seed `64001002`, 후보 순서 `[작은 D, 큰 D]`:

| 시행 | 요구 | 선택 | 최종 graph 유효성 | 실제 D | 목표 지지 규칙 수 |
|---|---|---|---|---:|---:|
| t033_base | shallow: 작은 D | route_1 | 유효 | **3** | **3** |
| t032_base | deep: 큰 D | route_0 | 유효 | **2** | **4** |

두 증명은 모두 같은 목표 `L96`에 도달하며 각 규칙·부모·final도 유효하다. 그러나 요구 방향에 완전히 반대다.

`t032_base`의 실제 구조는 세 병렬 가지를 마지막에 합친다.

```text
L69 → L12
L35 → L82
L50 → L38
L12 AND L82 AND L38 → L96

규칙 수 4, 실제 목표 깊이 D=2
```

`t033_base`의 실제 구조는 의존 관계가 이어진다.

```text
L69 AND L35 → L54
L54 AND L50 → L76
L76 → L96

규칙 수 3, 실제 목표 깊이 D=3
```

**서로 다른 D의 증명을 만드는 것과, 사용자가 요구한 방향에 맞춰 D를 선택적으로 제어하는 것은 다르다.** 이번 사례는 생성 무능력만으로 설명할 수 없는 선택 방향의 문제다.

이 방향은 “짧다/길다를 규칙 수로 판단”하는 행동과 일치한다. 그러나 H02/H04의 첫 후보 고정과 H03의 다른 후보 순서를 함께 보면, 전체 선택 실패의 원인을 규칙 수 혼동 하나로 단정할 수는 없다. 현재 확인된 것은 이 조건의 역방향 선택·출력 패턴이다.

원응답: `representative_raw/t032_select/`, `t033_select/`, `t032_base_*/`, `t033_base_*/`. 원문은 가공 없이 복사했다. 위 도식은 원 graph를 설명한 것이며 재채점용 수정본이 아니다.

| 부모 수 일치 | 146/178 |
| 부모 수는 맞으나 원자가 다름 | 18건 |

50개 잘못된 규칙 단계의 오류 코드는 모두 `premise_counter_mismatch`였다. 유효하지 않은 graph 34개는 각각 적어도 한 번의 실제 전제 연결 실패를 포함한다. 존재하지 않는 부모 ID, 잘못된 규칙 ID, 잘못된 결론 원자, 순환, final ID 실패로 집계된 사례는 이번 원응답에서 없었다.

실패 50건은 부모가 적은 경우 22건, 많은 경우 10건, 수는 같지만 원자가 틀린 경우 18건이다. 따라서 부모 개수만 고정하는 제약으로 이번 실패 전부를 해결할 수 없다. 앞 단계가 틀렸는데 마지막 goal 노드와 final ID가 맞아 보이는 경우에도 전체 증명은 실패로 유지했다.

### 6.3 H01: 올바른 선택 이후에도 빠진 전제

규칙 `u70`:

```text
필요: J20 AND J96 → J54
```

`t003_base_rule_01`은 다음처럼 출력했다.

```json
{"node":{"atom":"J54","id":"n004","parents":["n003"],"rule":"u70"}}
```

이때 `n003`은 `J20`이고, `J96`인 `n002`가 history에 존재한다. 모델이 그 노드를 부모로 연결하지 않았다. 본실험·참조를 합친 H01 긴 경로의 `u70`은 0/8 유효했다. 그래서 H01에서 올바른 양방향 선택 2쌍이 있었어도 종단 양방향은 0쌍이다.

### 6.4 H02: 전제가 하나여도 잘못 연결

규칙 `v51`:

```text
필요: K46 → K29
```

`t014_base_rule_01`의 원응답:

```json
{"node":{"atom":"K29","id":"n004","parents":["n001"],"rule":"v51"}}
```

앞 단계에서 `n003=K46`이 이미 정상적으로 생성됐지만, 모델은 `n001=K47`을 부모로 연결했다. 전제 수가 하나인 단계에서도 연결이 틀렸다는 관찰이다. 다중 전제 복잡성 하나로 모든 실패를 설명하지 않는다.

H02에서 `v51`은 1/6, `v52`는 0/6, `v15`는 0/6 유효했다. 본실험과 참조 모두 완전한 증명은 0건이었다.

### 6.5 H04: 부모 개수는 같지만 실제 전제가 다름

## 7. 이전 결과와 비교하여 어디까지 결론 내릴 수 있는가

v077 base의 원 결과를 graph 기준으로 다시 집계하면 종단 14/24, 양방향 2/12, 참조 10/12다. v078은 종단 4/32, 양방향 0/16, 참조 5/16이다.

그러나 **같은 문제에서 생성기만 바꾼 대조 실험이 아니다.** 유지된 base 계약을 새 문제에 적용한 것이다. 따라서 이 차이를 “v078 코드 변경이 성능을 그만큼 떨어뜨렸다”는 인과 효과로 쓰지 않는다. 관찰되는 것은 **기존 개발 문제의 성과가 새 확인 세트에서 유지되지 않았다는 것**이다.

현재 결론을 가설별로 나누면 다음과 같다.

| 주장/질문 | 이번 자료의 판정 |
|---|---|
| 실제로 유효한 서로 다른 D의 graph를 만들 수 있는가 | 일부 조건에서 관찰됨. 특히 H03 역방향 쌍의 두 graph 모두 유효 |
| 현재 계약이 새 네 문제에서 요구 D를 종단으로 양방향 제어하는가 | 0/16, 이번 배치에서 재현되지 않음 |
| 규칙 수가 같은 상황에서도 요구에 따른 경로 선택이 가능한가 | H01 특정 후보 순서에서 2쌍 관찰. 다른 순서와 종단에서는 유지되지 않음 |
| 모든 선택 실패가 단순 규칙 수 혼동 때문인가 | 자료로 특정되지 않음. 첫 후보/ID 고정과 역전 반응이 함께 존재 |
| 생성 실패는 JSON/final 형식 문제인가 | 이번 배치에서는 아님. 원응답 정상, 실제 전제 연결 오류가 관찰됨 |
| 이전 개발 문제의 부분 성공이 잘못 채점된 것인가 | 이번 결과가 그 결론을 뒷받침하지 않음. 기존 점수와 evidence 보존 |
| 작은 모델의 내부 추론 능력/용량이 확정 원인인가 | 해당 내부 원인을 분리한 실험이 아님 |

전수 100% 기준과 일부 효과를 구분하되, 이번 4건의 단방향 종단 성공을 안정적 D 제어로 확대하지 않는다. 반대로 0/16을 “모든 graph 생성이 0건”이나 “이전 부분 효과도 없었다”로 바꾸지 않는다.

## 8. 현재 가능한 운영 판단

**v078은 완료된 구조 전이 확인 배치로 닫고, 새 구조의 선택적 종단 D 제어를 확보했다고 보고하지 않는 것이 맞다.** 가드 삭제, 같은 배치의 반복 실행, 결과가 좋아질 때까지 seed/문구를 바꾸는 작업은 이번 분석에서 수행하지 않았다.

후속 연구에서는 다음 두 경계를 유지해야 한다.

1. H01~H04를 이후 조정에 사용한다면, 그 이후에는 이미 결과를 본 개발/진단 문제로 다룬다. 새로운 확인 결과와 분리한다.
2. 다음 설계가 선택 또는 생성 중 무엇을 개선하려는 것인지 정하고, 동일한 종단 성공 기준을 유지한다. 유효한 두 graph가 역방향으로 생성된 H03을 선택 문제의 사례로, 정답 경로가 주어져도 실패한 참조들을 생성 문제의 사례로 남긴다.

이 결과만으로 추가 부모 제약이나 binding을 기본으로 채택할 근거가 새로 생긴 것은 아니다. 이름/표현 영향, 구조 영향, 모델 내부 원인의 분리도 아직 수행하지 않았다. 이 분석은 새로운 v079 소스나 모델 실행을 만들지 않는다.
