# v056_layout_01 — 메시지 배치 실험 분석과 v057 결정

## 결론

480개 실제 호출은 완료됐고 480개 모두 출력 형식 검사를 통과했다. 분리(split)를 병합(merged)으로 바꾸어도 선택적 D 제어는 어느 모델에서도 생기지 않았다. Qwen의 유효 증명은 90/120 → 87/120, Gemma는 0/120 → 3/120이다. 유효성의 작은 변화와 D 지시 이행을 분리한다.

다음 단계는 또 다른 메시지 배치나 세 번째 모델을 추가하는 것이 아니라 **전체 증명 작성과 마지막 규칙 선택을 나눠 검사하는 v057**이다. 같은 문제에서 “짧은/긴 경로를 선택하라”는 요구를 최소 출력으로도 이행하지 못하는지 확인한다. 선택만 성공해도 완전한 증명이나 A/D/M 핵심 성공으로 승격하지 않는다.

## 1. 사용한 자료와 원문 재검사

- 실제 입력: `v056_layout_01_evidence.zip` (SHA-256 `426f49a62aa8687bed8a678277f866a85369b6621effa2b25a776b81bf7998db`).
- 추가 첨부: `v056_layout_01.plan.baseline.zip`. v056 증거 안의 `run/baseline/v055_evidence.zip`과 바이트 동일하다. 이미 제출된 실제 v055 원본과도 동일하다.
- 실행 기준: 이전 `current_session_full_chat.md`에서 정한 원문 보존, 무보정, 무재시도, 미측정/오답 분리, 제3자 심사 관점별 반론 대조, 작성 후 재검토와 반례 시험.
- v056 배포 코드를 별도 폴더에 풀고 원문을 재감사했다. 첨부 `source_snapshot`을 실행한 것이 아니다.

manifest 대상 **1,113개 파일**의 목록과 해시, 외부 계획/snapshot, 520개 이벤트(480호출+40 metadata 기록), 원문 요청/응답, 각 모델의 동결 identity를 검증했다. 재계산된 **전체 report 객체가 저장된 summary와 동일**했다.

기존 독립 검산기는 3,738개 필드를 비교해 불일치 0개였다. 이번에 추가 작성한 표준 라이브러리 기반 재귀 그래프 검산기는 3,040개 필드를 비교해 불일치 0개였다. 이들은 같은 480개 응답을 서로 다른 구현으로 검사한 것이며 표본 수를 더한 것이 아니다.

참조 파일: `production_and_existing_independent.json`, `independent_fresh.json`, `recheck_v056.py`, `trials.csv`, `D_pairs.csv`, `layout_pairs.csv`.

## 2. 조건별 결과

|모델|배치|정상 출력 형식|유효 증명|선택적 D 제어|
|---|---|---:|---:|---:|
|Qwen|split|120/120|90/120|0/40쌍|
|Qwen|merged|120/120|87/120|0/40쌍|
|Gemma|split|120/120|0/120|0/40쌍|
|Gemma|merged|120/120|3/120|0/40쌍|

`0/40쌍`은 같은 모델·배치·문제·규칙순서·seed에서 shallow와 deep 모두 유효하며 각각 최소/최대 깊이를 갖춘 쌍이 없다는 뜻이다. 한쪽만 맞거나 깊이가 우연히 바뀐 것을 성공으로 세지 않는다.

### Qwen

기존 패턴은 유지됐다. K01 original은 깊이 2, K01 swapped와 T02 original은 깊이 1을 반복했다. T02 swapped는 두 배치에서 모두 30개가 무효였다. merged에서 줄어든 유효 증명 3개는 모두 K01 original의 중립 조건이며, 미등록 규칙 2개와 불필요한 추가 경로 1개였다. 따라서 병합이 shallow/deep 제어를 방해하거나 살렸다는 결과가 아니라 **중립 3건의 작성 오류가 추가된 결과**다.

### Gemma

병합의 유효 증명 3개는 모두 T02 swapped의 깊이 4였다.

|seed|요청|실제 깊이|판정|
|---:|---|---:|---|
|580410664|deep|4|이 응답은 요구 이행|
|223674688|shallow|4|증명은 유효하나 요구 불이행|
|860724506|deep|4|이 응답은 요구 이행|

이 세 건에 대응하는 반대 방향 응답은 유효하지 않아 선택적 성공 쌍이 생기지 않았다. 긴 증명을 만드는 능력의 관측과 지시에 따른 선택 능력을 분리한다.

무효 응답에서는 없는/뒤에 있는 부모 참조, 주어지지 않은 사실, 규칙과 다른 결론·전제, 중복 노드 ID, 최종 참조 오류가 나타났다. 하나의 응답에 여러 오류가 있을 수 있어 결함 빈도는 중복 집계이며 응답 수로 합산하지 않는다. `independent_fresh.json`의 `faults_overlapping`에 구분해 기록했다.

## 3. 이전 v055와의 반복성

v056 split의 요청 240개는 v055 대응 요청과 모두 바이트 동일했다. 동결된 모델/서버 identity도 유지됐다.

Qwen은 120개 모두 증명 유효성 판정이 같았다. 응답 JSON 자체까지 동일한 것은 84/120개였다. Gemma는 118/120개에서 유효성 판정이 같았고, v055의 유효 2건은 이번 split에서는 재현되지 않았다. 응답 JSON 자체는 53/120개가 같았다.

따라서 같은 숫자 seed와 요청을 썼다는 이유로 매번 같은 출력을 보장하거나, Gemma의 0→3건을 안정적인 개선으로 단정하지 않는다. 그 차이의 구체적인 런타임 원인은 이번 기록으로 식별하지 않았다. 핵심인 선택적 제어는 두 배치 모두 0이라는 결과다. `v055_v056_replication.csv`에 대응을 보존했다.

## 4. 다각도 심사 관점의 대조

외부 심사자나 별도 에이전트를 호출한 것은 아니다. 서로 다른 제3자 심사 기준의 주장과 반례를 대조했고, 기술적 독립성은 생산 채점기와 다른 구현으로 확보했다.

|관점|대안/의심|증거에 따른 판단|
|---|---|---|
|측정 타당성|평가기가 잘못 탈락시킨 것인가?|원문·독립 재귀 계산·생산 report가 일치한다. 현재 결과를 바꿀 생산 채점 결함은 발견되지 않았다.|
|메시지 전달|한 user 메시지로 합치면 실패가 해결되는가?|시험한 병합만으로 해결되지 않았다. 계속 배치만 변형할 근거가 약하다.|
|모델 행동|Qwen과 Gemma의 0/40이 같은 내부 실패인가?|Qwen은 유효 경로를 반복하고 Gemma는 그래프 작성 오류가 대부분이다. 두 실패를 같은 원인으로 합칠 수 없다.|
|실험 식별|경로 선택과 증명 작성 중 어디에서 막히는가?|현재는 하나의 긴 출력에서 두 작업을 동시에 요구한다. 규칙 하나만 선택하는 축소 과제를 별도 대조할 가치가 있다.|
|논문 핵심|선택 ID만 맞으면 D 제어 성공인가?|아니다. 선택은 진단 지표다. 실제 유효 증명에서 재계산한 D만 기존 핵심 지표다.|
|재현·비용|모델·배치·문제를 계속 늘려야 하는가?|현재 두 모델·문제·규칙순서를 유지하고, 과제를 분리하는 한 단계로 한정한다. 기존 문제나 실패 seed를 제외하지 않는다.|

### 합의

**v057은 전체 증명 생성(graph) 대 마지막 규칙 선택(choice)을 같은 실행에 넣는다.** 두 모델 모두 merged로 고정한다. 병합이 우월해서 선택한 것이 아니라 모델별 서로 다른 배치를 고르는 혼선을 피하고 하나의 공통 역할 구조에서 과제 차이를 검사하기 위한 선택이다. 기존 split을 포함한 v056 전체 자료는 기준선 ZIP 안에 보존한다.

학습된 기본 전략과 외부 제어의 경쟁이라는 사용자의 가설은 현재 현상과 양립한다. 다만 이번 관측은 출력 행동과 인터페이스 수준이다. 어떤 학습 과정이나 내부 우선순위 때문인지 확정하는 실험으로 바꾸지 않는다.

## 5. v057의 조작과 보존

2모델 × 2출력과제 × 2문제 × 2규칙순서 × 3방향 × 10seed = 480회다. graph 240회, choice 240회이며 각 과제의 80개 중립 응답을 포함한다.

**graph**는 실제 v056 merged 요청과 바이트 동일하다. 기존 증명 DAG 형식과 채점 기준도 동일하다.

**choice**는 원래 문제와 경로 지시를 그대로 전달하되, 증명 DAG 대신 `{"final_rule_id":"..."}` 하나를 작성하게 한다. 입력의 모든 규칙을 그대로 제공한다. 정답 경로, 정답 깊이, 후보별 깊이, 선택할 규칙 ID, 정답 ID enum을 제공하지 않는다. 호스트가 정답을 골라 넣거나 잘못된 ID를 고치지 않는다.

choice에서 올바른 마지막 규칙을 선택하면 문제 명세상 해당 규칙의 경로 깊이를 사후 계산한다. 이를 `implied_depth`로 부르며, 실제 작성된 증명 깊이 `D`와 구분한다. `proof_valid`, `strict_valid`, `D`는 choice에서 null이다. 현재 두 문제는 마지막 규칙별 경로 깊이가 유일하므로 이 진단이 가능하다. 깊이가 유일하지 않은 문제로 바뀌면 승인하지 않는 시험을 추가했다.

이 대조는 출력 요구·설명·schema가 함께 달라지는 **과제 인터페이스 대조**다. 출력 길이 하나만의 효과, 내부 이해도, 모델이 같은 호출에서 선택을 잊어버렸다는 원인을 단독 입증하지 않는다.

## 7. 작성 후 발견·교정한 문제

새 v057 초안의 기준선 수입 함수는 `run/baseline/v056_evidence.zip`만 큰 ZIP 예외로 인정했다. 실제 v056 안에는 더 이전 `run/baseline/v055_evidence.zip`이 있고, 이 파일은 8 MiB를 넘는다. 실제 첨부 파일로 `prepare`를 실행해 추론 없이 실패를 재현했다.

이를 두 개의 정확한 기준선 경로에만 ZIP 한도를 적용하도록 교정했다. 모델 응답의 8 MiB, 로컬 계획의 32 MiB, archive 총 크기/파일 수/경로·중복·해시 검사는 유지한다. 다른 임의 ZIP이나 모델 응답을 예외로 허용하지 않는 반례를 추가했다. 수정 전후 로그는 `v057_prepare_before_fix.log`, `v057_prepare_after_fix.log`다.

이것은 새 코드 준비 단계의 결함이며, 완료된 v056 연구 결과에 대한 채점 수정이 아니다.

## 8. 검증 범위

최종 시험·새 폴더 재추출·자동화 하위 프로세스·합성 반례·source hash 보존의 실제 결과는 같은 분석 묶음의 `VALIDATION_RESULT.json`과 로그를 기준으로 한다. 성공한 합성 모델 응답은 테스트 장치이며 실제 Qwen/Gemma 성과가 아니다.

사용자의 Windows에서 새로운 실제 추론을 이 환경에서 실행하지 않았다. 이 환경의 Python 실행과 Windows PowerShell 실기 실행을 구분한다. 자동화 PowerShell은 앞서 사용자가 실제 실행한 v056 방식의 내장 소스/종료코드 처리 구조를 이어 사용한다.
