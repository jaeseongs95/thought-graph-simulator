# v066 원문 분석과 v067 정상 참조 계획 양성 대조

## 1. 결론

**v066의36회 수집과 검산은 정상 완료됐지만, 실제 선택적 D 대응은 direct0/6쌍·staged0/6쌍이었다.** direct는12개 중4개 strict 증명, 그중 요청 D까지 맞은2개다. staged는 계획12개 모두 무효, 최종 strict 증명0/12, 종단 성공0/12다. 모델의 계획 원문 전달은12개 모두 정확했다.

이번 결과는 '두 호출로 나누면 문제가 해결된다'는 기대를 지지하지 않는다. 사전에 정한 대로 **해당 모델 계획→graph 구조는 종료**한다. 정답 경로를 외부에서 고쳐 끼우거나 같은 문구를 더 강하게 써 다시 성공할 때까지 반복하지 않는다.

다만 정상 계획을 받은 constructor의 관측은 하나도 없었다. 그러므로 현재 결과로 정상 입력에서도 증명 작성이 불가능하다고 결론 내리면 안 된다. v067은 그 빈칸만 확인하는 **정답 경로 제공형 양성 대조12회**다. 모델의 자율적인 경로 선택이 아니라 주어진 유효한 경로를 graph로 재구성하는 기능 검사다. 이를 D/A/M 본 가설 성공으로 승격하지 않는다.

## 3. 실제로 어디서 실패했는가

|단계|응답 수|형식 유효|기본 증명 유효|strict 증명|요청 성공|
|---|---:|---:|---:|---:|---:|
|direct 전체 증명|12|12|11|4|요청 D 이행2|
|staged 계획|12|12|계획 유효0|graph 미측정|계획 D 이행0|
|staged 후속 증명|12|12|6|0|최종 D 이행0|

계획의 유효성은 실제 DAG의 증명 유효성과 다른 측정이다. planned_D를 actual_D로 바꾸지 않았다. proof_valid는 노드별 규칙뿐 아니라 실제 참조·최종 목표 등 기본 graph 계약을 포함하며 strict_valid는 추가로 위상 순서·최종 조상 밖 노드 부재를 요구한다.

### 3.1 계획은 문제별로 동일한 목록을 네 번씩 반복했다

각 문제에서 seed2개×shallow/deep2개=4개의 출력 계획이 모두 같았다.

|문제|실제 목록|실패 이유|
|---|---|---|
|T02|`[r83,r69]`|r83은 곧바로Lg를 만들지만 r69의 전제Lt를 얻는 r21→r57→r04가 빠졌다. 목표를 만드는 두 대안 규칙을 나열한 형태이지 순서대로 적용할 완전한 경로가 아니다.|
|E01_shared_fork|`[n08,n91,n52]`|n08/n91은Ax/Ay를 만들지만 마지막 n52는Aa/Ab만 사용한다. 두 중간 규칙은 최종 목표를 지지하지 않는 불필요한 규칙이다.|
|E02_two_vs_four|`[m18,m33,m05,m84]`|m84의 결론은Pw다. goal Pg를 만드는 m76이나m41이 계획에 없어서 목표까지 도달하지 않는다.|

이는 원문에 관찰된 목록의 특성이다. 모델이 지시를 '의도적으로 무시했다', 내부에서 두 선택지만 생각했다, 학습 우선순위가 더 높았다는 등의 내부 원인으로 확정하지 않는다.

### 3.2 전달은 올바르게 되었고, 전달된 내용이 잘못되어 있었다

12개 construct 요청의 `route_plan_response`를 부모 원응답과 대조했다. parent slot ID, 원 envelope SHA, message.content의 공백·순서·문자열까지 모두 일치했다. 호스트의 전달 오류나 정답 보정은 없었다.

12개 중8개 후속 응답은 비사실 노드의 규칙 순서가 그 잘못된 계획과 정확히 같았다. 그렇다고 성공은 아니다. 계획 자체가 필요한 전제·목표·단일 지지 경로 요건을 위반하고 있었으므로 그대로 따른다고 유효한 목표 증명이 되지는 않는다. 나머지4개는 계획과 다른 규칙을 추가하거나 참조를 잘못 만들었고, 역시 strict 성공이 아니었다.

T02 shallow 한 응답은 누락된 중간 규칙을 모델 스스로 추가하고 깊은 목표도 만들었지만 여러 목표·대안 노드가 함께 남았다. 이것을 호스트가 정답 경로만 골라 strict 성공으로 다시 만들지 않았다. 다른 T02 응답은 잘못된 부모 전제나 존재하지 않는 final 참조가 있었고, E01은 불필요 노드, E02는 잘못된 부모/목표 참조와 계획 밖 규칙 추가가 나타났다.

### 3.3 실패 계층은 섞지 않았다

- direct: 기본 논리/참조 실패1개, 논리는 유효하지만 strict-only 실패7개, strict 증명4개. strict4개는 모두 T02의깊이1이며 shallow2개만 방향까지 맞았다.
- construct: 기본 논리/목표/참조 실패6개, strict-only 실패6개, strict 증명0개.
- planner: 형식 유효12개, 유효 계획0개. 파싱 실패를 오답으로 바꿔서0이 된 결과가 아니다.

오류 코드 중복 빈도는 응답 수와 다르다. 예를 들어 construct에는 extra_unused_node6, premise_counter_mismatch5, missing_final_node1, final_goal_mismatch2, missing_parent1이 기록되며 한 응답에 여러 오류가 겹친다.

## 4. 직접 대조의 재현성과 비용

v066 direct12개와 동봉된 v064의 같은 문제·seed·방향 요청을 비교했다. 요청12개 모두 바이트 동일이고, strict 판정도12개 모두 같았다. 응답 content 자체는10/12가 같았고2개는 달랐다. 동일 seed를 사용했다고 매번 동일 응답을 보장한다고 표현하지 않는다. `v064_direct_replication.json`에 대응을 보존했다.

## 6. v067 소스가 실제로 하는 일

모델이 계획을 작성하는 호출은 넣지 않는다. 다음 정상 참조들을 입력으로 명시하고 모델이 한 번에 전체 graph를 작성한다.

|문제|짧은 참조|긴 참조|
|---|---|---|
|T02|r83|r21→r57→r04→r69|
|E01|n52|n08, n91, n37|
|E02|m18→m76|m33→m05→m84→m41|

요청은 `provided_route_plan.origin="experimenter_verified_reference"`로 실험자가 제공한 정답 경로임을 밝힌다. 모델 원응답으로 위장한 출처/해시를 만들지 않는다. 정답 규칙 목록은 주지만 실제 노드 ID, 부모 ID, 노드 배열, final_node_id를 가진 완성 DAG는 주지 않는다.

모델·서버·digest·옵션·schema·문제·규칙 순서·seed는 보존했다. 자유롭게 최소/최대 경로를 고르는 지시 대신 제공된 경로를 모두 순서대로 사용하라는 지시를 넣는다. v066의 same-byte constructor나 순수 입력정확도 하나만의 인과 대조라고 주장하지 않는다.

3문제×2seed×2참조=12호출. 문제별 두 seed에서 참조 선후를 반전한다. metadata12묶음은 별도다. 생성 설정 상한은12×4096=49,152이며 실제 토큰/시간 보장이 아니다. warmup·재시도·모델 갱신·서버 시작은 없다.

출력은 기존 strict 평가기 바이트 그대로 검사한다. 참조 순서와 다른 동등한 graph는 graph의 국소 strict 성과를 인정할 수 있지만 순서 지정 과제의 이행에는 실패한다. 오류 노드·참조·규칙은 수선하지 않는다.

### 결과별 다음 행동

- 모든12건이 측정되고12/12: 정상 참조 입력에서 생성기 재구성이 가능하다는 기준선. v066에서 계획기만 유일한 실패 원인이었다고 확정하지 않는다. D 제어·A/M 진입은 여전히 미측정이다.
- 모든12건이 측정되고0/12: 현재 모델·전체-DAG 출력 과제의 양성 대조도 종료. 같은 문구를 바꾸어 반복하지 않는다.
- 부분 성공: 문제·참조·seed별 범위를 그대로 남기며, 성공 부분만 새 실험 전체로 올리지 않는다.
- 미완료/파싱·형식 미측정: 전체 기준은null. 관측한 부분은 유지하고 자동 재시도는 하지 않는다.

이 양성 대조만으로 새 구조의 일반화나 내부 사고, 비용 효율, 논문 전체를 입증할 수 없다. 다른 모델/간단한 출력 계약/독립 A·M 실험은 각각 별도 연구 결정이며, 이 gate를 연구 전체의 보편적 필수조건으로 만들지 않는다.

## 7. 작성 후 검증

최종 ZIP을 새 빈 폴더에 풀어 **62개 시험 중61개 통과, Windows 전용1개 제외**를 확인했다. 고정 소스 원위치의 동일62개 시험도 같은 결과였다. 원본 v066의64개 시험은63개 통과·Windows1개 제외였다. 재실행을 서로 다른 연구 표본이나126개의 독립 시험 종류로 더하지 않는다.

별도 참조 명세 검증에서는 고정3문제의 무반복 규칙 목록2,606개를 전수 열거했다. T02의2개, E01의3개(독립 가지의 두 순서 포함), E02의2개 유효 목록만 승인했고, 생산 reference 검사·독립 verifier·표준 라이브러리 분석기가 일치했다. 이 중 입력으로 쓰는 경로는 동결된6개이며 모델 결과를 보고 고른 것이 아니다.

12개 실제 요청을 원 v066 direct와 대조해 모델·나머지 옵션·graph schema·문제 바이트·핵심 graph 지시가 같음을 확인했다. 바뀐 지시와 실험자 참조 제공은 명시된 새 과제 변경이다. 생성기 요청에 depth 채점기나 graph 정답 생성기가 호출되지 않는지 검사했다.

합성 반례에는 정답 재구성, 같은 짧은 경로, 반대 경로, 규칙명만 맞춘 틀린 graph, 불필요 노드, 잘못된 부모, 독립 가지 순서 변경, 파싱 실패, HTTP 중단을 넣었다. 정상 재구성12/12라도 D/A/M gate는 올라가지 않는다. 잘못된 요청·출처·원응답·보고서를 다시 해시해도 독립 검산이 거부한다. 자동화는 실제 Python 하위 프로세스에서 설치→계획→합성12회→감사/증거ZIP/독립검산을 완료했다.

작성 후 정적 검토에서 '0/12이면 종료'라는 문구가 미측정까지 포함할 수 있어 '모두 측정됐는데0/12'로 명확히 했고, next_decision을 기계 판독 가능하게 분리했다. 실제로 실행하지 않은 수정 전 실패를 재현했다고 기록하지 않았다. 모델 출력이나 성공 기준을 고친 것이 아니다.

실제 로그와 파일 hash, 보존한 합성 사례 결과는 `VALIDATION_RESULT.json`을 기준으로 한다. 이전 measure.py·원 v066 ZIP·복원한 동결 prior source ZIP은 변경하지 않았다.

## 8. 실행과 한계

사용자 GPU에 새로운 v067 추론을 이 환경에서 실행한 것은 아니다. Linux·Python3.13.5에서 오프라인/합성 검증을 했으며 Windows PowerShell 실기 실행은 하지 않았다. PowerShell 내장 소스 ZIP과 최종25개 소스 파일 hash는 검증했다. 원시 subprocess 출력은 바이트로 저장하고 표시용 UTF-8 처리를 분리했다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Run-v067-Auto.ps1"
```

이 파일 하나에 소스가 들어 있다. 기준선은 이번 v066 evidence이며 기존 저장소/버전 결과/Downloads에서 정확한 hash로 찾는다. 별도 v067 폴더만 설치하고 이전 결과는 보존한다. `-CheckOnly`로 실제 추론 없이 자체시험·원자료 감사·계획 생성까지만 할 수 있다.

완료 결과는 `llm_experiments/v067/results_llm/v067_reference_<실행시각>_evidence.zip`과 `_independent.json`이다. 소스ZIP의 README에 수동 명령과 오프라인 v066 재분석 명령도 있다.

검산 보증은 고정 계획과 동봉 원문·소스의 내부 일관성이다. 동일 OS 권한에서 모든 소스/기록을 함께 조작한 상황이나 물리적 모델 수신을 외부 전자서명으로 인증하지 않는다. 두 의미 계산기는 바이트/JSON 경계·명세·이전 고정 감사기를 공유하므로 공통 명세 오류 가능성은 독립 코드와 별개의 한계다.
