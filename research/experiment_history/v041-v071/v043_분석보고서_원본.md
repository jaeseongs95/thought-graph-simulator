# v043 판정 실험: 근거 조건 무시와 실패 원인 교차검토

## 결론

신규 8건의 상태는 원문·원본 평가기에서 5건 성공, 3건 실패로 재현된다.
핵심은 staged 3/4가 요구된 식 수행의 충분한 증거가 아니라는 것이다. 네 응답은 모두 `(a,a,false)`와 일치한다.
초기 사실 소속 여부 b가 달라져도, 목표 동일성 a가 같으면 staged의 실제 응답은 변하지 않았다.
이는 **이번 네 출력의 의존 관계**를 정확히 기술한 것이며 모델 내부에 그 코드가 들어 있다는 추정이 아니다.

출력 순서가 달라진 json 군에서도 같은 핵심 오류가 남고, 실제 호출 경계를 둔 staged 군에서도 남는다.
따라서 순서 변경이나 두 호출로 나누는 것만으로 해결된다는 설명은 이번 실험의 반례와 충돌한다.
코어의 채점 오류는 발견되지 않았다. local_llm의 총 성공 수도 맞았다.
새 단계형 과제가 원문 상세진단 분기에서는 빠져 있던 연결 누락을 보완하고,
군별 필요조건·반례·b 민감도를 제시하는 v0.4.4를 작성했다.

## 정확한 기준

`a = probe.atom == problem.goal`
`b = probe.atom in problem.facts`

요구되는 최종값은 순서대로 `answer_only_accepts=a`, `proof_and_goal_accepts=a AND b`, `gap_detected=a AND NOT b`다.
현재 probe는 `rule:null, parents:[]`인 단독 사실 주장이다. 새 증명을 만들라는 과제가 아니다.
따라서 전체 문제에서 목표에 도달할 수 있더라도 초기 사실이 아닌 무근거 주장은 strict 수락 대상이 아니다.

| a | b | 정확한 최종값 | v042 schema | v043 json | v043 staged |
| --- | --- | --- | --- | --- | --- |
| F | F | F,F,F | F,F,F | **F,F,T** | F,F,F |
| F | T | F,F,F | F,F,F | F,F,F | F,F,F |
| T | F | T,F,T | **F,F,F** | **T,T,F** | **T,T,F** |
| T | T | T,T,F | **F,F,F** | T,T,F | T,T,F |

schema와 json은 각 2/4이다. json은 TT 한 건을 고치면서 FF 한 건을 새로 틀렸다.
staged는 3/4지만 정확한 식 대신 b를 무시한 단순식 `(a,a,false)`도 같은 점수를 얻는다.
실제 `goal_is_fact__staged`와 `goal_not_fact__staged`는 응답 본문이 바이트 단위로 같다.
[군별 지표](comparison.json).

## 직접 원인과 상위 원인의 구분

### 직접 원인: strict의 필요조건 b를 반영하지 않은 최종 출력

`a=T,b=F`에서 모델은 `proof_and_goal_accepts=true`라고 답했다. 원래 계약은 false다.
동시에 `gap_detected=false`라고 답했으나 정답은 true다.
원문 복사본에서 이 두 비트를 모두 수정하면 통과하고, 한 비트만 수정하면 실패한다.
json의 FF 조건은 gap 하나만 수정하면 통과한다.
총 10개 합성 변경을 실행했다. 수정한 응답은 연구 성공률에 포함하지 않았다.
[변경 대조](counterfactuals.json).

### 전체 출력끼리 일관돼 보여도 원문 의존성을 지킬 필요가 있다

TF에서 나온 T,T,F는 최종 필드끼리만 보면 `gap = answer AND NOT strict`를 만족한다.
그런데 strict는 원래 입력의 b를 위반한다. 즉 자기 일관성만으로는 이 오류를 걸러낼 수 없다.
원문/이전 출력의 b와 최종 strict를 연결하는 검사가 필요하다.
v044의 `strict_accept_without_initial_fact`와 `critical_b_pair`가 이 연결을 명시한다.
기존 core는 이미 원문 입력과 비교해 거부했다. 새 검사는 그 이유를 보고서에 드러내는 추가 증거다.

### 아직 분리되지 않은 상위 원인

분기/필드 이름의 의미에 끌린 출력, 입력의 위치 효과, 특정 문맥의 논리식 적용 실패,
제약 디코딩, 샘플링·캐시·수치 경로, 양자화·체크포인트의 영향은 현재 원문만으로 하나로 구별되지 않는다.
오류가 정확히 어느 값에 있는지 밝혔다는 사실과, 그 값이 생성된 내부 메커니즘을 밝혔다는 것은 다르다.

## 앞선 해석을 이번 결과로 갱신

### 입력을 잘못 읽었다는 설명

json 네 건의 observed와 primitives는 모두 맞다. staged 입력은 원래 모델이 반환한 정확한 두 객체를 그대로 사용한다.
이번 TF 실패를 문자열 동일성이나 소속 여부를 계산하지 못한 것으로 설명할 수 없다.
단, 올바르게 출력한 중간값이 내부에서 최종값을 생성하는 데 실제 쓰였다고 역추론할 수는 없다.

### 정렬 때문에 실패했다는 설명

json 네 건은 `observed → primitives → finding` 순서로 반환됐다. 그런데 두 건은 여전히 틀렸다.
staged는 이전 응답을 새 호출의 user 메시지에 넣었으므로 중간값이 후속 호출 전에 존재한다.
그런데 TF 오류는 계속됐다. 따라서 의도한 순서 복원이나 호출 경계 추가는 충분조건이 아니다.
순서가 전혀 영향을 주지 않는다는 결론도 아니다. 출력의 순서와 내용은 함께 바뀌었으며 단독 효과는 분리하지 못했다.

### 규칙을 따라 도출할 수 있으니 사실처럼 취급했다는 설명

staged 요청에는 원래 rules가 없다. a,b와 observed만 제공된다. 그 상태에서도 같은 TF 오류가 난다.
이전 full 문제의 규칙을 읽어 새 증명을 구성해야만 이 오류가 나온다는 설명은 필요하지 않다.
핵심 증거는 출력식에서 b가 반영되지 않았다는 것이다.

### schema가 true/false를 강제했다는 설명

기존/신규 schema는 세 필드를 boolean으로만 지정한다. 정답 const/enum이 없다.
32개 진리표 대조와 신규 군 128개 출력 조합 검사에서 모든 형식상 가능한 부울값을 입력할 수 있었다.
형식 제약이 생성 분포에 영향을 줄 가능성과, 특정 정답값을 금지했다는 주장을 구분한다.

## core 교차검증

별도로 명시한 네 행 진리표를 정답 기준으로 두고, 4입력 × 8출력 = 32개를 원래 local 평가기와 core에서 비교했다. 전부 일치했다.
core 시험에서는 유효한 기본 증명에 criterion probe만 교체하여 다른 실패가 판정을 가리지 않도록 했다.
실제 응답의 finding 키 순서를 바꾼 48개 순열에서도 판정이 유지됐다.
따라서 검증기 객체 순서 때문에 참값을 거짓으로 읽은 문제가 아니다.

[32개 진리표 대조](truth_table.json), [48개 순열](key_permutations.json).

유한 검사로 core 전체 무결성을 주장하지 않는다. 이번 세 실패의 거부를 뒤집을 근거가 없다는 판단이다.

## 모델·런타임 검사

기록된 모델은 qwen3:4b-instruct / Instruct-2507 / Q4_K_M이다.
요청의 think는 생략됐다. temperature=0.7, top_p=0.8, top_k=20, min_p=0은 Qwen 공식 권장값과 맞다.
공식 Ollama 태그 페이지의 `0edcdef34593` 접두부와 4.02B/Q4_K_M도 기록과 일치한다.
[실행 기록](runtime.json), [외부 자료와 한계](external_sources.json).

신규 8건은 모두 done=true, stop 종료다. 최대 95토큰, 생성 토큰 합계 468, 기록된 API wall 합계 약 9.27초다.
출력 한도 4096에서 잘린 기록, OOM, API 실패는 없다. /api/ps의 size_vram과 size는 둘 다 3,742,808,145바이트였다.
이로부터 이번 실패를 출력 소진·적재 실패로 설명할 증거는 없다고 판단한다. 전체 VRAM 여유나 GPU 수치 정확성을 검증했다는 뜻은 아니다.

서버는 기록상 0.34.0이다. v042와 동일한 템플릿/메타데이터가 유지됐음을 대조했다. 보존된 Jinja 템플릿을 신규 8개 단일턴 입력으로 렌더한 결과도 명시적인 메시지 포맷과 일치했다. 이는 서버 내부에서 실행된 토큰열을 관측한 것이 아니다. [템플릿 대조](template_check.json).
공개 정확한 v0.34.0 소스 경로는 이번 웹 조회에서 가져오지 못했으므로 특정 upstream 함수에 책임을 돌리지 않는다.
캐시 사용량이 기록됐다는 사실은 캐시 오염의 증거가 아니다. 응답이 같다는 것 역시 캐시 오류의 독립 증거가 아니다.

실제 가중치 파일은 이 컨테이너에 없으므로 읽지 않았다.
이를 사용자가 네트워크/추론 없이 검사할 수 있도록 기록된 FROM blob의 바이트를 SHA-256으로 대조하는 코드를 추가했다.
기대 blob 해시 `85e4a5...`는 모델 manifest digest `0edcdef...`와 다른 값이다.
체크섬 일치는 손상 가능성을 좁히지만 공식 모델 인증이나 양자화의 무손실성을 증명하지 않는다.

## 심사 관점별 주장·반박·채택 기준

아래는 한 분석자가 서로 다른 심사 기준을 적용한 교차검토다. 독립 외부 에이전트를 호출했다고 주장하지 않는다.
프로그램 교차검증은 원문 재현, 고정 진리표, 값 변경 반례와 요청 차분 검사로 수행했다.

### 관점 1 — 형식 검증 심사

가설: core가 실현 가능한 결과를 과도하게 거부한다.
반박: TF의 strict=true는 명세 자체의 반례다. 32조합 대조도 기존 core와 일치한다.
판단: core와 기존 FAIL 유지. 실패값 위치를 별도 제시한다.

### 관점 2 — 모델 행동 심사

가설: 입력 이해 자체가 실패한다.
반박: json 입력 사본·기본 판정은 전부 정확하다. staged에서는 정확한 기본값을 입력으로 제공한다.
판단: 현재 실패는 입력과 최종 출력의 필요조건 연결에서 관측된다. staged 네 행은 b 없는 단순식과 일치한다.

### 관점 3 — 런타임·추론 엔진 심사

가설: JSON 스키마 정렬이나 메모리 부족이 원인이다.
반박: json에서 요청 순서가 복원돼도 TF 오류가 남는다. 정상 stop과 짧은 출력, 적재 정보도 메모리 원인을 지지하지 않는다.
판단: 모드·잘림 원인은 현재 지지되지 않는다. 디코딩/수치 원인을 완전 배제하지는 않는다. 실제 파일 바이트 확인과 staged json 대조가 적절하다.

### 관점 4 — 실험 설계 심사

가설: staged 3/4가 원래 2/4보다 높으므로 단계화가 근본 해법이다.
반박: b를 무시해도 3/4다. 가장 중요한 두 기준의 차이를 드러내는 TF 행은 계속 틀린다.
판단: 총점보다 반례 행을 우선한다. 같은 요청 재실행을 동시 대조로 넣고, 순서·형식·출력 이름을 한 요인씩 바꾼다.

### 토론 결론

검증 완화, 더 큰 모델로 즉시 교체, 순서만 더 강조, 성공률이 가장 높은 군을 승자로 정하는 의견은 채택하지 않는다.
반례를 설명하고 실제 수행한 범위를 넘지 않는 결론은 다음이다.

1. 출력 차원에서 b 필요조건의 소실은 확정할 수 있다.
2. 그 소실을 유발한 내부/런타임 단일 원인은 아직 분리되지 않았다.
3. 점수는 유지하고 상세진단을 연결한다. 기존 단계형 호출을 기준으로 요청이 정확히 하나씩 달라지는 비교를 한다.
4. 모델 파일 자체 손상은 추론과 별도로 로컬에서 검사한다.

의견 수가 아니라 반례와 원문 요청으로 판단했다.

## 제공 소스와 원인별 대응

### 확인한 상세진단 연결 누락

v043 task_diagnostics의 분기는 proof/schema/criterion/criterion_witness까지였다.
새 decision_stage에는 JSON 형식 진단만 남고 source와 finding의 관계를 보여 주는 task_evidence 항목이 없었다.
기존 audit.details, 총 성공 수, generic criterion 패턴 집계는 정상이다. 전체 집계가 누락됐다고 확대하지 않는다.
v044는 원문 상세진단과 군별 진리표를 연결했다.

### 새 대조

- replay: 이전 staged 요청 바이트를 그대로 재실행. 이번 시점의 반복 결과와 비교.
- json: staged의 format만 변경. 기존 디자인에서 빠진 staged × JSON 조건을 확보.
- b_last: 입력 두 키의 순서만 변경. 같은 명제/값을 유지.
- neutral_keys: 최종 필드 이름만 r0/r1/r2로 교체. 식과 입력을 유지. 이름 변경에 따른 토큰화/직렬화 변화까지 순수한 의미 효과로 분리한 실험은 아님.
- temperature_zero: 명시 요청할 때만 별도 군으로 사용.

기본 16회이며, 69조건을 다시 실행하지 않는다. 16회도 같은 과제 16개가 아니라 4입력 × 4군이다.
샘플링 불확실성 때문에 작은 성공 차이를 바로 효과 크기나 일반 성공률로 해석하지 않는다.
전용 checker가 각 군의 허용 변경 외 다른 요청 차이를 거부한다.
반환 값은 수정하지 않으며 이름 치환은 일대일 수송 매핑만 복원한다.
이 설계가 반드시 모든 실패를 해결한다고 약속하지 않는다. 실제 개선은 새 응답으로 판정한다.

## 완료한 작업과 미실행 범위

완료: 16개 원문 재현, 실제 응답·요청 대조, 32개 진리표·48개 순열·10개 반례 변경,
기존 204개 시험 재실행, 새 31개 시험 작성과 수행, 패키지 검사.
새 군의 128개 출력 조합 검사와 16회 모의 API 실행/재개 검사를 포함한다.

미실행: 새 LLM 추론, Windows 실행, GPU 실행, 실제 사용자 가중치 blob 읽기.
모의 응답을 실제 모델 개선 결과로 세지 않는다.
