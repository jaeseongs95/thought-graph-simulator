# v067 원문 재검산과 v068 후속 설계

## 결론

**v067의 참조 재구성 성공은 4/12이며, 모든 실패를 생성 능력 부재로 묶는 해석은 맞지 않는다.** 두 문제의 짧은 참조에서는 전체 증명이 성공했다. 실패 8개 중 3개는 노드 배열의 관계와 참조 규칙 순서가 맞았지만 `final_node_id`가 존재하지 않는 노드를 가리켰다. 다른 5개는 부모 연결, 참조 경로 이행, 불필요 노드 등 추가 결함이 있어 같은 원인으로 묶지 않는다.

이 결과에 맞춰 **v068: 전체 graph 직접 출력 vs nodes 먼저 생성 → 모델이 final_node_id 지정**의 한 번짜리 대조를 설계·구현했다. v067의 실패를 수선하거나 재채점하는 소스가 아니다. 실제 v068 Qwen 추론은 아직 실행하지 않았다.

## 1. 분석 자료와 실제로 수행한 확인

기준 자료는 사용자가 올린 다음 두 파일이다.

- `v067_reference_20260913_192953_571655_evidence(1).zip`
- `v067_reference_20260913_192953_571655_independent(1).json`

입력 ZIP SHA-256:

```text
68ab53158bdbcdbd1f079be1b1400950cd881d12191a0a8ac307d582444b205f
```

동결 계획 SHA-256:

```text
1d88337db00c2ede3fc26e72a359e62867e43f2ea17fed1b04d77afcf7327710
```

177개 ZIP 항목을 확인했고 wire 원응답 12개를 전부 읽었다. 첨부 independent의 PASS만 인용한 것이 아니라 다음을 수행했다.

1. manifest의 전 파일 해시와 첨부 ZIP 해시를 대조했다.
2. evidence/source의 소스로 결정적 배포 ZIP을 재구성했고 인계 문서에 기록된 v067 원 배포 SHA-256 `39844126a460298af87ca9b447f1110fee710aa36c65f3a443d2a3ad874f7b63`와 정확히 일치했다.
3. 그 v067 검산기를 실제로 다시 실행했다. live/complete, 시작 및 완료 action 24, inference/observed 12, differences=[]였다.
4. 생산 report.summarize를 원 records에서 다시 계산했고 summary.json의 모든 값 및 한국어 보고서 바이트가 일치했다.
5. 생산 모듈을 import하지 않는 별도 `review_v067.py`로 원응답의 노드·규칙·전제·조상·위상 순서·최종 참조와 성공을 재계산했다. 12개 판정 차이는 0개다.

각 결과는 `v067_reverified.json`, `PRODUCTION_RECALCULATION.json`, `RAW_RECALCULATION.json`, `v067_cells.csv`, `RAW_RESPONSES.ko.md`에 보존했다. 이들은 **같은 실행 증거의 재검산**이지 새로운 독립 모델 실험 12회를 추가한 것이 아니다. 번들 내부 일관성 확인은 외부 실행 사실에 대한 전자서명 인증과도 구분한다.

전체 12개 중 기본 proof_valid는 6개, strict_valid와 reference reconstruction success는 각각 4개다. 규칙 순서만 일치하는 응답은 8개이지만 이것을 전체 성공으로 세지 않는다. 전체 proof가 실패한 6개와 기본 논리는 맞지만 strict 계약만 실패한 2개를 구분한다.

단순 노드 관계의 국소 유효성은 9/12로 관찰됐다. 그러나 최종 노드를 못 찾거나, 최종 경로에서 쓰이지 않는 노드가 남으면 전체 증명은 실패다. **국소 유효 9/12를 전체 증명 9/12로 승격하지 않는다.**

## 3. 원문 예시와 오류 위치

### T02 긴 참조: 두 seed 모두 최종 ID만 잘못 연결됨

원문 파일:

```text
wire/b00_p0_reference_long/response.raw.json
wire/b01_p0_reference_long/response.raw.json
```

두 원응답은 `r21 → r57 → r04 → r69`를 올바른 전제·부모 관계로 작성했다. 목표 `Lg` 노드의 실제 id는 `r69`다. 하지만 최상위 필드는 `"final_node_id":"r83"`이고 nodes에는 r83이 없다. 원 채점과 재계산 모두 `missing_final_node` 하나로 실패한다.

이는 '긴 경로의 노드 관계도 작성하지 못했다'와 다르다. 다만 호스트가 final을 r69로 바꾸어 성공으로 세지 않았다. 이 원응답에서 실제 D의 공식 측정값은 계속 null이다.

### E01 긴 참조: 최종 ID 하나를 고쳐서 해결할 사례가 아님

```text
wire/b02_p1_reference_long/response.raw.json
wire/b03_p1_reference_long/response.raw.json
```

n08로 Ax, n91로 Ay는 만들었지만 최종 목표는 n52로 도출했다. 주어진 긴 경로의 n37 노드가 아예 없다. 만든 Ax/Ay는 선택된 goal 노드의 조상이 아니다. 기본 rule 적용은 맞지만 strict 조건과 참조 순서를 모두 위반했다.

### E02 짧은 참조: 두 seed의 오류를 구분해야 함

```text
wire/b04_p2_reference_short/response.raw.json
wire/b05_p2_reference_short/response.raw.json
```

seed 64001001: 노드 ID는 m18, fact_pc인데 마지막 노드의 parents에는 Ps, Pc가 들어갔다. 이 경우 final_node_id=m76은 실제 존재하지만 부모 ID가 틀렸다.

seed 64001002: nodes의 목표 ID는 m76_result이고 부모 연결은 맞다. final_node_id에는 m76이 들어가 존재하지 않는 최종 ID가 됐다. 이 후자의 실패만 T02 긴 참조 두 개와 함께 '최종 ID 참조만 고립되어 틀린 세 사례'에 속한다.

### E02 긴 참조: 여러 결함이 함께 존재

```text
wire/b04_p2_reference_long/response.raw.json
wire/b05_p2_reference_long/response.raw.json
```

두 응답 모두 제공한 경로에 없는 m18이 끼어 있고 final_node_id=m76은 실제 배열에 없다. m41의 부모도 Pw라는 원자 이름을 사용해 실제 부모 노드 ID m84를 참조하지 않는다. 첫 seed에서는 fact2/fact3를 부모로 쓰면서 그 초기 사실 노드들을 출력하지 않았다. 단일 final ID 지정 실패로만 설명할 수 없다.

## 4. 관찰·설명 후보·구별하는 증거·현재 결론

**관찰:** 12개 응답 모두 JSON 최상위에서 final_node_id가 nodes보다 먼저 출력됐다. 12개 모두 그 값은 입력 rules에서 첫 번째 goal 도출 규칙의 ID와 같다. 긴 참조 노드를 만들면서도 이 최종 값은 다른 경로의 규칙 ID로 남는 경우가 있다.

**설명 후보:** 노드 배열을 생성하는 작업과 최종 참조를 일관되게 연결하는 작업의 결합이 불안정할 수 있다. 또는 최종 참조 외에도 경로 이행·부모 참조 작성에 별도의 문제가 있을 수 있다. 원문은 두 종류의 실패가 함께 있음을 보여 준다.

**현재 구별되지 않는 것:** final 필드가 먼저 출력되어 실패한 것인지, 규칙 순서 선호·출력 제약·반복 참조 작성 등 다른 과정 때문에 그런 것인지 원문만으로 확인하지 못했다. 출력 문자열의 순서를 모델의 내부 생각 순서로 바꾸어 설명하지 않는다.

**결론:** 전체 생성기를 불가능하다고 정리하기보다는, 노드 배열을 먼저 만들고 모델이 그 배열의 최종 ID를 나중에 지정하는 계약을 한 번 비교할 근거가 있다. 나머지 결함도 남아 있으므로 final 분리가 전부 해결하리라고 예측하지 않는다. 이 비교가 실패하면 같은 진단을 문구만 바꾸어 반복하지 않는다.

## 5. v068 설계

같은 세 문제, 같은 두 seed, 같은 짧고 긴 정답 참조를 사용한 12개 짝에서 다음을 비교한다.

|구조|실행|모델 호출 수|
|---|---|---:|
|direct|v067과 동일한 요청으로 nodes와 final_node_id를 한 번에 출력|12|
|staged|첫 모델이 nodes만 출력 → 그 원응답을 전달 → 둘째 모델이 final_node_id만 출력|24|

총 36회다. 모든 problem/reference cell에서 두 seed 사이에 direct/staged의 선후가 반전된다. 짧고 긴 참조의 선후도 반전된다. 원문 전달은 노드 payload를 고쳐 재작성하는 것이 아니라 원래 message.content 문자열과 SHA-256을 전달하는 방식이다.

호스트는 첫 응답의 nodes와 둘째 응답의 final_node_id를 그대로 결합한다. 정답 노드를 추출해 후보로 주지 않으며, 사후 가지치기·부모 수정·없는 ID 추측도 하지 않는다. 앞 단계가 틀렸다면 마지막 ID가 맞아도 전체 성공이 아니다.

비교 대상은 '출력 계약+호출 분리'다. staged는 더 많은 호출과 설정상 생성 예산을 사용하므로 공정한 동일 예산 비교나 내부 원인 한 개를 고립시키는 실험이 아니다. 다만 구성요소로 사용할 생성기가 확보되는지 판단하는 데 직접 도움이 된다. 같은 배치의 direct를 둬 과거 결과 4/12와 현재 결과를 단순 인과 비교하지 않는다.

## 6. 판정과 분기 종료

각 arm의 12개 종단 증명이 전부 측정되어 12/12이면 그 arm에 한정된 정상 참조 입력 생성기 기준선이다. direct만, staged만, 양쪽 모두 기준선을 충족하는 경우를 분리한다.

일부 성공은 문제·참조·seed 범위를 보존한다. staged 0/12이면 그 두 호출 계약을 종료한다. 어느 경우든 이번 제한 진단은 이 배치에서 종료하며 문구·seed·모델을 바꾸어 자동으로 반복하지 않는다. 미완료·미측정은 전체 gate null로 남는다.

기준선이 확보돼도 자율 D 제어는 아니다. 다음 단계가 필요하다면 별도 사전 설계 아래 D 요구에서 모델이 경로를 선택하고 그 원값을 검증된 생성 계약에 넘기는 실험이어야 한다. 이번 코드는 다음 분기를 자동 실행하지 않는다.

## 7. 실제 구현·검증 범위

원문에 대한 과거 채점 기준은 바꾸지 않았다. 새 v068의 `measure.py`는 v067과 바이트 동일하다. `verify.py`는 생산 측정·요청·보고서·단계 결합 모듈을 import하지 않고 원증거에서 다시 계산한다. 고정 문제/계약과 바이트 도구는 공유하므로 완전히 다른 실험자나 물리적으로 독립한 모델 실행이라는 뜻이 아니다.

단위·반례 시험, 합성 HTTP 왕복, 원응답 전달, report 재계산, 재해시한 증거 변조, 중단·미실행·요청 전 pending·응답 후 pending, 실제 Python 하위프로세스 자동화 및 배포 ZIP 재추출 검증을 구분해 실행한다. 최종 시험 결과와 실제 제외 항목은 함께 전달한 `VALIDATION_RESULT.json`과 원문 로그가 기준이다.

**실제 v068 Qwen 추론과 Windows PowerShell 네이티브 실행은 이 환경에서 수행하지 않았다.** 합성 시험의 성공률은 Qwen의 예상 성공률이 아니다. 전달 소스는 사용자의 기존 로컬 모델에 대해 위 36회 배치를 실행하도록 준비한 것이다.

## 8. 최종 배포 검증 결과

배포한 소스 ZIP을 새 빈 폴더에 다시 추출한 바이트로 전체 시험을 실행했다. **총 65개 중 64개 통과, 실패 0개, 오류 0개, Windows PowerShell 네이티브 경계 시험 1개 제외**다. 제외 사유는 Linux 실행 환경이며 Windows 실기 통과로 표현하지 않는다.

생산 채점기와 별도 구현의 증명 반례 대조는 180개 변형을 포함한다. 실제 원 v067 ZIP에 대한 재해시 변조 6개(거짓 성공, final 수선 후 원 보고서와 불일치, 요청 seed 변경, 한국어 보고서 변경, 실행 건수 변경, 측정 소스 변경)도 모두 거부됐다. 새 v068 합성 시험은 설치·실제 Python 하위프로세스·loopback HTTP·증거 ZIP·독립 JSON 생성까지 포함했다.

PowerShell 자동화 내부에서 소스 ZIP을 다시 꺼내 배포 ZIP과 바이트 동일함 및 RELEASE_MANIFEST 해시 일치를 확인했다. 이것은 PowerShell을 실제 Windows에서 실행한 시험과는 별개다.

배포 소스 ZIP SHA-256:

```text
ee9734f552fc6405f3015922cc250f338bc9054447c57f09e22f4e21c6049d20
```

`Run-v068-Auto.ps1` SHA-256:

```text
57c70075a3134e868d29f1d1f464b3e6156ddfd33f0dc7a7a606de0bc02e6572
```

전체 결과는 `v068_validation/VALIDATION_RESULT.json` 및 원문 시험 로그에 있다. 이 시험들은 새 소스의 계약 이행과 오류 검출을 확인한 것이며 실제 Qwen의 v068 성공률을 측정한 것이 아니다.
