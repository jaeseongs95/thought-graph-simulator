# v065 결과 분석과 v066 직접/단계형 비교 결정

## 1. 결론

실제 v065는 12/12 호출 완료, 지정 규칙 구성 성공0/12다. 정상 출력 형식12개, 기본 증명 유효6개, strict 유효 증명1개, 최종 참조가 가리킨 규칙의 지정 ID 일치4개다. 유일한 strict 증명은 **짧은 r83을 요구했을 때 나온 깊이4/r69의 긴 증명**이었다. 따라서 이 관측을 긴 증명 생성 능력이 전혀 없다는 주장으로 바꾸지 않는다. 동시에 요구한 경로로 제어했다는 성공도 아니다.

사전 기준대로 **마지막 규칙을 알려주는 단일 호출 구성 분기는 종료**한다. 문구 강조/오타 보정/생성 노드 삭제를 추가하지 않는다. 다음 소스는 정답 규칙을 외부에서 지정하지 않는 **직접 D 생성 대 모델의 전체 규칙 경로 계획→그 원응답을 받은 증명 작성** 비교다. 다른 실행 인터페이스를 36회의 한 묶음에서 시험하며, 이전 실패는 보존한다.

## 4. 사전 종료와 다음 선택

v065의 사전 규정은 깊은 지정 경로의 strict 구성이 하나도 성공하지 않으면 현재 단일 호출·출력 인터페이스의 지정 구성 분기를 종료하는 것이다. 실제 prescribed_long 성공은0/6이다. 이를 그대로 따르고 같은 문구 변형을 재실행하지 않는다.

연구 전체의 종료는 아니다. 다음 시스템 대조를 택한 근거는 (1) 유효한 깊은 증명 자체는 한 응답에서 관측됐다는 점, (2) 직접 생성에서 선택·최종 참조·부모 연결을 한 번에 요구할 때 요구 이행이 실패한다는 점, (3) 실제 모델 원값을 다음 단계에 보존 전달하는 실행 구조는 원래 연구가 허용한 별도 비교라는 점이다.

|검토 관점|반론|처분|
|---|---|---|
|사전 규정|실패했는데 또 같은 검사를 늘리는가?|지정 규칙 단일 호출 분기를 종료한다. 다음은 호스트가 규칙을 주지 않는 직접/2단계 구조 비교다.|
|측정|계획 목록이 맞으면 완전한 D 제어인가?|계획은 별도 진단이다. 실제 graph strict·actual_D와 원계획 준수가 모두 있어야 종단 성공이다.|
|인과|단계형이 좋아지면 분해 자체가 원인인가?|추가 호출·문맥·출력 계약이 함께 바뀐다. 시스템 묶음의 차이만 보고하며 동등 계산량·내부 학습 원인으로 확대하지 않는다.|
|공정성|호스트가 정답 계획으로 고쳐주나?|원 content 문자열을 그대로 전달한다. 잘못된 중간값, 공백, 깨진 JSON까지 수정하지 않는다.|
|비용|실험이 다시 무한히 커지나?|36회 한 묶음, direct12/staged24. 결과 후 자동 호출·모델변경·새 이름 반복은 없다.|
|연구 복귀|또 규칙 ID 자체의 진단만 하는가?|최종 결과는 실제 유효 증명의 shallow/deep 대응이다. ID 목록은 중간단계이며 주 성공을 대신하지 않는다.|

이 검토는 다른 외부 심사자나 에이전트를 호출한 것이 아니다. 같은 자료에 대해 상충하는 제3자 관점을 대조하고 구현상 독립 계산과 반례로 검증했다.

## 5. v066이 하는 일

같은3문제×2seed×2방향=12조건에 대해 다음을 실행한다.

- direct: 기존 D 지시로 전체 증명 한 번 생성. 총12호출.
- staged: D 지시로 모델이 규칙 목록을 계획하고, 실제 원응답을 다음 모델 호출에 전달해 전체 증명을 작성. 총24호출.

총36호출이며 모델/문제/목표/규칙순서/seed/options를 유지한다. 기존 직접 D 요청12개를 v064 실제 요청과 바이트 단위로 대조해 모두 일치했다. 나머지24개에서도 원래 문제·모델옵션은 같았다. 생성설정 상한147,456토큰은36×4096이며 실제 사용량 또는 입력 토큰 보장이 아니다. direct와 staged의 계산 기회는 다르다.

첫 단계 응답은 `{"rule_ids":[...]}` 형태지만 정답 ID enum/정답 경로/정답 깊이는 주지 않는다. 두 번째 단계는 첫 모델의 message.content를 받은 그대로 사용한다. 원 envelope는 별도 raw 파일로 보존하고 전달 필드의 SHA와 결속한다. 호스트는 content를 규칙 목록으로 파싱·수정한 뒤 보내지 않는다. 내용 자체가 없으면 null이며 정답 계획을 만들어 넣지 않는다.

planner의 계획 유효성·planned_D는 실행 뒤에 계산한다. 실제 증명은 바이트가 보존된 기존 measure.py로 검사한다. generated actual_D는 strict 유효 증명에만 부여한다.

**staged 종단 성공 조건:** 계획이 유효하고 방향에 맞음 + 원content 전달 + 그래프가 원계획 규칙 순서와 일치 + graph strict 유효 + actual_D가 방향에 맞음. 잘못된 계획 뒤 최종 정답이 우연히 생성되면 최종 국소 성과는 남기되 종단 성공은 false다. 파싱/미관측은 진위 미측정과 구별하고 gate는 null로 둔다.

같은 문제·seed의 두 방향을 모두 이행해야 방식별 대응쌍 성공이다. direct6쌍, staged6쌍이다. 중립은 이번 시스템 대비에서 추가 실행하지 않으며 과거 v064 원자료를 그대로 보존한다.

## 6. 결과별 다음 결정

- staged6/6쌍: 제한된 외부 실행 구조의 D 기준선을 확보한 것이다. 이전 단일 호출 실패는 그대로다. 다음은 설계에 사용하지 않은 문제·구조에서 재현 및 A/M 복귀 설계를 별도 검토한다.
- 일부 성공: 해당 문제·방향·구성의 성공과 실패를 모두 보존한다. 성공 subset으로 전체를 포장하지 않는다.
- staged 종단 성공0: 이 두 호출 구조도 종료한다. 문구·예제를 계속 바꾸는 자동 연장 금지.
- direct에서도 새로운 성공: 반복 변동을 인정하며 staged만의 개선으로 소유시키지 않는다.
- 미완료/파싱 미측정: 전체 진입 판단 보류. 원문 보존, 자동 재시도 없음.

이 문제들은 이미 응답을 본 개발 구조다. 일반화, 내부 사고 제어, 작은 모델과 큰 모델의 동등 성능, 비용 절감은 아직 이 실험의 성과가 아니다.

## 7. 소스 작성 후 검증

실제 v065 원문 재감사, 108개 의미 필드 별도 재계산, 새 요청36개 내용·옵션 및 직접 요청12개 바이트 대조를 수행했다. 기존 measure.py는 SHA-256 `47e6a93f5e96e8346ccb21c77034a5859ad8fbe9a326e77bff44acd58d610f71`로 바이트 동일하다.

최종 소스 ZIP을 새 폴더로 풀고 시험64개를 실행해63개 통과, Windows 전용1개를 제외했다. 원본 v065의54개도 재실행해53개 통과, 같은 Windows전용1개 제외였다. 초기 긴 시험 명령은 도구 제한으로 끝까지 완료되지 않아 그 실행을 통과 기록으로 세지 않았다. 최종 동결본 실행의 종료코드는0이며 해당 로그를 보존했다.

잘못된 계획을 전달하고도 생성 모델이 정답을 출력하는 반례에서 최종 D 성공12/12와 종단 성공0/12를 구분했다. 단계별 성공을 지우지 않는지, 같은 경로를 반복하면0/6인지, direct만/staged만 성공을 공정하게 검출하는지, 원content 재작성·summary 한국어·JSON 재해시 변조를 거부하는지 검사했다.

완료8종×36회, 중단1회/3회의 별도 합성 원문292호출을 보존했다. 이 숫자는 그10가지 사례만이며 fixture 준비나 자체시험의 호출을 합산하지 않았다. 동일한 큰 기준선을10번 복제하지 않도록 content-addressed 묶음으로 보존했다. 각 case의 원 ZIP을 복원해 hash가 같음을 확인했고 독립 검산 receipt도 보존했다. 합성 성과는 실제 모델의 연구 성과가 아니다.

새 소스의 핵심 필드와 이전 파일명을 대조하면서 외부 입력명을 바로잡았다. 수정 전 실행하지 않은 오류를 실행 재현했다고 주장하지 않는다. 주 채점 기준을 완화하는 수정은 없다.

## 8. 자동화와 실제 실행 경계

`Run-v066-Auto.ps1`은 내장 소스 ZIP을 검사하고 기존 저장소의 별도 v066 폴더에 설치한다. 실제 파일 바이트가 같을 때만 재사용하고 다르면 백업한다. 원 v065 evidence 해시가 같은 파일을 찾는다. 자체시험→무추론 기준선 감사/계획→기존 Qwen identity→36회→감사/ZIP/독립 검산까지 연결된다.

실제 사용자 Qwen의 새36회 추론은 이 환경에서 수행하지 않았다. Python 자동화의 별도 하위 프로세스는 합성 서버로 end-to-end 실행했다. Windows PowerShell은 이 Linux환경에서 직접 실행하지 않았고 내장ZIP·해시·실행 경계 검사와 구분한다. 모델 다운로드·갱신·서버 시작은 하지 않는다. Ollama는 사용자가 기존처럼 켜 두어야 한다.
