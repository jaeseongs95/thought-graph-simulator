# v069 실제 증거 재검산 및 v070 의사결정

## 1. 결론

**v069는 사전 지정한 12조건에서 12/12 성공했다.** 실험자가 정상 참조 경로와 현재 적용할 규칙을 제공하는 append-only 계약에서, Qwen이 사실·규칙 노드·부모 ID·최종 ID를 직접 작성해 전체 증명을 완성하는 기준선이 확보됐다.

이 판단은 첨부 independent JSON의 PASS만 인용한 것이 아니다. evidence의 실제 모델 응답 54개를 읽고, 생산 집계를 재실행하고, 고정 배포본의 독립 검산기를 다시 실행하고, 별도 raw 재계산 코드로 전체 12증명 및 54단계 계약을 대조했다. 세 계산 모두 기존 결과와 차이가 없었다. 기존 응답을 고치거나 실패를 다시 성공으로 바꾸지 않았다.

반면 D 지시만으로 경로를 선택하는 능력은 v069의 측정 대상이 아니다. 따라서 다음 단계는 같은 구성 문구를 바꾸는 반복이 아니라 D 기반 선택이다.

## 2. 입력과 실행 기록

원본 evidence: `v069_append_20260913_204633_329627_evidence.zip`

SHA-256: `346a2096dd24476f0bda8f1244c14cf9a1670843b2dbe7068da6405507432cb4`

계획 SHA-256: `6d247f4a6a6ada3b927a83d9ba2e381458a32a252b855b50d47b924c5db5d35e`

첨부 및 재생성 독립 결과는 provenance=live, state=complete, 시작/완료 action=66/66, 추론 시작/관측=54/54, pending=null, differences=[]다. 모델 추론 54회와 metadata action 12개를 구분한다. metadata action에는 여러 HTTP 조회가 있지만 모델 추론으로 세지 않는다.

무결성/재계산은 번들 내부 일관성과 동결 계약을 확인한 것이다. 외부 PC/GPU 실행 자체를 별도의 제3자 수단으로 인증한 것은 아니다. 기존 PASS를 별도의 새로운 모델 실험이나 독립 표본으로 중복 계산하지 않았다.

## 3. 원응답별 성공 범위

|문제|참조|실제 D|성공|원응답에서 확인한 내용|
|---|---|---:|---:|---|
|T02|short|1|2/2|r83가 Lp/Ls 사실을 직접 사용하고 실제 최종 노드를 가리킴|
|T02|long|4|2/2|r21→r57→r04→r69 의존 연결과 final ID가 모두 맞음|
|E01_shared_fork|short|1|2/2|n52만 적용하며 불필요한 n08/n91 노드가 없음|
|E01_shared_fork|long|2|2/2|n08과 n91이 각각 Aa에서 갈라지고 n37이 Ax/Ay/Ab를 모두 사용|
|E02_two_vs_four|short|2|2/2|m18 결과 Ps와 Pc를 m76에서 결합|
|E02_two_vs_four|long|4|2/2|m33→m05→m84→m41의 모든 전제/부모가 올바름|
|합계|||12/12|strict 증명, 단계 계약, 참조 순서, 실제 D 모두 통과|

전체 증명에 포함된 노드는 58개다. 초기 사실 노드는 28개, 규칙 적용 노드는 30개다. 12번의 final 호출을 포함한 단계 계약은 총 54개다. 중복 ID, 누락 부모, 잘못된 전제, 잘못된 원자, 존재하지 않는 final ID, 사용되지 않는 노드는 발견되지 않았다. 각 증명의 모든 노드가 최종 goal의 지지 ancestry에 들어간다.

E01 long의 규칙 수는 3이지만 D=2다. n08과 n91이 순차 생성됐다는 이유로 논리적 의존 깊이를 3으로 계산하지 않았다.

### E02 long의 실제 예

seed 64001001의 초기 사실 ID는 F01=Pa, F02=Pb, F03=Pc다.

```text
m33: N01=Pu, parents=[F01]
m05: N02=Pv, parents=[N01,F02]
m84: N03=Pw, parents=[N02,F03]
m41: N04=Pg, parents=[N03]
final_node_id=N04
```

v068에서 문제가 된 m05/m84의 부모 연결이 이번 원응답에서는 맞았다. 단계별 원문은 `raw_contents.json`에, 조합한 graph 및 별도 계산은 `raw_recalculation.json`에 보존했다.

## 4. 관찰, 추론, 미확인 원인

**관찰:** 모든 참조 조건에서 모델이 올바른 노드/부모/최종 ID를 작성했다. 앞선 원응답 전체가 내용과 SHA에 맞춰 그대로 다음 요청에 포함됐다. 호스트는 규칙 경로와 현재 규칙을 안내하지만 생성된 값은 보정하지 않았다.

**현재 가능한 추론:** 이 모델·문제·seed·정답 경로/규칙 안내 계약에서는 전체 증명 구성 기준선을 얻었다. 따라서 같은 모델이 해당 구조를 전혀 구성하지 못한다는 설명은 맞지 않는다. 이미 이전에도 긴 증명 성공 반례가 있었으므로 이를 긴 증명의 최초 가능성 증명이라고 표현하지 않는다. 이번에 새로 얻은 것은 사전 배정한 모든 12조건에서의 완전 성공이다.

**구분하지 못한 원인:** 한 번에 처리하는 출력량 감소, 현재 규칙 명시, history 재제공, 호출 수 증가, 출력 스키마 변화 중 어떤 요인이 성공을 만들었는지는 이 배치만으로 분리되지 않는다. v068과 동시 대조하지 않았으므로 8/12→12/12 차이를 append-only 단일 요인의 인과효과 또는 동일 비용 우월성으로 해석하지 않는다.

12건은 두 seed를 포함한 계획된 실행 기록이다. 서로 독립적인 모집단 표본이거나 새로운 문제로 일반화했다는 뜻은 아니다. 동일한 모델/조건의 반복 기록이므로 성공 확률의 일반 추정이나 통계적 유의성 주장을 추가하지 않는다.

## 5. 감사와 변조 시험

1. 원본 bundle manifest/plan/source/runtime/event/request/response/summary 및 한국어 보고서를 동결 소스로 검산했다.
2. 생산 `report.summarize` 재실행이 원래 summary와 일치했다.
3. 생산 모듈을 import하지 않는 `review_raw_v069.py`로 history 원문 결합, 54단계 계약, 12전체 graph의 dependency depth/ancestry를 다시 계산했다. 차이 0이었다.
4. 실제 bundle 복제본에 한국어 보고서, D 성공 주장, final ID, 부모, 추가 fact, 요청 규칙, 원문 history, source, 추론 수, HTTP 중단 경계의 10가지 변조를 가했다. manifest/event/record를 해당 변조에 맞춰 다시 해시해도 모두 거부됐다. 성공률이나 원본은 바꾸지 않았다.

`real_bundle_mutations.json`은 각 거부 지점을 남긴다. 부모/fact 원응답 변조는 후속 history의 원문 결합이 깨지는 지점에서 먼저 거부되기도 한다. 이는 해당 변조가 언제나 의미 채점 단계까지 도달했다는 뜻이 아니다. 원문 graph의 의미는 별도 raw 계산으로도 확인했다.

## 6. 다음 실험 선택

v069의 사전 성공 기준을 충족했으므로 지정 구성 반복 분기를 종료한다. 생성기 기준선을 활용하기 위한 다음 새 질문은 **D 요구를 보고 경로를 선택할 수 있는가**다.

바로 전체 selector→generator 실험으로 확대하면 새로운 선택 실패와 연결 후 생성 실패를 함께 다시 분석해야 하고 호출 수도 늘어난다. v070은 우선 선택 인터페이스만 40회 검사한다. v069를 재실행하지 않으며 generator를 호출하지 않는다. 두 모듈의 개별 성공을 연결 성공이라고 미리 합산하지 않는다.

모델에게 두 정상 후보 규칙 배열을 주되 short/long 이름, 기대 D, 정답 index는 숨긴다. 동일 문제/seed/후보 순서에서 작은 D/큰 D 요구만 바꾼다. 후보 순서는 두 방향 모두 실행한다. 모델 출력은 `rule_ids` 배열 하나이며 보정/재정렬하지 않는다.

기존 세 문제는 규칙 수가 많을수록 D도 크다. 이를 그대로 사용하면 모델이 목록 길이로 답을 골라도 높은 점수를 얻을 수 있다. 그래서 두 진단 대조를 추가했다.

|대조|후보 1|후보 2|구분하려는 설명|
|---|---|---|---|
|C01_equal_count|규칙 3개, D=2|규칙 3개, D=3|같은 규칙 수에서도 깊이를 구분하는가|
|C02_count_reversal|규칙 4개, D=2|규칙 3개, D=3|많은 규칙=깊은 경로라는 규칙을 그대로 쓰는가|

이 두 문제는 직접 만든 진단 대조이지 독립 holdout이 아니다. 새로운 두 문제에서 Qwen의 graph 생성은 아직 측정하지 않았다. v070의 `route_D`는 출력 규칙 목록을 problem 규칙의 의존 관계로 재계산한 값이며, 새로 생성한 graph의 parent ID를 검증한 값과 구분한다.

## 7. v070 사전 분기

5문제×2seed×2후보 순서×2D=40회, 20짝이다. 40/40 및 20/20 짝 성공이면 후보 목록 내 D 선택 기준선으로 보고, 별도 연결 실험을 설계할 근거로 삼는다. 자유 경로 생성, full-graph D 제어, A/M, hidden-layer 조작, 비용 우월성을 입증하지 않는다.

일부/전부 실패면 해당 범위를 보존하고 이번 선택 계약을 종료한다. 미완료/미측정이면 전체 gate=null이다. 결과가 좋아야만 다음 조건을 실행하는 동작, 자동 재시도, 새 seed 반복, 다음 버전 자동 실행은 없다. Windows 자동화에도 한 번 시작한 v070을 새 RunName으로 반복하지 않는 guard를 넣었다.

## 8. 전달 범위

`Run-v070-Auto.ps1`, `v070_depth_selection_source.zip`, 이 분석 보고서, 원문 재계산/변조/새 소스 시험 자료를 함께 제공한다. 실제 Qwen v070 추론은 개발 과정에서 실행하지 않았다. 새 소스의 시험 숫자와 제외 사유는 최종 배포본 기준 `VALIDATION_RESULT.json`을 따른다.
