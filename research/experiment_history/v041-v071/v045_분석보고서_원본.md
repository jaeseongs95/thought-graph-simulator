# v0.4.5 operator 결과 분석 및 v0.4.6 수정 근거

## 결론

이번 16개 응답에서는 COPY(a), AND(a,b), NOT(b)가 각각 4/4로 맞았지만, 복합식 AND(a,NOT(b))는 유일한 양성 입력 (true,false)을 놓쳤다. 복합식의 실제 응답은 네 행 모두 false다. 실패의 직접 위치는 이 복합식의 반환값이다. NOT 또는 AND 단독의 수행 불가, 파서가 답을 바꾼 문제, adm_minimal.py의 오채점으로 설명할 자료가 아니다.

현재 증거가 지지하는 표현은 **해당 모델·프롬프트·출력제약·시드 조합에서 단독 연산의 성공이 복합식의 성공으로 이어지지 않았다**는 것이다. 모델 내부에서 어떤 학습된 패턴이나 토큰 선택이 그 오류를 유발했는지까지 특정한 결과는 아니다.

이번에는 기존 16건의 채점을 바꾸지 않는다. v0.4.6은 진단 분류를 수정하고, NOT의 실제 모델 반환값을 후속 AND 호출의 입력으로 연결하는 실행 경로를 제공한다.

## 2. 정확한 결과

| a | b | COPY 실제/정답 | AND 실제/정답 | NOT b 실제/정답 | AND-NOT 실제/정답 |
| --- | --- | --- | --- | --- | --- |
| F | F | F/F | F/F | T/T | F/F |
| F | T | F/F | F/F | F/F | F/F |
| T | F | T/T | F/F | T/T | **F/T** |
| T | T | T/T | T/T | F/F | F/F |

합계 15/16은 서로 다른 작업의 합계다. 이전 factor 실험의 12/16과 같은 과제가 아니므로 성능이 75%에서 93.75%로 향상됐다고 비교하지 않는다.

복합식만 보면 항상 false인 상수 출력도 3/4를 맞힌다. 양성 검출은 0/1이다. 따라서 3/4라는 수치가 부정과 결합의 실제 수행을 충분히 보여주지는 않는다.

실패 case_id는 `47badd1edf3341302ec8411f`다.

```text
요청: input: {"a":true,"b":false,"expression":"(a AND (NOT b))"}
실제 응답 content: {"value":false}
정답: true
```

같은 원래 입력의 NOT 단독 응답은 true, AND(a,b) 단독 응답은 false다. AND(true,true) 단독 응답도 true다. 따라서 NOT 단독 또는 AND의 진리값 조합을 전혀 내지 못한다는 설명에는 실제 반례가 있다.

반대로 모든 복합식 결과를 “NOT를 무시했다”고 설명하는 것도 맞지 않는다. NOT를 단순히 무시해 AND(a,b)를 계산했다면 (true,true)에서 true를 내야 하지만 실제 복합식은 false였다. 관측된 함수표와 내부 계산 경로를 구분해야 한다.

## 3. 실제로 채점한 코드는 어디인가

현재 operator 과제의 응답 판정은 `local_llm/operator_probe.py::assess_payload()`의 유한 진리표에서 이루어진다. `runner.assess_response()`가 `operator-v045`를 이 평가기로 분기한다. `adm_minimal.py::verify()`가 이 불리언 하나를 거부해서 생긴 FAIL은 아니다.

core는 사전 검사와 문제의 유효성·결합 확인에 사용된다. 이번에는 독립적인 제한 문법 파서로 네 식을 재계산하고, 별도로 core의 수락 기준도 검사했다.

| 교차검증 | 범위 | 결과 |
| --- | ---: | --- |
| 별도 식 파서·직접 명시 진리표·operator 평가기 | 16조건 × 반환 bool 2개 = 32조합 | 전부 일치 |
| 직접 명시 기준표·core 기준 검토 | 4입력 × 판정 8조합 = 32조합 | 전부 일치 |
| 원래 실패 응답의 value만 바꾼 복사본 | false / true 2조합 | false 거부, true 수락 |
| 직접식과 교환식의 논리적 동치 | 4입력 | 전부 일치 |
| 보존 템플릿의 실제 단일턴 렌더 | 16개 입력 | 명시적 메시지 형식과 일치 |

이들은 합성 입력과 오프라인 검사다. 신규 LLM 표본이나 독립된 사람의 검토 수로 집계하지 않는다. core 전체의 모든 가능한 결함을 증명 없이 배제하는 주장도 아니다.

## 5. 모델·런타임 외부 대조

업로드 metadata는 Qwen3-4B-Instruct-2507 / Q4_K_M, 서버 버전 문자열 0.34.0을 기록한다. 설정은 temperature 0.7, top_p 0.8, top_k 20, min_p 0, think 생략이다. Qwen 공식 모델 카드의 non-thinking 전용 설명과 권장 샘플링에 부합한다. 공식 문서의 권장값은 이 특정 문제의 정답 보장이 아니다.

Ollama 공식 문서는 JSON Schema를 출력 형식 제약으로 설명한다. 이 조합식의 논리적 정답까지 schema가 계산하는 것은 아니다. source의 SCHEMA는 `{"value": {"type": "boolean"}}`이며 const/enum으로 답을 지정하지 않는다.

외부 확인 출처:
- https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507 — non-thinking 전용 및 샘플링.
- https://docs.ollama.com/capabilities/structured-outputs — JSON/schema 모드 및 형식 제약.
- https://docs.ollama.com/api/chat — 응답 종료·토큰·처리 시간 필드.

사용자 기계의 실제 바이너리, 서버 내부 토큰열, 가중치 파일 바이트는 여기서 관측하지 않았다. 보존 템플릿 렌더 결과를 서버 내부 실행 관측으로 표현하지 않는다. 이번 ZIP에는 가중치 해시 검사 결과도 없다.

## 6. 제3자 관점 검토와 교차 반박

별도 사람이나 독립 에이전트를 호출한 것이 아니다. 아래는 같은 자료에 서로 다른 심사 기준을 적용한 관점별 검토이며, 알고리즘 대조는 앞의 실제 실행 검사로 수행했다.

### 검증기 심사 관점

주장: 먼저 채점표가 틀렸을 가능성을 확인해야 한다.
대조: 식 파서·직접 진리표·operator 평가기, core의 관련 기준이 일치한다. 실제 false를 true로 바꾼 합성 응답만 통과한다.
의견: 기존 FAIL을 유지한다. core나 점수를 완화할 이유는 없다.

### 모델 행동 관점

주장: 부정이 문제라면 NOT를 따로 보아야 한다.
대조: NOT가 모두 맞았다. AND도 모두 맞았다. 그러나 두 연산이 함께 있는 표현은 양성 입력을 놓친다.
의견: 관측 수준에서는 복합식 수행의 취약성으로 좁힌다. NOT 자체의 무능력이나 모델 크기 하나를 근본 원인으로 지정하지 않는다.

### 실험 설계 관점

주장: “연산 하나당 한 호출”이라는 이전 이름이 실험 구조를 정확히 설명하는가?
대조: `and_not_b`는 출력 필드가 하나지만 연산 그래프는 NOT→AND다. 기존 코드의 `all_atomic_correct` 및 실패 분류는 이 차이를 명시하지 않았다.
의견: 단일 출력·원시 게이트·복합식을 분리해서 보고한다. 실제 중간 모델값을 소비하는 연결 실행이 필요하다.

### 런타임 관점

주장: 고정 schema·특정 가중치/커널이 단순식에서도 특이한 결과를 낼 수 있다.
대조: 현재 모드·전송·응답 종료는 정상이고 true도 출력됐다. 실제 가중치/커널 비교는 없다.
의견: 태그 metadata만으로 런타임 영향 전체를 배제하지 않는다. 체크섬은 별도 검사하며, 모델 교체를 했다면 같은 조건의 별도 비교로 남겨야 한다.

### 반박을 종합한 선택

1. “NOT를 못 하므로 모델을 바꾼다”는 의견은 NOT 성공 사례와 충돌한다.
2. “15/16이니 거의 해결”이라는 의견은 복합식 양성 검출 0/1을 가린다.
3. “LLM 대신 코드로 NOT와 AND를 계산한다”는 방식은 이 실험의 모델 수행 측정을 바꾸므로 채택하지 않는다.
4. “단독 연산의 실제 모델 결과를 서로 연결한다”는 방식은 현재 관측을 활용하면서 여전히 모델이 두 연산을 수행하게 할 수 있다. 단, 연결 그래프는 호스트가 제공한 것으로 표시해야 한다.

네 번째를 구현한다. 다수결이나 가장 높은 합계가 아니라, 확인된 증거·반례·연구의 수행 주체 구분을 함께 만족하는 방식으로 선택했다.

## 7. v0.4.6의 수정과 새 실행

이번 16건의 최종 판정을 바꿔야 할 코드 결함은 발견하지 않았다. 수정한 것은 진단 분류와 실행 경계다.

- `operator_probe.summary`: primitive가 맞고 composite만 틀린 상태를 따로 분류한다. 미완료를 실패 원인처럼 해석하지 않는다. 호환성용 old key는 유지하되 설명을 수정한다.
- `operator_audit`: 승인된 v0.4.5 raw 요청·응답·소스와 판정을 다시 검사한다.
- `composition_probe`: 새 NOT 출력 c를 실제로 다음 AND(a,c) 호출에 전달한다.
- `runner`, `task_evidence`: 새 계약의 요청·채점·기록 라우팅을 연결한다.

기존 v0.4.5에서는 NOT를 성공해도 그 응답이 AND-NOT 과제의 입력에 들어가지 않았다. 두 과제가 독립적이었다. 이번에는 새 NOT 응답을 받은 뒤에만 다음 요청을 만든다. 다음 요청에서 c는 직전 모델의 실제 값이며 코드의 정답 계산값이 아니다.

기본 최대 12회: 새 NOT 4회 + 교환식 대조 4회 + 새 AND 4회.
교환식은 user expression 하나만 변경한다. 체인은 호출 횟수와 입력 구조를 바꾸므로 단일 표기 효과와 별도 해석한다.

잘못된 bool은 그대로 연결하되 전체 단계 검사에서 실패시킨다. 형식 오류로 사용할 값이 없으면 후속 호출을 차단하고 네 파이프라인의 분모에 남긴다. 최종값이 우연히 맞더라도 이전 단계가 틀리면 전체 통과가 아니다.

호스트가 NOT→AND 구조와 변수 연결을 제공한다. 모델이 자율적으로 문제를 분해했다는 성과로 세지 않는다. 게이트 호출은 새 실행이지만 이전 a/b를 재사용하므로 초기 입력 추출부터 다시 수행한 종단 간 ADM 성공도 아니다.

## 8. 실행·검증 상태

`all_tests.txt`, `new_tests.txt`, `selfcheck.json` 및 배포 패키지의 BUILD_STATUS를 참조한다. 모든 모델 응답 재현은 원래 보존된 응답을 다시 평가한 것이며 새 LLM 추론은 없다. 모의 API 시험은 제어 흐름·요청 바이트·오류 전파·재개 검사용이다.

모델 가중치 다운로드, 사용자 GPU/Windows 실행, 새 실제 모델 추론은 수행하지 않았다. 새 파이프라인의 실제 성공 여부는 사용자 실행 전에는 미측정이다.
