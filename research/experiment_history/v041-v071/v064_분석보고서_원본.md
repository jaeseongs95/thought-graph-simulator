# v064 실제 결과 분석 및 v065 구현 결정

## 1. 결론

**v064의 18회는 정상 완료됐고, 원래 D 대응 기준은 0/6쌍으로 불통과다.** 다만 strict 유효 증명이 6/18이라는 숫자만으로 나머지12개가 논리적으로 틀렸다고 읽으면 안 된다. 실제로는 **18개 모두 각 노드의 사실·규칙·부모 연결 검사를 통과**했고, 새 두 문제의12개는 최종 목표에 쓰이지 않는 노드를 출력해 strict 계약에서 탈락했다.

모든 문제에서 shallow/deep/neutral과 관계없이 같은 짧은 최종 경로를 골랐다. 긴 경로의 중간 노드가 출력된 경우도 있었지만 최종 goal은 그 경로에 연결되지 않았다. 불필요한 노드를 제거한다고 deep 경로가 새로 생기는 것은 아니다. 원문이나 기존0/6 판정을 고치지 않았다.

다음은 한정된 **12회 지정 마지막 규칙 구성 검사(v065)**로 정했다. 마지막 규칙을 직접 알려줬을 때 완전한 짧은/긴 증명을 구성하고 무관 노드를 배제할 수 있는지 검사한다. 이 검사의 성공은 고정 경로 구성 능력이며, D 명령만으로 경로를 선택하는 성공으로 승격하지 않는다. v064가 통과하지 않았으므로 A/M 실험으로 바로 진입하지 않는다.

## 3. 실제 결과

각 문제에서 방향3개×seed2개=6응답이다.

|문제|각 노드 논리 검사|엄격한 전체 증명|공식 actual_D|원문 최종 지지 깊이 진단|최종 규칙|D 대응|
|---|---:|---:|---|---|---|---:|
|T02|6/6|6/6|전부1|전부1|전부r83|0/2쌍|
|E01_shared_fork|6/6|0/6|전부null|전부1|전부n52|0/2쌍|

E01/E02의 진단 깊이는 **원문에 이미 있는 final과 parents를 따라 계산한 값**이다. 노드를 삭제한 새 정답을 만들거나 official actual_D를 null에서 숫자로 바꾼 것이 아니다. 가능한 goal 깊이는 T02 {1,4}, E01 {1,2}, E02 {2,4}임을 별도 전방 계산으로 확인했다.

### T02

r83으로 Lp와 Ls에서 Lg를 직접 도출했다. 모든 방향·seed에서 같은 구조였다. 유효한 증명 생성은 성공했지만 deep 요청에서 필요한 깊이4를 만들지 않았다.

### E01

Aa/Ab 사실, Ax/Ay 중간 노드를 모두 올바르게 만들었지만 final은 Aa/Ab를 바로 쓰는 n52였다. Ax/Ay는 그 final을 지지하지 않는 추가 노드다. 같은5개 노드 구조가6회 반복됐다.

긴 경로의 마지막 규칙은 n37이며 Ax/Ay/Ab가 전제다. 원문에는 n37을 적용한 goal 노드가 없었다. 중간 전제를 만들었다는 사실과 완전한 깊은 goal 증명을 구성했다는 사실은 다르다.

### E02

Pa/Pb/Pc에서 짧은 쪽 Ps뿐 아니라 긴 쪽 Pu→Pv→Pw도 국소적으로 올바르게 만들었다. Pw까지의 깊이는3이다. 그런데 final은 m76으로 Ps/Pc를 연결한 깊이2의 goal이었다. 긴 쪽 Pu/Pv/Pw는 final과 무관한 노드가 됐다. 같은8개 노드 구조가6회 반복됐다.

긴 goal을 완성하는 규칙은 m41: Pw→Pg다. 이것이 원문에서 적용되지 않았다. 따라서 “깊이4 경로를 만들었는데 출력 순서 때문에만 실패했다”는 해석은 맞지 않는다. 이번12개 strict 실패에는 non_topological_order가 없고 extra_unused_node만 있다.

### 기존 logical_failures 필드의 의미

v064 summary의 `logical_failures=12`는 실제 코드상 strict 실패도 포함하는 이름이다. 이번12개는 전부 proof_valid=true, strict_valid=false였다. 기존 summary는 원본대로 보존했고, 이번 분석과 새 보고서는 **논리 실패0 / strict-only 실패12**로 구분한다. 성공률을 올리기 위한 재채점이 아니라 진단 항목의 의미를 바로 읽은 것이다.

전수표: `all_18_responses.csv`, `six_D_pairs.csv`, `problem_summary.csv`. 실제 payload는 `raw_payloads.json`에 별도 보존했다.

## 4. 현재 가능한 판단

**확인:** 노드의 국소 사실/규칙/연결은 구성할 수 있었고, final은 항상 짧은 규칙을 선택했다. E01/E02에서 다른 가지의 중간 노드도 만들었지만 선택한 final의 증명으로만 묶지 못했다.

**미분리:** 깊이 요구를 마지막 규칙 선택으로 연결하지 못한 것인지, 원하는 final을 지정해도 전체 구조를 완결하지 못하는 것인지. 모델의 학습된 우선순위, 내부 알고리즘, 의도를 이번 원문으로 확정하지 않는다.

**다음 판단에 필요한 것:** final 규칙을 명시하면 깊은 목표 증명과 strict closure를 만족시킬 수 있는지. 답이 주어지지 않은 D 선택 능력과 경로가 지정된 구성 능력은 분리한다.

## 6. 작성한 v065

3문제×2seed×2지정 규칙=12회다. 짧은/긴 지정은 각 문제의 두 seed에서 순서를 반대로 배치해 위치가 균형이다. 중립은 이번에 재실행하지 않는다. 원 v064의 중립6개를 삭제하거나 성공 분모에 합치지 않는다.

|문제|짧은 규칙 지정|긴 규칙 지정|
|---|---|---|
|T02|r83|r69|
|E01|n52|n37|
|E02|m76|m41|

원래 “가장 작은/큰 경로를 선택하라” 문장을 다음 유형으로 바꾼다.

```text
최종 goal 노드의 rule은 반드시 'r69'로 지정한다. 이 규칙을 마지막으로 사용하는 유효한 증명 하나를 구성한다.
```

나머지 그래프 작성 지시·문제 JSON·규칙 순서·schema·옵션·seed·모델은 보존했다. 실제 v064에 대응하는12개 요청과 최종 배포본의 새12개 요청을 전수 대조했다. 다른 메시지 필드나 샘플링 설정은 바뀌지 않았고, 정답 DAG·부모 ID·중간 노드를 넣지 않았다.

평가기 `measure.py`는 v064와 바이트 동일하다. 새 집계는 규칙명 이행, 국소 논리, strict 유효성, 실제 D, 지정 구성 성공을 따로 기록한다. `D_instruction_control`은 not_measured이고 A/M 진입은null이다. 잘못된 중간값/규칙/부모/노드를 고치거나 원하는 경로만 골라주지 않는다.

### 결과별 다음 행동

- 모든 지정 경로가 strict하게 구성됨: 고정 경로 구성 기준선만 확보. D로 선택하고 실제 출력값을 그대로 전달하는 시스템이 필요한지 별도 직접/단계형 대조를 검토한다.
- 깊은 지정 경로 strict 성공이0: 이 모델·현재 출력 인터페이스의 지정 구성 분기를 종료한다. 문구만 바꿔 반복하지 않는다. 이는 다른 모델이나 A/M 연구 전체의 불가능을 뜻하지 않는다.
- 일부 성공: 조건별 범위를 그대로 남긴다. 성공 seed만 골라 전체 성공으로 바꾸지 않는다.
- 미완료/미측정: 전체 진입 판정null. 오류 원문을 보존하며 자동 재시도하지 않는다.

## 7. 코드 및 배포 검증

원본 v064 시험:19개 중18통과, Windows 전용1개 제외.

새 소스의 최종 ZIP을 새 빈 폴더에 추출한 시험: **54개 중53통과, Windows 전용1개 제외**. 같은54개를 두 번 실행한 것을108개의 서로 다른 시험으로 부르지 않는다. 48개 정상/오류 의미 사례의 생산/독립 계산 일치 검사는 이 시험 모음에 포함된다.

검사에는 지정 경로 이행, 짧은 경로 고정, 반대 경로, 규칙 이름만 맞고 부모가 틀린 경우, 무관 노드, 위상순서, 파싱 미측정, HTTP/identity/생성 예산 중단, 한 pending action의 미채점 원문 보존, 재해시 변조, 한국어 보고서 변조, source 변경, 기존 결과 충돌을 포함했다.

자동화는 별도 하위 Python 프로세스에서 소스 검사·설치·준비·12회 합성 HTTP·독립 검산까지 실행했다. stderr에 텍스트가 있어도 종료코드0이면 성공하고, 종료코드가 잘못되면 추가 시도 없이 중단하는 것을 확인했다. 동일 manifest만 보고 수정된 소스를 재사용하지 않고 실제 파일 hash로 검사했다.

## 9. 실제 검증 경계

이 환경은 Linux/Python3.13.5이며 새로운 실제 Qwen 추론은0회다. 사용자 모델의18개 응답을 분석했고 새 코드는 합성 서버로 검증했다. Windows PowerShell을 이 환경에서 직접 실행하지 않았다. 이전에 사용한 방식의 UTF-8·인자 전달·종료코드 경계를 적용하고, 내장 ZIP을 다시 꺼내 실제 최종 ZIP 바이트와 일치시켰다.

이전 코드의 OS별 manifest 정렬 차이는 새 `common.sources()`에서 POSIX 상대경로 문자열 정렬로 제거했다. 동일한 빌드 환경에서 재빌드 ZIP이 바이트 동일함을 확인했다. 모든 Python/zlib 버전 사이의 압축 바이트 동일성을 주장하지 않는다.

수집·검산 보증은 동봉 파일과 계획의 일관성이다. 동일 OS 권한의 공격자가 원자료와 전체 코드를 함께 바꾸는 상황을 외부 전자서명으로 방어하거나 실제 물리적 모델 수신을 인증하는 체계는 아니다. 손상된 committed JSON/torn event를 자동 복구하지 않는다.
