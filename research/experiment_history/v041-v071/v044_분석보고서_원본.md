# v044 factor 원인 분석 — 총점은 같지만 실패 내용은 다르다

## 결론

네 군은 모두 3/4 성공이다. 그러나 `b_last`는 엄격 수락 오류를 없애고 gap 오류만 남겼다.
나머지 세 군은 두 항목을 모두 틀렸다. 따라서 “전부 같은 조건에서 FAIL이면 모델 자체 문제”라는
앞선 분기 기준만으로 이번 결과를 처리하면 부분 변화를 놓친다.

현재 가장 강한 결론은 다음과 같다.

> 이 모델·서버·요청 조합에서는 b를 마지막에 두었을 때 strict 값이 달라진 대응 사례가 관측됐다.
> 한편 gap는 16개 응답 모두 false이며, true여야 하는 네 대응 조건을 모두 놓쳤다.
> NOT 단독 오류인지, AND-NOT 조합 오류인지, 여러 필드 작성의 문제인지는 현재 과제만으로 분리되지 않는다.

원래 core의 거부는 타당하다. 현재 채점을 바꾸는 core 결함은 발견하지 못했다. 실제 LLM 내부 원인을
단일하게 확정한 결과로 표현하지 않는다.

- 기존 상태, 오류, audit 전체 객체, 사용량, 종료 원인, 채널, 상세 진단: 16/16 재현.
- 실행 시 보존된 런타임 소스 36개와 실제 배포 ZIP 바이트: 전부 일치.

`replay.json`, `cases.json`, `EVIDENCE.ko.md`에 상세 근거를 보존했다.

## 1. 측정 결과

식의 정의는 a=목표 동일성, b=초기 사실 소속 여부다.
최종 판정 순서는 `(a, a AND b, a AND NOT b)`이다.

| 군 | 정확한 행 | 정확한 비트 | 거짓 strict 수락 | gap 양성 검출 |
| --- | ---: | ---: | ---: | ---: |
| replay | 3/4 | 10/12 | 1 | 0/1 |
| json | 3/4 | 10/12 | 1 | 0/1 |
| b_last | 3/4 | 11/12 | 0 | 0/1 |
| neutral_keys | 3/4 | 10/12 | 1 | 0/1 |

전체는 12/16 행, 41/48 비트가 맞다. 네 군은 독립된 네 문제 집합이 아니라 같은 네 입력의 대응 조건이다.
이를 일반 정확도 75%나 독립 표본 16개에 대한 통계적 추정으로 확대하지 않는다.

### 가장 중요한 입력: a=true, b=false

정답은 `T,F,T`다.

- replay/json/neutral_keys: `T,T,F` — b가 false인데 strict=true, 그리고 gap=false.
- b_last: `T,F,F` — strict는 맞지만 gap=false.

`b_last`의 입력 문자열에서 바뀐 것은 primitives의 두 키 순서뿐이다. 값, system 메시지,
출력 스키마, 모델, 샘플링, seed는 그대로인 것을 실제 wire 수준에서 확인했다.
이 대응 사례는 입력 배치와 무관하게 완전히 같은 실패라고 설명할 수 없게 한다. 하지만 단 한 시드의
한 쌍 변화이므로 입력 순서의 일반적 인과효과를 추정한 것은 아니다.

### b_last는 또 다른 내부 일관성 오류를 드러낸다

`answer_only=true`, `proof_and_goal=false`이면 두 기준의 수락 여부가 다르다.
그런데 `gap=false`라고 답했다. 기존 세 군의 `T,T,F`는 최종 필드끼리는 일관적이지만 초기 사실 조건을
어겼고, b_last의 `T,F,F`는 최종 필드끼리의 관계도 틀렸다. 두 실패를 같은 원인으로 합쳐서는 안 된다.

### 재현성과 부분 대조

replay의 네 응답 content는 과거 staged 네 응답과 각각 바이트 단위로 같다.
json과 neutral_keys는 대응하는 값이 네 입력 모두 replay와 같다. json은 JSON 키 직렬화 순서가
다르고 neutral_keys는 이름이 다르므로 원문 바이트 동일이라고 표현하지 않는다.
현재 네 입력에서 format 완화나 최종 필드명 치환이 문제를 해결했다는 증거는 없다.

## 2. core와 평가기 교차검사

`adm_minimal.py` 316–320행은 아래를 원문에서 계산한다.

```python
answer_only = probe['atom'] == p['goal']
strict = answer_only and probe['atom'] in p['facts']
gap = answer_only and not strict
```

a=true일 때 b=false인 경우 strict=false, gap=true여야 한다.

### 실행한 합성 대조

1. 네 군 × 네 입력 × 가능한 3비트 출력 8개 = 128조합.
   명시적 진리표, local 평가기, core의 기준 검토가 128/128 일치했다.
2. 실제 응답 16개 × 최종 객체 키 순열 6개 = 96조합.
   키 순서만 바꿔도 판정은 전부 유지됐다. 채점기가 키 순서 때문에 거부한 것이 아니다.
3. 실패 네 응답에서 잘못된 비트만 바꾼 복사본 = 14개.
   b_last는 gap 한 비트만, 나머지는 strict와 gap 두 비트를 모두 고쳐야 통과했다.

합성 복사본은 모델 성공으로 집계하지 않았다. 이 검사는 거부를 발생시킨 값의 위치와 해당 유한 계약의
판정 일치를 확인한다. 전체 core를 수학적으로 완전 검증했다는 주장으로 확대하지 않는다.
상세는 `truth_table.json`, `counterfactuals.json`에 있다.

## 3. 모델·추론 엔진·원문 전달

실행 메타데이터는 Qwen3-4B-Instruct-2507 / Q4_K_M / think 필드 생략 / Ollama 0.34.0이다.
샘플링은 temperature 0.7, top_p 0.8, top_k 20, min_p 0, repeat_penalty 1이다.
Qwen 공식 카드의 non-thinking 계열 설명과 권장 샘플링에 맞는다. 다만 공식 권장값이 이 과제의
성공이나 최적값을 보장하는 것은 아니다.

- 16/16 정상 stop 종료. 최대 생성은 24토큰, 합계 364토큰. 설정 한도는 4,096토큰.
- OOM, HTTP 실패, 출력 길이 잘림 기록이 없다. 이를 PC 사양 부족의 증거로 삼을 수 없다.
- 요청마다 모델 digest가 확인됐고 보존된 모델 적재 정보와도 일치한다.
- 현재와 과거 원문의 show 지문/모델 digest/서버 버전은 일치한다.
- 저장된 Jinja 템플릿을 실제 16개 system+user 메시지로 렌더해 표준 단일턴 구분자 형식과 대조했다.
  16/16 일치했다. 서버가 실제 사용한 최종 토큰열을 관측한 것은 아니다.
- 클라이언트는 저장할 응답 content를 다시 정렬하거나 불리언을 교정하지 않는다.
  각 요청을 POST하고 응답 원문을 저장한다. 클라이언트 응답 재사용 로직은 없다.
- prompt cache 사용량은 기록돼 있지만, 그 수치나 동일한 응답만으로 잘못된 결과 캐시를 입증하지 못한다.

## 4. 관점별 주장·반박·채택

아래는 같은 분석자가 서로 다른 심사 기준을 적용한 검토다. 외부 사람 또는 별도 에이전트 여러 명을
실제로 호출하지 않았다. 프로그램 교차검사는 원문 재현과 별도 명시 진리표를 사용했다.

### 형식 검증 관점

주장: core가 너무 엄격해서 실패했는가?
대조: `T,F,F` 또는 `T,T,F`를 정답 `T,F,T`로 볼 근거가 없고, 128조합 교차검사도 일치한다.
채택: 거부 유지. 본 문제의 채점 기준 완화는 수정이 아니다.

### 측정·통계 관점

주장: 모든 군이 3/4이므로 조작은 무효인가?
반박: strict의 false positive가 1에서 0으로 바뀌고 비트 정답이 10에서 11로 바뀌었다.
채택: 전체 행 성공과 필드 변화/오류 심각도를 분리한다. 한 시드의 작은 대응 사례를 일반 효과로 단정하지 않는다.

### 모델 행동 관점

주장: 네 군 모두 gap를 놓쳤으니 NOT를 못 하는가?
반박: 현재 과제는 NOT 단독을 질문하지 않았다. 변수 대응, 부정-결합, 다중 필드 유지가 섞여 있다.
채택: NOT 단독과 AND-NOT를 분리해야 한다. 지금은 관측된 gap 상수화라고 표현한다.

### 런타임 관점

주장: schema/정렬/캐시/가중치 손상이 원인인가?
대조: JSON mode로 바꿔도 값이 같고, b_last에서 값 변화는 실제 보인다. 모드와 보존 템플릿은 적합하다.
하지만 내부 서버 경로와 가중치 파일을 모두 관측하지 않았으므로 완전 배제도 하지 않는다.
채택: 특정 엔진 버그나 파일 손상을 확정하지 않는다. byte 검사 결과와 같은 최소 과제의 다른 모델 대조가 필요한 영역이다.

### 실행 설계 관점

주장: b_last가 가장 나으니 이제 그것으로 고정해 계속 진행할 수 있는가?
반박: gap 양성 검출은 여전히 0이다. 3/4가 아니라 반례 탐지 계약의 완성이 필요한 단계다.
채택: 성공한 모양을 선택해 원래 결과를 대체하지 않는다. 입력을 그대로 투영한 단일 연산 호출로
연산별 출력을 수집하고, 조립 결과도 조건부 진단으로만 남긴다.

### 최종 선정

다수의 관점이 지지해서 선택한 것이 아니다. 실제 반례와 부분 성공을 동시에 설명하는 판단은
“입력 배치에 따른 partial strict 변화 + 현재 응답군 전체의 gap 누락”이다.
이로부터 4B 전체의 능력 한계나 이론 실패를 선언하는 의견은 채택하지 않는다.

## 5. 발견한 소스 문제와 수정

### 결과 표시의 문제

기존 summary의 Markdown 표 안에 설명 문단을 삽입해 뒤쪽 군의 행이 표 밖으로 나갔다.
수정본은 네 행을 연속해서 표시하고 필드별 TP/FN/TN/FP와 양성 검출을 추가한다.
기존 decision_tables.json에 있던 correct_bits/false_acceptance를 숨기지 않는다.
이 표시 문제는 모델이 틀린 답을 낸 원인이 아니다.

### core identity의 방어 결함

기존 `core_identity_compatibility({}, {})`는 `None == None` 경로로 same_source=true를 반환했다.
수정본은 유효한 해시가 없으면 false다. 빈 문자열/잘못된 길이도 허용하지 않는다.
사용자 실제 로그에는 유효한 raw/normalized 해시가 모두 있으므로 이번 실패의 원인은 아니다.
원래 CRLF/BOM 호환성은 유지했다. `identity_empty_counterexample.json`에 수정 전후를 보존했다.

### 새 단일 연산 실행

동일한 네 모델 중간값으로 다음을 별도 호출한다: a / a AND b / NOT b / a AND (NOT b).
한 호출에는 식 하나와 value 하나만 들어간다. 기본 16회이며 모델/서버/샘플링은 동일하다.

모델 반환값 a, AND, AND-NOT를 최종 세 판정에 일대일 복사해 조립한다. 코드가 계산한 정답이나
NOT의 반환값으로 AND-NOT 오류를 자동 보충하지 않는다. 이전 중간값이 틀리면 과제 전체 실패를 유지한다.
이 조립은 새 ADM 종단 간 성공으로 세지 않는다.

새 표현은 문맥, 변수명, 출력 부담도 바꾸므로 순수하게 하나의 요인 효과라고 부르지 않는다.
모든 단일 연산이 맞으면 “해당 Boolean 값을 산출할 능력이 없다”는 설명과 충돌한다.
실패가 남으면 동일한 최소 과제를 다른 설치 모델과 비교할 수 있는 명시 옵션을 제공한다.
새 모델을 자동 설치하거나 실패를 성공할 때까지 재시도하지 않는다.

## 6. 실제 검증과 미실행 영역

원본 v0.4.4.1 오프라인 시험 241개를 실행해 통과했다.
수정본은 기존 241개와 신규 35개, 합계 276개를 실행해 통과했다. 자체 검사 21항목도 통과했다.
새 시험에는 16건 회귀, CRLF 호환, 실제 내용 변경 차단, 32개 단일 연산 출력 조합,
잘린 응답/잘못된 자료형, 모의 API 16회 실행, 실패 보존, 재개 시 재호출 방지가 포함된다.

모의 API는 실제 모델의 성능 시험이 아니다. 실제 LLM 추론, Windows/GPU 실행, 사용자 가중치 파일 검사는
수행하지 않았다. 최종 ZIP 재검사 결과는 별도 package_validation에 기록한다.
