# v0.4.2 결과 분석 및 v0.4.3 수정 근거

## 결론

이번 8건은 입력 전반의 오독이 아니라, 기준 과제의 **정확한 입력 사본·기본 판정과 모순되는 최종 판정**을 보여 준다. 기준 과제 네 건의 `observed`와 `primitives`는 전부 맞았지만 `finding`은 모두 `(false,false,false)`였다. 이 때문에 목표가 맞는 두 조건을 실패했고, 목표가 다른 두 조건만 통과했다.

반면 이것만으로 가중치, 양자화, 추론 엔진, 프롬프트 중 하나를 유일한 내부 원인으로 확정할 수는 없다. 직접 확인한 것은 출력 모순의 위치와 하네스가 실행 순서를 보장하지 않았다는 설계 전제다. 이번 수정은 이를 실제 두 호출의 입출력 연결로 바꾸는 선택형 경로와, 다른 변경을 배제한 format 대조를 제공한다. 원래 원샷 실패를 성공으로 덮어쓰지 않는다.

새 입력 자료는 `results_llm_042.zip`이다. `v042_micro_01`의 8개 응답만 새 LLM 관측이다. 함께 든 `v042_probe_audit_01`은 이전 12개 응답의 오프라인 재검사이며 신규 표본에 합산하지 않았다.

## 2. 실패한 것은 무엇인가

`a = probe.atom == goal`, `b = probe.atom in facts`라고 하면 정답은 `(a, a AND b, a AND NOT b)`다. rules로 목표가 도출되는지는 이 단독 사실 probe 판정에서 추가로 계산하지 않는다. 이 계약은 기존 `adm_minimal.py`의 기준 검토 코드와 같다.

| 과제 | a | b | 모델의 primitives | 정답 finding | 실제 finding |
|---|---|---|---|---|---|
| criterion_goal_not_fact | T | F | T,F | T,F,T | F,F,F |
| criterion_fact_not_goal | F | T | F,T | F,F,F | F,F,F |
| criterion_goal_is_fact | T | T | T,T | T,T,F | F,F,F |
| criterion_neither | F | F | F,F | F,F,F | F,F,F |

예컨대 목표 `Cc`, 주장 `Cc`, 사실 `[Ca,Cc]`인 응답은 `same_as_goal=true`, `in_facts=true`라고 출력하면서 `answer_only_accepts=false`, `proof_and_goal_accepts=false`라고 출력했다. 단순히 “모델이 Cc를 읽지 못했다”는 설명은 이 출력과 맞지 않는다. [네 조건의 원문 대조](witnesses.json)

네 조건에서 늘 F,F,F를 내는 상수 기준선도 2/4다. 최종 판정의 50%를 조건을 구별하는 능력의 증거로 읽어서는 안 된다. 세 최종 필드 모두 실제 양성에 대한 참양성은 0이고 음성은 맞았다. 현재 고정 진리표에서 각 필드의 sensitivity=0, specificity=1, balanced accuracy=0.5다. 이는 네 입력과 한 시드의 기술 통계이지 모집단 성능 추정이 아니다. 반대로 입력 사본과 두 기본 판정의 정확성은 별도 관측으로 남는다. [확장 집계](v043_reanalysis/reanalysis.json)

## 3. 중요한 실행 전제 오류: 필드 나열은 단계 실행이 아니다

프롬프트와 요청의 `properties`에는 `observed → primitives → finding` 순서가 보존돼 있다. 그러나 실제 `message.content`의 네 기준 응답은 모두 `finding → observed → primitives` 순서다. 전체 8응답의 20개 JSON 객체 순서가 모두 사전순이었다. 이것은 보고서 재출력의 순서가 아니라 저장된 응답 content의 순서다. 클라이언트는 HTTP 응답 원문을 그대로 저장하며 그 문자열 내부 키를 정렬하지 않는다. [순서 장부](output_orders.json), `baseline/local_llm/client.py`, `baseline/local_llm/runner.py`

이 기록으로 **반환된 직렬화 순서**는 확인할 수 있다. 서버가 후처리했는지, 디코더가 순서를 제한했는지, 모델이 그 순서로 생성했는지는 서버 내부 토큰 로그 없이 구별되지 않는다. 따라서 “올바른 중간값을 먼저 계산하고도 최종 답을 틀렸다”는 시간 순서 설명도, “알파벳 정렬이 실패의 단독 원인”이라는 설명도 채택하지 않는다.

폐기해야 할 전제는 “한 JSON 객체에 세 필드를 순서대로 요구하면 세 단계 실행이 보장된다”는 것이다. 실제 선행 단계 출력을 다음 호출의 입력으로 넘겨야 호출 간 데이터 의존관계를 보장할 수 있다. 새 staged 경로는 바로 이 실행 계약을 갖는다. 중간값이 바뀌거나 틀린 경우는 보충하지 않으며 파이프라인 성공으로 인정하지 않는다.

이번 독립 대조는 기존 `criterion_evidence` 함수를 정답 계산에 사용하지 않고, 네 불리언 입력의 진리표를 별도로 고정했다.

| 네 입력 × 가능한 세 출력 비트 | 32조합 | 진리표, local 평가기, core 판정 일치 |
| 네 실제 응답 × 루트 필드 순열 | 24조합 | 필드 순서와 무관하게 기존 판정 유지 |

## 5. 모델·런타임 조사

원본은 Ollama `0.34.0`, `qwen3:4b-instruct`, GGUF Instruct-2507, Q4_K_M이다. `think` 필드를 보내지 않았고, 샘플링은 temperature=.7, top_p=.8, top_k=20, min_p=0이다. 실제 태그와 /api/ps의 digest가 일치했다. Qwen 공식 모델카드는 이 체크포인트를 non-thinking 전용으로 설명하고 이 네 샘플링 값을 권장한다. 따라서 이전 Thinking 모델에 비추론 모드를 적용했던 문제를 이번 실패에 재적용하지 않는다. [실행 기록](runtime.json), [Qwen 공식 모델카드](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)

8응답 모두 정상 stop, 최대 출력 101토큰, 출력 합계 434토큰이다. 설정 한도는 4,096토큰, 문맥은 8,192토큰이며 기록된 입력도 짧다. OOM·전송 오류·잘림은 관측되지 않았다. /api/ps는 모델 적재 정보이며 최고 GPU 이용률 측정은 아니다. 실제 가중치 바이트와 서버 바이너리는 받지 않았으므로 엔진·양자화 영향을 모두 검증했다고 말하지 않는다.

출력 스키마의 세 finding 필드는 단순 boolean이며 false만 허용하는 const/enum은 없다. true를 포함하는 모든 여덟 출력 조합이 로컬 스키마를 통과하고, 실제 같은 응답 안의 primitives에도 true가 나온다. “서버가 모든 불리언의 true를 금지했다”는 가설은 맞지 않는다. 특정 키/문맥의 편향이나 엔진 영향을 전부 배제한 것은 아니다.

Ollama 공식 문서는 format='json'과 format=JSON Schema를 구분하고, 스키마를 프롬프트에도 넣는 구성을 설명한다. 기존 프롬프트에도 스키마는 이미 있었다. 단순히 이번에 스키마를 프롬프트에 추가하면 해결된다고 주장하지 않는다. 다음 format 대조는 메시지를 바꾸지 않는다. [Ollama 공식 문서](https://docs.ollama.com/capabilities/structured-outputs)

공개 소스도 확인했다. 공개 Ollama `83ed7d9965b1ee07e0f0b29fd46e47c31f0fcab8`의 LLAMA_CPP_VERSION은 b10760이고, 해당 llama.cpp의 common_json 설명은 객체 키의 삽입 순서를 유지한다고 한다. 변환기는 전달된 properties를 순회한다. 이 사실만으로 관측된 정렬의 원인 위치를 특정할 수는 없다. 사용자 서버의 version 문자열만으로 공개 소스의 정확한 build commit과 같다고 확인할 수 없고, 서버 전체 전달 경로를 실제 바이너리에서 실행한 것도 아니다. 원문 response 정렬을 곧바로 특정 upstream 함수의 버그로 확정하지 않았다. [외부 자료와 조사 범위](external_sources.json)

## 6. 관점별 제3자 검토와 교차반박

실제 별도 에이전트·외부 심사자를 호출한 결과가 아니다. 같은 분석자가 서로 다른 심사 기준을 적용했고, 기술적 교차검증은 별도 진리표·변이·실행 재현으로 수행했다. 지지하는 사람 수가 아니라 반례를 통과하는 설명을 선택했다.

### 형식 검증 심사

가설: 기준 정의나 검증기가 틀려 정상 판정을 거부한다.

검토: 정확히 같은 문자열인데 최종 동등성 판정이 false인 것은 정의와 충돌한다. 32조합 독립 진리표와 core가 일치하고, 필드 순열 24회는 판정을 바꾸지 않는다.

판단: 이번 판정은 유지한다. 성공 기준 완화나 host 정답 보충은 원인 해결이 아니다.

### 모델 행동 심사

가설: 소형 모델이 단순 동일성·소속 연산 자체를 수행하지 못한다.

반박: 중간 필드 8/8과 기본 대조 4/4가 맞는다. 모든 실패를 기본 비교 능력 부재로 설명할 수 없다. 그렇다고 최종 판정도 수행된 것으로 간주할 수 없다. 동일 응답 내부에 요구식과 충돌하는 값이 있다.

판단: 관측된 실패 위치를 최종 판정값과 중간값의 연결로 좁힌다. 모델 전체 능력이나 모든 AND 연산에 관한 결론으로 확대하지 않는다.

### 추론 엔진·출력 제약 심사

가설: JSON 제약이나 서버 정렬이 최종값을 먼저 만들게 해 실패시켰다.

지지 증거: 요청 순서와 반환 순서가 다르고 모든 객체가 사전순이다.

반박: 반환 순서와 생성 순서가 같다는 증거가 없고, 지금까지 이 입력 묶음에서 format을 바꾼 결과도 없다. 스키마는 true도 허용한다. 공개 converter 일부는 순서를 보존한다.

판단: 유력하게 조사할 조건이지만 단독 원인으로 확정하지 않는다. 실제 wire에서 format만 바꾼 대응 실험을 만든다.

### 실행 설계·측정 심사

가설: 세 필드를 한 호출에 배치한 것을 세 단계 수행으로 해석한 하네스의 전제가 문제다.

검토: 실제 원샷에 호출 간 선행 의존성이 없다는 것은 코드로 확인된다. 추가로 component_report는 task='criterion'만 집계하여 새 task='criterion_witness'의 상수 패턴을 누락했다. 이는 실패 원인을 만들지는 않지만 진단을 감춘다.

판단: 실제 후속 호출에서 앞선 모델의 observed/primitives를 읽도록 만들고, 잘못된 source 중간값은 교정하지 않는다. 원샷과 단계형의 결과를 섞지 않는다. 집계 누락은 즉시 수정한다.

### 종합 논쟁

“정렬이 원인이니 순서만 고치면 된다”는 의견은 원인 증거가 부족하여 채택하지 않았다. “모델이 기본 비교부터 못 한다”는 의견은 성공 반례 때문에 배제했다. “검증기를 완화한다”는 의견은 명시적 진리표와 충돌한다.

채택한 것은 **정상인 검증 계약을 유지하고, 실제 단계 경계를 제공하며, format 요인만 별도로 대조한다**는 접근이다. 이 접근은 관측된 모순을 숨기지 않고 미확인 원인을 단정하지 않는다.

JSON에서 값의 위치만 바꾸는 패치가 아니다. 기본 모델·샘플링·기존 프로토콜·기존 core는 바꾸지 않는다. 기존 요청과 결과 8건은 수정 후에도 그대로 재현된다.

## 8. 새 실행의 두 군은 다른 질문이다

**format_json 4회:** 같은 네 문제, 같은 messages와 options/seed/model에서 API의 format만 schema에서 'json'으로 바꾼다. 스키마는 같은 원문 prompt에 남아 있다. 모델이 낸 출력은 여전히 엄격한 기존 과제 스키마와 의미 검사를 받는다. 잘못된 객체나 불리언을 자동 변환하지 않는다. 새 결과가 좋아져도 한 시드의 대응 관측이지 일반적인 효과 크기 추정은 아니다.

**staged 4회:** 기존 모델 원문에서 observed와 primitives 두 객체만 복사해 후속 호출에 넘긴다. 원래 finding은 다음 입력에서 제외하지만 원본과 원래 실패 기록은 유지한다. 이 선택은 코드와 보고서에 명시되어 있다. 모든 네 조건을 사용하며, 중간값 정답을 계산해 주입하거나 성공한 조건만 추리지 않는다. 다음 finding이 옳더라도 원래 observed/primitives가 틀리면 end-to-end 파이프라인은 실패다.

staged는 호출 경계·프롬프트 길이/형태·출력 부담이 함께 달라지는 **파이프라인 변경**이다. 따라서 이것의 성공을 순수 생성 순서의 인과 효과나 원래 원샷 성공으로 주장하지 않는다. 본 A/D/M 조합의 성능에도 합산하지 않는다.

새 추론은 8회 배정이고 과거 schema 기준선은 재호출하지 않는다. 따라서 추가 지연·캐시 상태를 무시한 완전한 동시 무작위실험은 아니다. 모델 digest/메타데이터/서버 버전/core/확정 설정이 바뀌면 호출 전에 중단한다.

## 9. 결과별 판정 규칙

| 관측 | 가능한 결론 | 금지할 확대 해석 |
|---|---|---|
| format_json에서 원래 실패 조건 개선 | 이 대응 실행에서 format 차이와 결과 변화가 함께 나타남 | 엔진 버그가 유일 원인이라는 단정 |
| staged에서 원래 실패 조건 개선 | 원래 모델 중간값을 재사용한 파이프라인이 이 조건을 완성함 | 원샷 성공·순수 순서 효과·본 ADM 성공으로 재집계 |
| 둘 다 실패 | 두 변경으로는 이번 실패를 없애지 못함 | 정답 주입·검증 완화·실패 제외 |
| 결과에 형식 오류 포함 | 형식 단계와 의미 단계 분리 | 파싱 실패를 false 판정으로 대체 |
| 원본과 실행 메타데이터 불일치 | 이 대응 대조 조건이 충족되지 않음 | 조건이 다르지만 같은 실험이라고 계속 실행 |

새 모델을 여러 개 받거나 69조건을 재실행하는 것보다 우선 이 대응 결과가 필요하다. 다른 모델/엔진 검증이 필요해지면 그 한 요인만 바꾸어 별도 비교한다. 이번 전달물에서 그 비교를 수행했다고 주장하지 않는다.

## 10. 검사 상태

새 LLM 호출·모델 다운로드·GPU 실행·Windows 실행은 하지 않았다. 오프라인 전체 시험 204개(기존 172 + 새 32)와 자체 검사 21항목을 실행했다. 이전 실제 응답을 재사용한 회귀시험과 모의 API 시험은 새로운 모델 성능 데이터가 아니다. 실제 배포 ZIP 재추출 검사 결과는 별도 package_validation 파일을 따른다.
