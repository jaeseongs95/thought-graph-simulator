# v055_model_02 실제 결과 분석과 v056 결정

## 1. 결론

**이번에는 실행이 정상 완료됐다. Qwen은 유효한 증명 90/120, Gemma는 2/120이었다. 두 모델의 선택적 D 제어는 각각 0/40쌍이다.** 그러나 실패 지점이 다르므로 이를 같은 원인이나 같은 내부 정책의 증거로 합치지 않는다.

기록된 Gemma native template에는 system과 user 메시지를 각각 user로 매핑하는 분기가 있다. 기존 요청은 system(지시문)과 user(문제)를 분리한다. Google은 Gemma IT에 별도의 system 턴 대신 첫 user 메시지 안에 지시를 배치하도록 안내한다. 따라서 다음에는 모델을 더 늘리거나 정답 경로를 제공하지 않고, **기존 분리 배치와 동일 텍스트를 단일 user 메시지에 합친 배치를 두 모델에서 비교**한다.

이는 Gemma 실패의 원인이 이미 밝혀졌다는 결론이 아니다. 실제로 저장한 것은 API 요청과 template metadata이지 서버 내부의 최종 토큰 스트림이 아니다. 배치가 달라도 현재처럼 실패할 가능성까지 검출하도록 실험을 만들었다.

## 4. 무엇이 확인됐고, 무엇을 다음에 구별해야 하는가

현재 관측은 다음 두 종류다.

- Qwen: 대부분 증명을 만들지만, 지시한 짧음/깊음보다 규칙 순서에 따른 같은 경로를 선택한다.
- Gemma: 동일 API 요청 계약에서 증명 생성 경계부터 실패하는 경우가 많다. 몇몇 경우 긴 증명은 생성한다.

따라서 **두 모델 모두 D 대응쌍 0이라는 사실만으로 '모든 모델의 기본 사고 정책이 외부 지시보다 우선한다'는 원인을 도출하지 않는다.** 같은 실패 숫자가 같은 실패 과정을 뜻하지 않기 때문이다. 사용자가 제안한 학습된 기본 정책 가설은, 먼저 전달·구성 경계가 분리된 조건에서 검토하는 편이 정확하다.

v055 비교 자체를 무효로 돌리는 것은 아니다. 이것은 동일한 API 메시지·옵션 아래 **모델 패키지를 바꾼 결과**다. 다만 가중치뿐 아니라 native template도 패키지에 포함되므로, 차이를 곧바로 가중치나 학습 우선순위만의 효과로 분리할 수는 없다.

### 기록된 template에서 확인한 사항

Gemma template의 관련 분기는 다음과 같다.

```text
if role == user OR role == system:
    <start_of_turn>user
    content
    <end_of_turn>
```

실제 원문은 `recorded_templates.json`에 보존했다. 이 정의를 그대로 적용하면 기존 system/user 두 메시지는 user 턴 두 개로 배치된다. 그러나 서버 내부의 사전 처리 또는 최종 토큰화를 직접 캡처하지 않았으므로 이 도식을 실제 최종 토큰 기록이라고 주장하지 않는다. **지시문 텍스트가 없어졌다는 뜻도 아니다.**

Google의 공식 안내는 Gemma IT의 user/model 역할과 첫 user 메시지 내 system-level instruction 배치다. 이 문서와 실제 metadata를 결합하면, 내용은 그대로 두고 배치만 바꾸는 대조를 우선할 구체적인 근거가 된다.

참고: Google, *Gemma formatting and system instructions*, https://ai.google.dev/gemma/docs/core/prompt-structure (문서 표기 최종 갱신 2025-03-21).

## 5. 제3자 관점 대조와 채택한 방향

실제 외부 심사자나 별도 에이전트를 호출하지 않았다. 아래는 상충하는 심사 관점의 주장들을 원문과 별도 계산으로 대조한 결과다.

| 관점 | 검토한 해석/선택 | 증거에 따른 결론 |
|---|---|---|
| 형식/논리 | 평가기가 너무 엄격해서 실패했나? | 기존 평가와 독립 그래프 계산이 일치한다. 빠진 참조와 잘못된 규칙이 실제로 있다. 기존 기준을 완화하지 않는다. |
| 모델 행동 | 두 모델이 같은 방식으로 실패했나? | Qwen의 반복 경로와 Gemma의 구성 실패는 다르다. 같은 원인으로 묶지 않는다. |
| 전달/구현 | model 필드만 다르면 모델이 받는 역할도 같나? | native template의 역할 처리가 다르다. 배치를 추가로 대조할 이유가 있다. |
| 인과 | 메시지를 합치면 해결된다고 볼 수 있나? | 아직 그 처치를 실행하지 않았다. 분리 대조를 남겨서 무효·역효과·재현 변동을 모두 관측한다. |
| 비교 공정성 | Gemma만 좋은 조건으로 바꿀 것인가? | 두 모델에 똑같이 split/merged를 적용하고 두 문제·두 순서·중립·전체 seed를 유지한다. |
| 연구 목적 | 정상 JSON/증명만 나오면 성공인가? | 아니다. 선택적 D 대응쌍, 중립 대비, 두 순서의 견고성을 따로 판정한다. |
| 비용/실행 | 모델을 더 받거나 계획 JSON을 더 키울 것인가? | 기존 두 모델을 재사용한다. 재귀 JSON 대신 기준선 ZIP 별도 보존을 채택한다. |

**채택: v056 입력 메시지 배치 대조.** 더 큰 모델이나 세 번째 모델은 이번에 추가하지 않는다. 후보 증명을 주고 고르게 하는 방식도 아직 채택하지 않는다. 그것은 생성 과제를 바꾸는 추가 개입이기 때문이다.

## 6. v056 코드가 실제로 하는 것

```text
split:  system[기존 지시문] + user[기존 문제]
merged: user[기존 지시문 + 줄바꿈 두 개 + 기존 문제]
```

2모델×2배치×2문제×2규칙순서×3방향×10seed = **480회**다. 방향 지정320, 중립160이다.

실제 v055 기준선으로 계획을 준비하고 요청 480개를 전수 대조했다.

- split **240개 전부 원래 요청과 바이트 동일**.
- merged **240개 전부 메시지 결합만 다름**. 지시문 내용, 문제, 모델, 옵션, seed, schema는 동일.
- 기준선 수입·계획 준비·재읽기에서는 새 모델 추론 **0회**.
- 원래 v055 계획은 **9,433,093바이트**, 새 v056 계획은 **1,591,996바이트**였다. 이전 JSON을 반복 삽입하지 않고 원 ZIP을 별도 파일로 보존한다.
- 기존 Python 파일 **174개는 바이트 변경 없음**. 이 중 이전 생산 source fingerprint 대상은94개다. 새 생산10개를 더해 source snapshot은104개다.

각 seed에서 모델별 24회 블록을 두고 모델 선후는5:5, 블록 안 split/merged 선후는6:6으로 배정했다. warmup 추론은 없다. 모델 metadata의 사전 확인 및 블록 전후 확인은 추론 횟수와 구분한다.

증명 유효성 개선과 D 제어 개선은 다른 표로 보고한다. 미관측 응답은 false로 채우지 않으며, 미완료 실행의 전체 비교율은 null이다. 무효 증명에서 올바른 부분 경로만 골라 D를 만들어내지 않는다.

다음 결과의 판단은 다음처럼 고정했다.

1. 유효성과 선택적 D가 함께 개선 → 해당 모델/문제/순서에서 메시지 배치에 의존하는 제어의 근거.
2. 유효성만 개선 → 생성 경계 개선은 인정하지만 선택적 제어 문제는 남음.
3. 변화 없음 → 이 배치 개입은 실패. 다른 원인 구별이나 D operationalization 재검토로 이동.
4. split에서도 새 성공 → 반복 변동부터 검토. 병합 효과로 독점 귀속하지 않음.

역할·턴 경계·구분자가 함께 바뀐 대조이므로, 'system의 권한'이나 '토큰 위치' 하나의 효과를 각각 분리한 실험은 아니다. 내부 hidden state나 학습 원인도 직접 측정하지 않는다.

## 7. 작성 후 재검토와 검증 기록

초기 독립 검산기에서 정렬 JSON을 사용해 요청 바이트를 비교했지만, 생산 요청은 삽입 순서를 유지했다. 이 때문에 정상 병합 요청을 거부하는 시험 실패가 발생했다. 원래 삽입 순서를 유지하는 별도 인코더로 교정했다. 시험 경로의 .plan/.plan.json 차이도 바로잡았다. 증명 채점이나 모델 응답은 바꾸지 않았다.

소스 수정과 진행 중인 시험이 겹쳐 fingerprint gate가 '계획 이후 소스 변경'으로 거부한 실행도 있었다. 그 실행은 완료 검증으로 세지 않고, 소스를 동결한 후 다시 실행했다. 이 개발 실행을 새 모델 실패로 취급하지 않는다.

실제 완료한 검증 횟수는 `VALIDATION_RESULT.json`과 각 로그에 기록한다. 원본 v055의 712개 시험, 새 v056 시험, 최종 ZIP 전체 회귀는 서로 다른 실행이며 이전 성공 기록을 새 코드의 성공으로 대신 쓰지 않았다. 합성 서버의 정답 응답은 실제 Qwen/Gemma 성과가 아니다.

합성 반례는 정답 지시 이행, 항상 첫 가지, 병합만 성공, 분리만 성공, 유효성만 개선, 첫 HTTP 실패, 두 번째 모델 HTTP 실패로 구분했다. 잘못된 규칙/노드/최종 참조, 파싱 불가, 길이 종료, metadata 불일치, 파일·요청·소스·summary 변조는 별도 회귀시험에 포함했다.

자동화는 별도 하위 Python 프로세스에서 설치·자체시험·prepare·preflight·480회 합성 HTTP·audit·bundle·독립 검산까지 실행했다. Windows PowerShell 5.1을 실제 Windows에서 실행한 것은 아니다. PowerShell은 소스 ZIP이 내장된 얇은 실행기로 만들고, native stderr 문자열 대신 종료 코드를 확인한다. 최종 payload는 실제 배포 ZIP 바이트와 일치시켰다.

## 8. 휴대폰 원격 실행

**Run-v056-Auto.ps1 하나만 PC의 다운로드 폴더에 저장**한다. 소스 ZIP을 별도로 받을 필요가 없다.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\Downloads\Run-v056-Auto.ps1"
```

기존 저장소, v055_model_02_evidence.zip, 설치된 Qwen/Gemma를 자동으로 확인한다. 모델 다운로드/갱신은 하지 않는다. Ollama가 꺼져 있으면 서버만 시작한다. 실제 두 모델의 식별값이 달라지면 추론 전에 중단한다.

소스 전 파일 해시 검사 후 동일 설치만 재사용한다. 다른 설치본은 삭제하지 않고 백업한다. 새로운 빈 RunName을 한 번 선택해 실행하며, 실패 뒤 자동으로 다른 이름을 골라 재시작하지 않는다.

완료 후 주요 파일:

```text
results_llm/v056_layout_01/summary.ko.md
results_llm/v056_layout_01_evidence.zip
results_llm/v056_layout_01_independent.json
```

이미01 자료가 있으면02 등 다음 빈 번호를 사용한다. 기존 v055 결과와 실패 계획은 건드리지 않는다. 새 실제 480회 Qwen/Gemma 추론은 이 배포 검증 환경에서 실행하지 않았다.
