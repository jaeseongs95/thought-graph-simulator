# v0.2 실행 결과 분석과 v0.3 수정 근거

## 결론

39조건을 시작하지 못한 직접 원인은 v0.2의 **성능 성공을 요구하는 smoke 게이트**다. 첨부 ZIP에는 calibration 8건과 smoke 6건이 있고 pilot 실행 기록은 없다. smoke에서 역할 미준수/표현 오류가 나오자 프로그램이 다음 단계 시작 전에 차단했다.

이것은 설치 오류가 아니다. 다만 역할을 따르는지 측정하는 연구에 “역할을 전부 따라야 측정을 계속한다”는 조건을 기본 적용한 것은 부적절했다. v0.3은 **기술적 실행 준비 검사와 의미·역할 성능 판정**을 분리했다. 검증기 자체를 느슨하게 하거나 실패 응답을 성공으로 바꾸지 않는다.

이번 결과는 모두 실패한 것도 아니다. smoke의 증명 자체는 6/6 유효하고, 표현·검토까지 포함한 전체 제출물은 5/6 유효하다. 다만 요청한 A/D/M을 모두 충족한 조건은 지시 조건 5개 중 1개다. A 표현 전환과 M0→M1 변화가 일부 관측됐고, D의 얕음/깊음 분리와 M2 수행은 실패했다.

## 1. 근거와 실제 수행 범위

입력은 사용자 제공 `results_llm (2).zip`이다. 기존 v0.2 소스 ZIP과 양쪽 실행 manifest·원문 요청/응답·record·core 스냅샷을 대조했다. 런타임 15개 파일은 두 실행에서 모두 이전 배포본과 일치한다. core Git blob은 `b7aa0b58b9257fdb80882b48e4ecf1006ac4ff45`, SHA-256은 `24542551351225d4a2ed0e65c95cfca3d850e7bbd102439f1f3662d2eefcfad8`이다.

14개 원문 응답을 오프라인 재검사해 기존 상태·성공 여부·진단 검사 판정을 14/14 재현했다. 설명 문구는 v0.3에서 명료화했으므로 문자열 일치와 의미 판정 재현을 분리해 기록했다. JSON 및 각 과제의 출력 스키마는 14/14 충족했다. API의 정상 stop 종료도 14/14다.

원본 ZIP/파일을 수정하지 않았고 새 LLM 추론·모델 다운로드는 하지 않았다. 분석 재집계는 별도 작업 사본에서 만들었다. 수치와 해시는 `run_metrics.json`, 각 응답 재검사는 `v02_smoke_01/reanalysis.json`, `v02_calibration_01/reanalysis.json`에 있다.

## 2. smoke의 실제 관측

| 요청 조건 | 관측 A | 목표 D → 관측 D | 요청 M → 관측 검토 수준 | 전체 제출물 유효 | 전체 역할 준수 |
| --- | --- | --- | --- | --- | --- |
| schema_shallow_M0 | schema | 1 → 2 | 0 → 0 | 예 | 아니오: D |
| instance_deep_M0 | instance | 2 → 2 | 0 → 0 | 예 | 예 |
| instance_shallow_M0 | instance | 1 → 2 | 0 → 0 | 예 | 아니오: D |
| instance_shallow_M2 | instance | 1 → 2 | 2 → 1 | 예 | 아니오: D, M |
| instance_shallow_M1 | instance | 1 → 2 | 1 → 1 | 예 | 아니오: D |
| neutral | 혼합 표현 중 도식 오류 | 지정 없음 → 2 | 지정 없음 → 1 | 아니오: 표현 | 중립이므로 해당 없음 |

여섯 응답 모두 사실 p에서 step1로 q, step2로 g를 도출한 깊이 2 경로를 제출했다. 최종 참조 누락, 부모 참조 오류, 빈 바인딩은 이번 smoke에서 각각 0건이다. 따라서 이전의 노드 ID 혼동은 이번 기록에서 재발하지 않았다.

얕은 경로 네 조건은 모두 직접 규칙 p→g의 깊이 1을 선택해야 하지만 깊이 2를 제출했다. 이때 `role_mismatch`는 증명이 틀렸다는 뜻이 아니라, **유효한 증명이나 요청한 깊이가 아니라는 뜻**이다.

M2는 잘못된 두 번째 검토를 제출한 것이 아니라 **두 번째 검토 자체를 생략**했다. 제출한 M1 argument 검토는 유효하기 때문에 전체 제출물은 유효하다. 그러나 “argument와 acceptance_criterion 두 개”라는 M2 역할 요구를 충족하지 못했다.

중립 조건의 schema는 해당 노드가 아니라 부모 쪽 부분 증명에 머물렀다. q 노드에서 p만 바인딩하고 결론을 p의 변수로 두었고, g 노드에서도 q까지의 바인딩·절만 기록했다. 중립의 자유 선택 자체가 문제가 아니라, 선택한 도식의 의미가 해당 노드와 맞지 않았다.

### 축별 판정은 전체 역할 성공과 구분해야 한다

지시 조건 5건에서 A 요청 일치는 5/5, D는 1/5, M은 4/5다. A에는 schema 조건 한 개만 포함되므로 이를 광범위한 도식화 능력의 추정치로 확대하지 않는다.

기존 엄격 대조는 양쪽 모두 전체 역할을 충족해야 하므로 0/4다. 그러나 instance_shallow_M0와 schema_shallow_M0는 둘 다 D=2, M=0인 상태에서 A만 달라졌다. instance_shallow_M0와 instance_shallow_M1도 A=instance, D=2인 상태에서 검토 수준이 0→1로 달라졌다. **엄격 대조 0/4가 “어떤 축 변화도 없었다”는 뜻은 아니다.**

v0.3은 이 두 관측을 `descriptive_contrasts.json`으로 분리했다. 나머지 축의 요청 절대값에 실패한 사실은 유지하며, 전체 역할 성공·엄격 대조 성공 수에는 추가하지 않는다. D 대조는 두 조건 모두 깊이 2이고, M1→M2 대조는 모두 M1이어서 요청한 변화가 관측되지 않았다.

## 3. calibration 1/8을 해석할 때 중요한 구분

### 증명 선택은 맞았지만 제출 범위를 어겼다

`proof_shallow`와 `proof_deep`는 둘 다 직접 경로와 우회 경로를 한꺼번에 나열했다. shallow는 최종 노드를 n1로 선택했고 실제 선택 연결부 깊이는 1이다. deep는 n3를 선택했고 실제 깊이는 2다. 두 선택은 각각 요청과 맞는다.

하지만 shallow에는 선택한 n1과 무관한 n2·n3이 남아 있고, deep에는 선택한 n3과 무관한 n1이 남아 있다. 기존 검증기는 `GRAPH: 최종 증명과 무관한 노드`로 두 기록을 거부한다. 이는 원래 “증명 하나만 제출” 계약에 맞는 실패 판정이다.

기존 로그의 `requested_depth=false`는 전체 증명의 유효성을 전제로 한 결합 검사 결과다. 이 값만으로 “모델이 깊이를 잘못 선택했다”고 해석해서는 안 된다. v0.3은 선택 연결부 깊이와 전체 제출 범위 오류를 함께 보여주되, 원문을 잘라서 성공으로 바꾸지 않는다.

### 유효·무효 논증 구별은 실패했다

유효 증명 검토에서는 `support_valid=true, goal_match=true, proof_and_goal_accepts=true`로 맞게 답했다. 부모 참조를 제거한 손상 증명에서도 같은 세 값을 제출했다. 후자의 정답은 `false, true, false`다. 노드 ID는 모두 열거했지만 실제 지지 결함을 발견하지 못했다.

### 세 기준 비교 과제에서 같은 판정값을 반복했다

세 과제의 실제 모델 출력은 모두 아래 순서에서 `(true, false, false)`였다.

| 과제 | 항목 순서: answer_only / proof_and_goal / gap | 정답 |
| --- | --- | --- |
| unsupported_goal | true / false / false | true / false / true |
| non_goal_fact | true / false / false | false / false / false |
| supported_goal | true / false / false | true / true / false |

unsupported_goal에서는 두 수락 기준의 판정 자체는 맞게 구분했지만, true와 false가 다르다는 gap을 false로 냈다. non_goal_fact에서는 목표가 아닌 사실을 정답 일치로 받아들였다. supported_goal에서는 목표가 원문 facts에 추가되어 있는데도 단독 사실 증명을 거부했다.

이는 단순 JSON 문법 문제가 아니라 이 프롬프트 조건에서의 의미 판정 오류다. 다만 여섯 통합 증명을 올바르게 구성한 관측과 함께 봐야 하므로 “모델이 규칙을 전혀 이해하지 못한다”는 결론은 맞지 않는다.

### 기존 콘솔 표시의 의미도 명확하지 않았다

v0.2가 출력한 `교정 과제 불일치: {...}`의 true/false는 모델의 실제 판정값이 아니라 **기대값과 일치했는가**였다. 예를 들어 `criterion_non_goal_fact`의 `proof_and_goal_accepts: true`는 모델이 true라고 답했다는 뜻이 아니다. 모델은 false라고 답했고 정답도 false라 일치했다는 뜻이다.

v0.3은 불일치 필드 이름과 `actual / expected / matches`를 구분한다. `v02_calibration_01/task_comparisons.json`에 전체 값을 기록했다.

## 4. 관찰, 원인 후보, 현재 결론

**확인된 코드 문제:** v0.2의 게이트가 정상 실험 응답의 의미·역할 실패까지 다음 단계 차단 사유로 삼았다. 또 첫 화면의 결합 불리언과 엄격 대조만으로는 부분적으로 올바른 수행이 가려질 수 있었다. 이 둘은 소스와 기록으로 직접 확인했다.

**확인된 프롬프트 구성:** v0.2는 사례·얕은 경로·M0 예시와 도식·깊은 경로·M2 예시 두 개를 묶어 제공했고, 후자가 뒤에 있었다. calibration에는 같은 완성 예시가 없었다. 따라서 분리 진단이 통합보다 단순해 보인다는 이유만으로 같은 보조 정보를 받은 더 쉬운 과제라고 가정할 수 없다.

**아직 분리되지 않은 원인:** 통합 출력이 깊이 2에 고정된 데에는 예시 모방·지시의 현저성·복합 계약 처리·현재 모델과 non-thinking 설정의 영향 등이 가능하다. 이번 관측만으로 마지막 예시가 원인이라거나 작은 모델의 크기만이 원인이라고 특정하지 않는다. 캐시가 다른 요청을 잘못 재사용했다는 증거도 없다.

**현재 조치:** 먼저 동일 프롬프트와 모델로 기존 39조건을 실행할 수 있게 게이트를 수정한다. 실패도 그대로 수집해 세 문제와 전체 역할 조합에서 양상이 유지되는지 본다. 원문 계약을 더 명시하고 구성요소 예시를 분리한 `explicit-v3`도 선택형 비교 조건으로 제공하지만 기본 실험에는 섞지 않는다. 이 프로필의 정확도 개선은 아직 측정하지 않았다.

## 5. 하드웨어와 실행 상태

로그의 환경은 RTX 4060, 전용 메모리 8188 MiB, Ollama 0.34.0, qwen3:4b Q4_K_M이다. 정상 종료 14/14이고 통신 실패·출력 길이 종료는 없다. 두 실행의 API 경과 시간 합계는 약 41.24초, 출력은 합계 2,754토큰이다.

따라서 이번 차단과 관측 오류를 RAM/VRAM 부족 탓으로 돌릴 근거는 없다. 새 GPU·더 큰 모델·Thinking 활성화를 이번 수정의 필수 전제로 만들지 않았다. `/api/ps`의 적재 정보는 최대 GPU 사용량을 측정한 것이 아니며, 이는 별도의 성능 벤치마크가 아니다.

## 6. 수정의 범위와 다음 실행

기본 `legacy-v2`의 기존 14개 요청을 재생성해 요청 바이트가 모두 같은지 시험했다. 기존 검증기의 전체 성공/실패 기준과 각 축의 목표값은 바꾸지 않았다. v0.2 smoke를 새 readiness 게이트로 실제 오프라인 재검사한 결과는 `gate_replay.json`에 있다: 준비 통과, 6건 재검사, 5건 실패 보존.

폴더 교체 후 다음을 실행한다:

```powershell
py -3 -m local_llm selfcheck
py -3 -m local_llm run --profile pilot --gate results_llm/v02_smoke_01 --out results_llm/v03_pilot_01
```

같은 모델·서버·설정이 유지되면 기존 calibration/smoke를 재실행할 필요가 없다. 39조건의 모델 실패가 있더라도 다음 조건을 계속 수집한다. 기술적 오류·중단은 별도 처리하며, 완료 여부와 성능 PASS/FAIL을 나눠 기록한다.

수정본 오프라인 시험과 최종 패키지 검사는 `local_llm/BUILD_STATUS.json` 및 `local_llm/validation/`에서 확인한다. 새 LLM 추론, 새 pilot, Windows 실행은 여기서 수행하지 않았다.
