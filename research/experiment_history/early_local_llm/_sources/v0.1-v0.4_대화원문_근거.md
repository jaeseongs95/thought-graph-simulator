## 무엇을 구현했는가

기존 연구자료의 **“문제와 목표를 고정하고 A/D/M 역할을 바꾸어 비교한다”**는 실험 방향을 이어서 구현했습니다. fileciteturn6file0

기존에는 `simulate()`가 규칙에 따라 증명 경로를 만들어 줬지만, 이번에는 **경로·표현 도식·검토 기록을 LLM이 직접 생성**합니다. 판정에는 기존 `adm_minimal.py`의 `verify()`를 사용합니다. 기존 검증기는 실제 지지 관계와 표현·검토 내용을 원문 문제에 대조하는 구조입니다. fileciteturn2file0turn3file0

```text id="l6grby"
같은 문제·사실·규칙·목표
    → A/D/M 역할 지시
    → 로컬 LLM이 증명 기록 생성
    → 기존 검증기로 재검사
    → 요청 역할과 실제 관측값 비교
    → 실패·토큰·시간·원문 응답 저장
```

A는 **사례 표현 / 보편 도식**, D는 **실제 지지 그래프의 의존 깊이**, M은 **문제 도출 / 논증 검토 / 평가 기준 검토**로 유지했습니다.

**모델이 잘못 만든 근거를 코드가 대신 채우지 않습니다.** 목표 문자열만 맞는 답, 잘못된 도식, 거짓 검토 결과, 요청한 역할을 따르지 않은 출력은 구분해서 기록합니다. 성공한 출력만 골라 집계하지 않으며, 중단 후 이어서 실행할 때도 완료된 실패 조건을 다시 뽑지 않도록 했습니다.

## PC 사양에 맞춘 기본 설정

시작 모델은 **Ollama의 `qwen3:4b`**입니다. 공식 라이브러리 기준 약 4.02B 파라미터, Q4_K_M 양자화, 모델 파일 약 2.5GB입니다. ([ollama.com](https://ollama.com/library/qwen3%3A4b)) Ollama는 Windows에서 NVIDIA GPU를 지원하며, RTX 4060도 지원 목록에 있습니다. ([docs.ollama.com](https://docs.ollama.com/windows))

소스의 기본 설정은 **문맥 8,192토큰, 호출당 최대 출력 4,096토큰, 동시 요청 1개, CPU 스레드 6개, Thinking 비활성**입니다. Python 부분은 표준 라이브러리만 사용하며, 모델 실행은 별도로 설치하는 Ollama가 담당합니다.

실행 시 모델 식별 해시와 환경을 저장하고, API가 반환하는 입력·출력 토큰 수와 처리 시간을 기록하도록 했습니다. 해당 필드는 Ollama Chat API에서 제공합니다. ([docs.ollama.com](https://docs.ollama.com/api/chat))

## 실행 방법

ZIP에서 나온 **`local_llm` 폴더를 기존 `adm_minimal.py` 옆에 복사**합니다. ZIP에는 기존 프로젝트 파일과 모델 가중치는 포함하지 않았습니다.

```text id="irjyy5"
thought-graph-simulator/
├─ adm_minimal.py
├─ examples/
│  └─ problems.json
└─ local_llm/          ← 이번 소스 폴더
```

Python 3.10 이상과 Windows용 Ollama를 설치한 뒤, **프로젝트 루트에서 PowerShell을 열어** 진행합니다.

### 1. 로컬 서버 시작

Ollama 트레이 앱이 이미 실행 중이면 **Quit으로 종료한 뒤** 실행합니다.

```powershell id="rqm682"
powershell -NoProfile -ExecutionPolicy Bypass -File .\local_llm\windows\serve-local.ps1
```

이 창은 열어 둡니다.

### 2. 두 번째 PowerShell에서 모델 준비와 첫 점검

두 번째 창도 프로젝트 루트에서 엽니다.

```powershell id="2ksz6n"
# 최초 모델 다운로드
ollama pull qwen3:4b

# 설치·모델·GPU 정보 확인 — 추론하지 않음
py -3 -m local_llm doctor

# 첫 실제 실험 — 6회 호출
py -3 -m local_llm run --profile smoke --out results_llm/smoke_01
```

### 3. 전체 조건 실행

기본 문제 파일을 사용할 때의 **실행 계획**은 다음과 같습니다.

| 모드 | 구성 | LLM 호출 수 |
|---|---|---:|
| `smoke` | 첫 문제에서 연결·출력 형식·최소 대조 확인 | 6회 |
| `pilot` | 3개 문제 × 중립 포함 13조건 | 39회 |
| `full` | `pilot` 구성을 세 시드로 반복 | 117회 |

전체 조건을 한 번씩 실행하는 명령입니다.

```powershell id="dz6myh"
py -3 -m local_llm run --profile pilot --out results_llm/pilot_01
```

결과는 **`results_llm/pilot_01/summary.md`**부터 보면 됩니다. 조건별 지표는 `metrics.csv`, 축별 비교는 `contrasts.json`, 실제 요청·응답·증명 기록은 `cases/`에 저장됩니다.

오프라인 단위시험 **39개도 소스에 포함**했습니다. 실행 명령과 실패 유형 해석, 중단 후 재개 방법은 함께 제공한 [실행 안내](sandbox:/mnt/data/thought_graph_local_llm_source/local_llm/README.ko.md)에 정리했습니다.

### 가장 큰 문제: 명제와 노드 ID를 혼동했습니다

실제 응답 중에는 다음과 같은 노드가 있습니다.

```json
{"id": "step2", "atom": "g"}
```

그런데 최종 노드 지정은 다음처럼 했습니다.

```json
"final": "g"
```

여기서 `g`는 **목표 명제**이고, `step2`는 **그 명제를 담은 노드의 ID**입니다. 검증기는 노드 ID를 요구하므로 이 출력을 거부하는 것이 맞습니다.

pilot 39건 중 34건은 `final`에 목표 명제 `g`를, 나머지 5건은 `chain_2` 또는 `chain_3`라는 **문제 ID**를 넣었습니다. 부모 참조에서도 명제 이름과 노드 ID를 혼동한 응답이 있었습니다.

### 그렇다고 ID만 고치면 끝나는 것도 아닙니다

**28건에서 개별 규칙 적용이 맞았다는 점은 의미가 있습니다.** 모델이 규칙 적용을 전혀 못 한 것은 아닙니다.

다만 가능한 모든 규칙과 대안 경로를 함께 나열한 출력도 있었습니다. 이번 실험은 “도출 가능한 내용을 전부 나열하라”가 아니라 **“요청한 역할에 맞는 증명 하나를 선택하고, 그 증명에 필요한 지지 관계를 작성하라”**는 과제입니다. 개별 단계가 맞더라도 선택된 최종 증명과 관계없는 노드가 섞이면 전체 증명은 실패합니다.

도식과 검토에도 별도 문제가 있었습니다. schema를 지정한 18조건 모두에서 모든 노드를 도식으로 표현하지 못했고, 일부 M2 응답은 목표 문자열이 같은데도 `answer_only_accepts=false`라고 판정했습니다. **참조 형식뿐 아니라 도식화와 기준 검토의 수행도 따로 확인해야 합니다.** 구체적인 응답 사례는 [상세 분석](sandbox:/mnt/data/thought_graph_local_llm_v02/analysis/RESULT_ANALYSIS.ko.md)에 넣었습니다.

## 2. 제가 만든 v0.1에서 수정해야 했던 부분

**부족했던 전제는 “소형 모델이 복잡한 증명·도식·검토 계약을 처음부터 한 번에 수행할 수 있다”는 것을 충분히 확인하지 않고 본 실험에 투입한 것입니다.**

기존 검증기는 잘못된 출력을 제대로 거부했습니다. 문제는 그 앞단의 계약 전달과, 실패했을 때 어느 구성요소에서 막혔는지 분리하는 절차였습니다.

| 문제 | v0.2 수정 |
|---|---|
| `id`, `atom`, `rule`, `final`의 구분이 불명확함 | `node_id`, `parent_node_ids`, `selected_final_node_id`로 명시 |
| 실제 HTTP 전송에서 키가 정렬되어 `final`이 `nodes`보다 먼저 전달됨 | 해시용 직렬화와 전송용 직렬화를 분리하고 실제 전송 원문 저장 |
| 동적 키를 사용하는 도식 바인딩과 빈 객체 출력 | 고정 필드의 `bindings` 배열로 변경하고 빈 값·중복을 검사 |
| 증명·도식·검토를 처음부터 함께 요구함 | **8회 구성요소별 진단**을 추가하고 통합 실험과 별도 집계 |
| 최초 오류만 보여 후속 문제가 가려짐 | 원문에서 확인 가능한 오류를 함께 기록하고 A/M의 평가 가능 여부도 구분 |

전송 순서 문제는 **코드에서 확인된 사실**입니다. 다만 이것이 실패 전체의 단독 원인이라고 확정하지는 않았습니다. 이번 수정에서는 참조 명칭·순서·표현 형식을 함께 개선하고, 실제 효과는 새 실행으로 확인하도록 했습니다.

공통 형식 예시도 추가했습니다. 따라서 v0.2는 **예시를 제공한 조건의 실험**이며, v0.1과 같은 조건의 단순 반복으로 합산하지 않습니다.

### 가장 뚜렷한 현상은 ‘깊이 2 경로로 고정’입니다

문제에는 다음 두 경로가 있습니다.

```text
얕은 경로: p → g          깊이 1
깊은 경로: p → q → g      깊이 2
```

**여섯 응답 모두 두 번째 경로를 제출했습니다.** 따라서 `instance_deep_M0`의 통과만으로 깊이 조절에 성공했다고 볼 수는 없습니다. 얕게 요청해도 같은 깊은 경로를 선택했기 때문입니다.

반면, 요청에 따라 instance와 schema 표현을 바꾸거나 M0에서 M1 검토를 추가한 변화는 실제로 관측됐습니다. **A와 M0→M1의 변화는 일부 반영됐지만, D의 분리와 M2 수행은 되지 않은 결과**입니다.

M2에서는 두 번째 검토의 판정을 틀린 것이 아니라, **수락 기준 검토 자체를 빠뜨리고 M1 검토 하나만 제출**했습니다. 중립 조건은 증명은 맞았지만 도식에 현재 노드까지 반영하지 않아 실패했습니다. [조건별 분석](sandbox:/mnt/data/thought_graph_local_llm_v03/analysis/RESULT_ANALYSIS.ko.md)

## 2. calibration의 실패도 구분해서 봐야 합니다

### 깊이를 잘못 선택한 것이 아니라, 선택하지 않은 경로까지 남겼습니다

`proof_shallow`와 `proof_deep`의 실제 출력은 직접 경로와 우회 경로를 **둘 다 나열**했습니다. 그런데 최종 노드 선택은 다음처럼 달랐습니다.

| 과제 | 선택한 최종 노드의 실제 깊이 | 요청과 일치 | 전체 증명이 실패한 이유 |
|---|---:|---|---|
| `proof_shallow` | **1** | 예 | 선택한 증명과 무관한 우회 경로를 남김 |
| `proof_deep` | **2** | 예 | 선택한 증명과 무관한 직접 경로를 남김 |

즉, **분리 진단에서는 얕음·깊음에 맞는 최종 노드를 선택했습니다.** 다만 이번 출력 계약은 “선택한 증명 하나와 그 근거만 제출”이므로, 다른 경로까지 남긴 전체 기록은 실패가 맞습니다.

기존 로그의 `requested_depth: false`는 전체 증명의 유효성까지 전제로 묶은 검사 결과라서, 이것만 보면 깊이 선택 자체가 틀린 것으로 오해하기 쉽습니다. 수정본은 **선택한 부분의 깊이와 전체 제출 범위 오류를 따로 표시**합니다. 불필요한 노드를 코드가 삭제해 성공으로 만드는 방식은 사용하지 않았습니다. [진단 상세](sandbox:/mnt/data/thought_graph_local_llm_v03/analysis/v02_calibration_01/task_comparisons.json)

### 검토와 기준 비교에는 실제 의미 판정 오류가 있습니다

손상된 증명에서도 모델은 `support_valid=true`라고 답했습니다. 노드 ID를 모두 나열했지만 부모 참조가 빠진 결함을 발견하지 못했습니다.

또한 세 가지 기준 비교 과제에서는 입력 조건이 달라졌는데도 모두 다음 판정을 반복했습니다.

```text
answer_only_accepts      = true
proof_and_goal_accepts    = false
gap_detected             = false
```

특히 첫 과제에서는 두 수락 기준을 `true`와 `false`로 다르게 판정하고도, **두 판정의 차이가 없다고 답했습니다.** 이 부분은 JSON 형식 문제가 아니라 해당 조건에서의 판단 오류입니다. [실제값·기대값 비교](sandbox:/mnt/data/thought_graph_local_llm_v03/analysis/v02_calibration_01/summary.md)

그리고 **기존 콘솔 표시도 명료하지 않았습니다.** `교정 과제 불일치: {...}` 안의 불리언은 모델이 출력한 값이 아니라 **정답과 일치했는가**였습니다. 모델과 정답이 모두 `false`이면 콘솔에는 일치 여부인 `true`가 표시될 수 있었습니다. v0.3에서는 **실제값 / 기대값 / 일치 여부**를 분리했습니다.

## 1. 가장 중요한 발견: 실제 모델과 실행 모드가 맞지 않습니다

업로드한 `manifest.json`에 다음 정보가 들어 있습니다.


**이 설치본은 일반적인 “추론 모드를 자유롭게 켜고 끄는 Qwen3”라고 가정해도 되는 모델이 아니었습니다.**

Qwen 공식 모델 카드는 **Qwen3-4B-Thinking-2507이 thinking 전용**이라고 명시합니다. Ollama의 `qwen3:4b`와 `qwen3:4b-thinking` 페이지에 표시된 모델 digest 접두부도 사용자 실행 기록과 같습니다. ([huggingface.co](https://huggingface.co/Qwen/Qwen3-4B-Thinking-2507))

> Thinking 계열 모델 + `think:false` + JSON 인증서 직접 출력

API가 이 요청을 받아 정상 종료했다는 사실과, **그 조합이 해당 모델의 성능을 평가하기에 적절한 실행 조건이라는 사실은 다릅니다.**

39개 원문 응답에는 별도 `thinking` 필드가 없고 `content`만 있습니다. 다만 기록만으로 서버 내부의 세부 처리까지 확정할 수는 없습니다. **확인된 문제는 모델의 공식 지원 형태와 다른 실행을 요청했고, 그 적합성을 사전 검사하지 않았다는 것입니다.** 이것이 실패 전체를 얼마나 설명하는지는 정상 모드와의 대조가 필요합니다.

### 이 문제는 이전 자료에도 이미 있었습니다

제가 앞서 모델 digest와 파일 일치는 확인하면서도, **그 모델의 세부 계열과 실행 모드 호환성은 확인하지 못했습니다.** 따라서 이전 답변의 “모델·설정은 그대로 두고 인터페이스부터 수정한다”는 우선순위는 바뀌어야 합니다. 사용자 설치 문제가 아니라, 제가 제공한 기본 설정과 분석에서 놓친 부분입니다. [과거 실행 메타데이터 대조](sandbox:/mnt/data/v03_review/report/prior_model_metadata.json)

| 예시 1 | instance | shallow | M0 |
| 예시 2 | schema | deep | M2 |

**세 축을 따로 조절하는 실험인데, 예시는 세 축을 동시에 바꾼 두 조합만 보여줬습니다.**

`schema + shallow`나 `instance + M2`처럼 교차된 조합은 완성 예시가 없습니다.

이 배치가 실패의 단독 원인이라고 확정할 수는 없습니다. 하지만 실제로 `instance + M2`에서 기준 검토가 자주 빠지고, schema에서는 깊은 경로를 반복하는 패턴과 부합합니다. **예시의 영향을 분리할 대조 조건이 필요합니다.**

특히 **유일하게 전체 역할까지 통과한 M2 조건**인 `chain_2/schema_deep_M2`의 출력은, 제공한 `DEMO_SCHEMA`에서 **원자명과 규칙명만 바꾼 객체와 정확히 같았습니다.**

이는 예시와의 구조적 중첩입니다. 모델이 실제로 복사했다는 내부 과정의 증거는 아니지만, **이 성공을 낯선 구조에 대한 일반화 성공으로 읽을 수는 없습니다.** [프롬프트·예시 대조](sandbox:/mnt/data/v03_review/report/EVIDENCE.ko.md)

### 문제 B. M2 정답이 모든 본 실험에서 똑같습니다

pilot의 세 문제는 모두 다음 조건입니다.

```text
목표는 g다.
g는 처음 주어진 사실이 아니다.
시험 입력은 “근거 없이 g라고 주장하기”다.
```

따라서 기준 검토의 정답은 모든 조건에서 같습니다.

```text
answer_only_accepts       true
proof_and_goal_accepts    false
gap_detected              true
```

예시에도 같은 답이 있습니다.

그러면 이 pilot만으로는 다음을 구별하기 어렵습니다.

> 실제 조건을 검토해서 답을 계산했는가?  
> 아니면 예시의 판정 패턴을 재현했는가?

**검증기가 판정 내용이 맞는지 검사하는 것과, 실험이 검토 능력을 충분히 구별해 측정하는 것은 다른 문제입니다.**

유효한 증명, 무효한 증명, 목표가 아닌 사실, 목표가 이미 사실인 경우처럼 **정답이 달라지는 분리 진단**이 필요합니다. 앞서 calibration을 별도로 둔 방향은 맞지만, 정상적인 모델 실행 조건에서 그 진단부터 확인해야 합니다.

### 문제 C. A/D 조작에 복잡한 JSON 작성 부담도 함께 들어갑니다

schema 방식은 각 노드마다 **그 노드와 모든 지지 조상의 사실·규칙·변수 대응을 다시 작성**하게 되어 있습니다.

깊이가 길어질수록 같은 근거를 여러 노드에서 반복해서 기술해야 합니다. 따라서 현재 비교에는 다음이 함께 섞입니다.

> 표현 수준·경로 깊이의 변화  
> + 누적 정보 추적과 JSON 작성 부담의 변화

모든 조건에 같은 토큰 상한을 적용했다고 해서 과제 부담까지 같아지는 것은 아닙니다.

다만 이번 응답은 모두 정상 `stop`으로 끝났고, 최대 출력은 **1,170토큰**이었습니다. 설정된 4,096토큰 상한에 잘린 결과는 아닙니다. 따라서 이번 실패를 **출력 길이 부족**으로 설명할 근거는 없습니다. [재계산 기록](sandbox:/mnt/data/v03_review/report/replay_and_independent_checks.json)

### 문제 D. ‘평가하지 못함’이 일반적인 실패와 섞여 있습니다

이 부분은 구체적인 진단 코드 문제입니다.

전체 그래프에 무관한 노드가 있으면, 기존 코드는 표현·검토를 평가 불가로 표시합니다. 그런데 축별 `role_matches`는 `false`로 만들고, 요약의 `missing_or_not_assessable`은 `None`인 경우만 셉니다.

그 결과 **평가 불가인 지시 조건 5건이 있는데도, 요약에는 A/D/M 모두 평가 불가 0건으로 표시됩니다.**

**전체 성공 수 12/36은 맞습니다.** 고쳐야 하는 것은 성공 기준이 아니라, 다음을 구분하는 진단입니다.

```text
요구를 실제로 어겼다.
다른 전제의 실패 때문에 이 항목은 평가하지 못했다.
선택된 연결 부분만 보면 이 항목은 맞았다.
```

이 구분이 없으면 “증명 외 노드 하나를 남긴 오류”가 A/D/M 전체 능력 실패처럼 보입니다. [코드 경로와 집계 문제](sandbox:/mnt/data/v03_review/report/EVIDENCE.ko.md)

## 4. 세 가지 제3자 관점에서의 의견

아래는 **서로 다른 심사 기준을 적용해 구성한 세 관점**입니다. 별도 에이전트나 외부 심사자 세 명이 실제로 검토했다는 의미는 아닙니다.

### 관점 1 — 추론 런타임·검증기 감사

**의견: “성능을 논하기 전에 실행 전제부터 정상화해야 한다.”**

모델·파일·요청의 일관성은 잘 보존됐습니다. 원문 판정도 재현됩니다. 그러나 **그 모델이 어떤 실행 모드를 전제로 하는지를 검사하지 않았습니다.** 셀프체크가 통과해도 이 조건은 보장되지 않습니다.

이 관점에서는 수정 우선순위가 명확합니다. **모델 계열과 모드 호환성을 검사하고, 평가 불가 처리도 고쳐야 합니다.** 반면 증명·도식 검증 조건을 느슨하게 할 이유는 없습니다.

### 관점 2 — 실험 설계·측정 타당성 심사

**의견: “설정을 고쳐 성공률이 올라도, 그것만으로 연구 검증이 충분해지는 것은 아니다.”**

두 예시에 A/D/M이 묶여 있고, 유일한 완전한 M2 성공은 예시와 구조적으로 같으며, 모든 M2 정답이 같은 패턴입니다. 문제 구조도 세 개뿐이고 반복 시드는 하나입니다.

따라서 **출력 형식을 따라 하는 능력과 실제 경로 선택·도식 일반화·오류 검토 능력을 더 분리해야 합니다.**

현재 최소 실험 자체를 버릴 필요는 없습니다. 다만 **형식 인증서 생성 시험이라는 범위를 넘어서 해석하려면**, 예시 배치 대조와 새로운 문제 구조가 필요합니다.

### 관점 3 — 모델 행동·실패 원인 분석

**의견: “기본 도출 능력보다, 지시에 따른 선택과 구성요소 유지에서 실패가 집중된다.”**

선택된 지지 연결 부분은 39/39 유효합니다. 반면 얕은 경로 요청은 2/18만 반영됐고, 특정 네 지시에는 완전히 같은 응답을 냈으며, 복합 문제의 schema 조건은 모두 틀렸습니다.

이 관점에서는 **“4B니까 못 한다”는 결론도, “JSON 형식만 바꾸면 된다”는 결론도 데이터와 맞지 않습니다.**

모드 호환성을 먼저 정리한 뒤에도 같은 패턴이 남는지 확인하고, 예시 의존·구성요소 결합 부담·모델 용량의 영향을 구분해야 합니다.

## 5. 세 관점을 맞붙이면 결론은 어떻게 나오는가?

### 쟁점 1. “설정만 고치면 해결되는가?”

**런타임 관점:** 지금 조합은 정상적인 성능 기준선으로 삼기 전에 적합성 확인이 필요하다.

**실험 설계 관점의 반론:** 맞지만, 설정을 고쳐도 M2 정답이 항상 같으면 검토 능력을 충분히 측정하지 못한다.

**모델 행동 관점의 보완:** 실제로 드러난 깊이 선택·도식 누락 패턴이 개선되는지도 따로 확인해야 한다.

**판단:** 설정 정상화는 **선행 조건**이지 **충분조건**은 아닙니다.

### 쟁점 2. “검증기가 지나치게 엄격해서 실패한 것 아닌가?”

**모델 행동 관점:** 무관한 노드가 붙은 6건도 선택된 증명은 맞으므로, 논리적 도출 능력에 관한 정보는 남겨야 한다.

**검증기 관점의 반론:** “선택한 증명과 그 근거만 제출하라”는 명시 계약을 어겼으므로 전체 실패 판정은 맞다.

**실험 설계 관점의 조정:** 두 평가 대상을 분리하면 충돌하지 않는다.

**판단:** **전체 제출물의 실패는 유지하되, 선택된 증명의 유효성은 별도 진단으로 보존**해야 합니다. 불필요한 노드를 코드가 몰래 지워 성공률을 높이는 것은 수정이 아닙니다.

### 쟁점 3. “작은 모델의 한계인가, 프롬프트 문제인가?”

**모델 행동 관점:** 용량 한계는 가능한 원인이다. 그러나 일부 얕은 경로 선택과 제출된 M2 판정은 맞았으므로 전면적인 수행 불가능은 아니다.

**실험 설계 관점의 반론:** 예시 배치와 누적 작성 부담의 영향이 분리되지 않았다.

**런타임 관점의 추가 반론:** 실행 모드 적합성도 아직 확인되지 않았다.

**판단:** 현재 자료로 단일 원인을 확정할 수는 없습니다. 반면 **현재 모델·모드·프롬프트 조합이 역할을 안정적으로 따르지 못했다는 관측은 명확합니다.**

## 6. 최종 결론과 수정 우선순위

**이번 실패를 사용자 PC 사양이나 이론 자체의 실패로 돌릴 근거는 없습니다. 우선 고쳐야 할 것은 제가 만든 실험의 실행 전제와 원인 분리 방식입니다.**

수정 순서는 다음이 타당합니다.

**첫째, 모델과 실행 모드를 맞춥니다.** 비추론 방식의 인증서 생성이 목적이면 명시적인 Instruct 계열을 사용하고, 현재 Thinking 계열을 평가하려면 지원되는 thinking 실행과 최종 응답 분리를 확인해야 합니다. Ollama에는 별도 `qwen3:4b-instruct` 태그가 있고, Qwen은 해당 Instruct-2507 모델을 non-thinking 전용으로 설명합니다. **Instruct와 Thinking은 다른 체크포인트이므로, 교체 결과를 같은 모델의 단순 on/off 비교로 취급하면 안 됩니다.** ([ollama.com](https://ollama.com/library/qwen3%3A4b-instruct))

**둘째, 한 번에 모든 것을 요구하기 전에 구성요소를 분리해 확인합니다.** 최소 증명 선택, 고정 증명의 도식 변환, 유효·무효 증명의 검토, 정답이 달라지는 기준 판정을 각각 검사해야 합니다. 모델이 해야 할 판단을 코드가 대신 완성해서는 안 됩니다.

**셋째, 예시와 평가 문제의 중첩을 줄이고 진단 지표를 고칩니다.** 축 조합을 교차 배치하고, 종단 간 실패·실제 역할 불일치·평가 불가를 분리해야 합니다. 기존 39건은 원래 조건의 결과로 보존하고 새 조건과 섞지 않습니다.

**핵심은 “검증기를 통과하게 만들기”가 아니라, “실패가 모델의 어떤 수행에서 발생했는지 구별할 수 있게 만들기”입니다. 이번 분석에서는 그 앞단인 모델·실행 모드 전제부터 확인되지 않았다는 점이 가장 큰 누락이었습니다.**

## 1. 가장 먼저 모델과 실행 모드를 맞췄습니다

기본 모델을 **`qwen3:4b-instruct`**로 변경했습니다. Qwen 공식 문서는 Instruct-2507을 non-thinking 전용, Thinking-2507을 thinking 전용으로 구분합니다. 이전처럼 실제 체크포인트를 확인하지 않고 `think:false`를 일괄 적용하지 않습니다. ([huggingface.co](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507))

새 소스는 **모델 이름이 아니라 실제 GGUF 메타데이터를 검사**합니다.

| 확인된 모델 | 새 실행 방식 |
|---|---|
| Instruct-2507 | `think` 필드를 보내지 않고 최종 응답 생성 |
| Thinking-2507 | `think:true`로 요청하고 사고·최종 응답 채널을 별도로 확인 |
| 모델과 요청 모드가 불일치 | **추론 전에 중단** |
| 모델 계열을 식별할 수 없거나 메타데이터가 모순됨 | 추측해서 진행하지 않고 원인을 표시 |

Thinking 응답은 Ollama의 별도 `message.thinking`과 최종 `message.content`를 구분해서 처리합니다. 사고 영역에서 JSON을 찾아 최종 답으로 사용하는 자동 복구는 하지 않습니다. ([docs.ollama.com](https://docs.ollama.com/capabilities/thinking))

기존에 설치한 Thinking 모델도 명시적으로 선택할 수 있도록 남겼습니다. 다만 기본 실행은 **명확한 non-thinking 체크포인트로 새로운 기준선을 확보하는 방식**입니다. 모델 정책과 실제 이전 메타데이터의 차단 시험은 [검사 기록](sandbox:/mnt/data/thought_graph_local_llm_v04/local_llm/validation/model_policy_actual_v03.json)에 있습니다.

## 2. 프롬프트와 측정 방식도 함께 수정했습니다

모델만 바꾸면 예시 의존이나 측정상의 문제는 남으므로, 다음 부분도 변경했습니다. [전체 수정 내역](sandbox:/mnt/data/thought_graph_local_llm_v04/local_llm/CHANGES.ko.md)

| 이전에 확인한 문제 | v0.4 변경 |
|---|---|
| `instance + shallow + M0`, `schema + deep + M2`로 묶인 예시 | **증명 선택·표현·검토 예시를 구성요소별로 분리** |
| 예시와 유사한 구조에서의 성공을 일반화와 구분하기 어려움 | 합류·공유 조상·순환 후보 등을 포함한 **새 문제 구조 3종** 추가 |
| 기준 검토 정답이 항상 같은 패턴 | **정답 패턴이 달라지는 기준 비교 진단 6회** 추가 |
| 도식의 의미 오류와 반복 작성 부담이 섞임 | 같은 증명을 **전체 노드 도식화 / 최종 노드만 도식화**로 나눠 비교 |
| 평가 불가가 역할 불일치로 집계됨 | **일치 / 불일치 / 평가 불가**로 분리 |
| 실패하면 다음 실험이 막히는 문제 | 의미적 실패는 계속 수집하고, 모델·모드·통신 문제만 별도로 중단 |

예시의 영향을 따로 볼 수 있도록 **동일한 지시에서 공통 예시만 제거하는 `definitions-v4` 대조 조건**도 넣었습니다.

또한 기존 통합 실험의 M2 계약은 유지했습니다. 따라서 **본 실험의 M2 정답 패턴이 동일하다는 한계는 보고서에 표시**하고, 다양한 기준 판정 능력은 별도 진단에서 확인하도록 했습니다. 분리 진단의 성공을 통합 실험의 성공률에 합산하지 않습니다. [실험 계약·해석 범위](sandbox:/mnt/data/thought_graph_local_llm_v04/local_llm/PROTOCOL.ko.md)

## 3. 사전 진단은 24회로 바꿨습니다

이제 다음 작업을 분리해서 측정합니다.

| 진단 | 호출 수 | 확인할 내용 |
|---|---:|---|
| 증명만 생성 | 6회 | 얕은 경로와 깊은 경로를 선택하고 필요한 근거만 제출하는가 |
| 고정 증명의 전체 노드 도식화 | 3회 | 전체 지지 관계를 도식으로 보존하는가 |
| 같은 증명의 최종 노드만 도식화 | 3회 | 반복 작성 범위를 줄였을 때 최종 도식은 정확한가 |
| 고정 기록의 논증 검토 | 6회 | 유효·무효 근거와 제출 범위 오류를 구별하는가 |
| 수락 기준 비교 | 6회 | 입력에 따라 서로 다른 판정을 내리는가 |

`calibrate`는 모델을 학습하거나 수정하는 명령이 아닙니다. **실패 지점을 나눠 확인하는 진단**입니다.

결과에는 `모델 실제값 / 기대값 / 일치 여부`를 따로 기록합니다. 전체 도식과 최종 도식 단독 과제의 결과·비용도 짝지어 저장합니다. [24회 진단 계획](sandbox:/mnt/data/thought_graph_local_llm_v04/local_llm/validation/plan_calibration.json)

## 4. 교체하고 실행하는 방법

기존 `local_llm` 폴더를 다른 이름으로 보관하고, ZIP 안의 **새 `local_llm` 폴더로 교체**합니다. 단순 덮어쓰기보다 폴더 교체가 적절합니다.

```text
thought-graph-simulator/
├─ adm_minimal.py          ← 기존 파일 유지
├─ examples/              ← 기존 파일 유지
├─ results_llm/           ← 기존 결과 유지
└─ local_llm/             ← 이번 폴더로 교체
```

Ollama와 Python을 다시 설치할 필요는 없습니다. **Ollama가 실행 중인 상태에서 프로젝트 루트의 PowerShell**에 입력합니다.

### 모델 준비와 실행 전제 확인

```powershell
# 새 기본 모델 다운로드 — 최초 한 번
ollama pull qwen3:4b-instruct

# 코드 자체 검사 — 모델 호출 없음
py -3 -m local_llm selfcheck

# 실제 모델 메타데이터·모드 확인 — 추론 없음
py -3 -m local_llm doctor
```

`doctor`에서 모델·모드 오류가 없다면 다음 단계로 진행합니다.

### 분리 진단 → smoke → pilot

```powershell
# 구성요소별 진단 — 24회
py -3 -m local_llm calibrate --out results_llm/v04_calibration_01

# 통합 최소 실험 — 6회
py -3 -m local_llm run --profile smoke --out results_llm/v04_smoke_01

# 같은 조건의 통합 본 실험 — 39회
py -3 -m local_llm run --profile pilot --gate results_llm/v04_smoke_01 --out results_llm/v04_pilot_01
```

**calibration이나 smoke에서 역할 불일치·증명 오류가 나왔다고 해서 전부 통과할 때까지 다시 돌릴 필요는 없습니다.** 해당 실패도 측정 결과입니다. 기본 게이트는 의미적 성공이 아니라 실행 준비 상태를 확인합니다.

반면 모델 모드 불일치, 통신 오류, 응답 잘림 등은 별도로 처리합니다. **예전 `v02_smoke_01`을 이번 실행의 게이트로 사용하면 안 됩니다.** 새 기본 조건과 맞지 않기 때문입니다.

각 실행 후에는 아래 파일부터 보면 됩니다.

```text
results_llm/v04_calibration_01/summary.md
results_llm/v04_calibration_01/component_diagnostics.json
results_llm/v04_smoke_01/summary.md
results_llm/v04_pilot_01/summary.md
```

기존 세 문제로 비교하는 `--suite legacy`, 기존 Thinking 모델 실행, 예시 유무 대조 명령은 [실행 안내](sandbox:/mnt/data/thought_graph_local_llm_v04/local_llm/README.ko.md)에 정리했습니다.

## 사용자 7

근데 저거 많이돌린다고 의미가 있어?

## 어시스턴트 7

많이 돌리는 것 자체가 의미 있는 건 아니다. **지금 단계에서는 반복 횟수보다 “서로 다른 실패 원인을 구별할 수 있는 조건을 얼마나 잘 구성했느냐”가 더 중요하다.**

현재 v0.4 기준으로 보면 `calibrate 24회 + smoke 6회 + pilot 39회`는 같은 걸 69번 반복하는 게 아니다. 각각 다른 구성요소와 A/D/M 조합을 보는 것이므로 **1회씩 도는 것만으로도 의미가 있다.** 우선 이걸 한 세트 돌려서 모델이 어디서 체계적으로 실패하는지 보는 게 먼저다.

반대로 같은 조건을 수십 번 반복하는 건 상황에 따라 가치가 크게 다르다.

| 상황 | 반복 실행 가치 |
|---|---|
| 같은 seed + 거의 결정적 sampling | 매우 낮음 |
| 다른 seed + stochastic sampling | 있음 |
| 같은 문제를 표현만 조금 바꿈 | 꽤 있음 |
| 완전히 새로운 문제 구조 추가 | 매우 큼 |
| 다른 모델과 동일 조건 비교 | 매우 큼 |

특히 지금처럼 우리가 보려는 게 **“A/D/M 조작이 실제 모델 동작을 분리해서 바꿀 수 있는가”**라면, 동일 문제를 100번 돌리는 것보다 이런 식이 낫다.

```text id="55l5vm"
1단계
v0.4 calibration 24회
→ 구성요소 자체를 수행할 수 있는지

2단계
pilot 39회 × 1
→ 전체 조건에서 실패 패턴 파악

3단계
중요 조건만 골라서 3~5개 seed
→ 우연인지 안정적인 경향인지 확인

4단계
새로운 문제 구조 추가
→ 예제 암기/패턴 복사가 아닌 일반화 확인

5단계
다른 모델과 동일 실험
→ 현상이 특정 모델 때문인지 구조 때문인지 확인
```

예를 들어 pilot에서 또 이런 결과가 나왔다고 하자.

```text id="rkf4fx"
shallow 요청: 2/18 성공
deep 요청: 18/18 성공
```

이 경우 곧바로 1,000번 돌릴 필요가 없다.

먼저 shallow 조건 몇 개만 골라 seed를 5개 정도 바꿔본다.

```text id="jhzl8h"
chain_2 shallow × 5
chain_3 shallow × 5
join 구조 shallow × 5
```

15회 정도면 **“우연히 한 번 깊은 경로를 고른 것인지, 강한 deep 편향이 있는 것인지”**가 훨씬 잘 보인다.

그리고 여기서도 계속 거의 같은 결과가 나오면 동일 문제 반복보다는 **새로운 그래프 문제를 10~20개 만드는 편이 연구적으로 훨씬 가치가 높다.**

### 이 연구에서는 특히 반복보다 문제 다양성이 중요하다

지금 우리가 검증하려는 가설에서 위험한 건 이런 것이다.

```text id="lzr030"
모델이 A/D/M이라는 개념을 실제로 조절함
```

이 아니라

```text id="j9wm73"
모델이 우리가 넣어준 세 가지 문제와 few-shot 패턴에 적응함
```

인데도 성공으로 착각하는 것.

그래서 나중에는 예를 들어:

```text id="hw9rxa"
chain
branch
merge
diamond
shared ancestor
irrelevant distractor
multiple valid proofs
asymmetric depth
cycle-looking but valid DAG
long shallow-vs-deep contrast
```

같이 **구조적으로 다른 문제**를 늘리는 게 같은 `chain_2`를 50번 돌리는 것보다 훨씬 중요하다.

### 반복 실행이 본격적으로 필요한 시점

논문에 이런 식의 수치를 넣고 싶을 때다.

> shallow 조건에서 목표 깊이 선택 성공률은 78%였다.

이때는 한 번씩만 실행하면 부족하다. 모델 출력은 확률적이기 때문이다.

그 단계에서는 대략:

```text id="w7btc2"
각 조건 5 seeds
39조건 × 5 = 195회
```

정도부터 꽤 쓸 만하다.

조금 더 안정적인 통계가 필요하면:

```text id="vgatdy"
39조건 × 10 seeds = 390회
```

정도로 늘릴 수 있다.

하지만 **지금 당장 390회 돌리는 건 비효율적이다.** 설계 오류가 하나 있으면 잘못된 실험을 390번 반복한 데이터만 생긴다. 우리가 v0.1~v0.3에서 실제로 경험한 게 바로 그런 종류의 문제다.

### 그래서 지금은

**v0.4를 일단 한 세트만 돌려봐.**

```powershell id="839za1"
py -3 -m local_llm calibrate --out results_llm/v04_calibration_01
py -3 -m local_llm run --profile smoke --out results_llm/v04_smoke_01
py -3 -m local_llm run --profile pilot --gate results_llm/v04_smoke_01 --out results_llm/v04_pilot_01
```

그 결과를 보고 내가 다시 분석해서,

**반복이 필요한 조건 / 새로운 문제를 추가해야 하는 조건 / 이미 결론이 충분히 나온 조건**

으로 나누는 게 맞다.

한 줄로 말하면, **지금은 N을 키울 단계가 아니라 실험이 실제로 우리가 주장하는 변수를 측정하는지 확인하는 단계다. 그게 확인된 다음에 N을 키우는 게 의미 있다.**

## 2. 원문에서 확인되는 가장 명확한 오류

calibration의 `K03` 문제에는 다음 관계가 있습니다.

```text
Ea → Eb
Eb → Ec
Eb → Ed
Ec AND Ed → Ee

별도 얕은 경로: Ea → Ee
```

여기서 `Ec`와 `Ed`는 모두 `Eb`로부터 갈라지는 결과입니다. 그런데 모델은 shallow와 deep 양쪽에서 다음과 같은 동일한 증명을 제출했습니다.

```text
n0: Ea                         정상
n1: Eb, 부모=[n0]              정상
n2: Ec, 부모=[n1]              정상

n3: Ed, 부모=[n2]              오류
    이 규칙은 Eb를 요구하지만, 실제 부모 n2는 Ec다.

n4: Ee, 부모=[n3]              오류
    이 규칙은 Ec와 Ed를 모두 요구하지만, Ed만 연결했다.
```

**분기와 합류가 있는 근거 관계를 일렬 연결로 바꾼 것입니다.** 이 출력은 검증 기준을 조금 완화한다고 올바른 증명이 되지 않습니다. 해당 규칙이 허용하지 않는 근거를 사용했기 때문입니다. 원본 core도 실제 부모의 명제를 모아 규칙의 전제와 정확히 비교하도록 구현돼 있습니다. fileciteturn12file0L210-L225

다만 이것을 **“이 모델은 AND를 전혀 처리하지 못한다”**고 확대하면 안 됩니다. 같은 calibration의 `K02 deep`에서는 합류 전제를 올바르게 연결했습니다. 현재 기록이 지지하는 결론은 **관계 추적을 안정적으로 수행하지 못했다**는 것이지, 해당 연산의 수행 가능성이 전혀 없다는 것은 아닙니다. [K03 원문과 K02 성공 사례](sandbox:/mnt/data/v04_forensic/report/v04_calibration_01_cases.json)

### 검토 기록도 실제 근거를 제대로 확인하지 않았습니다

pilot에서 제출된 argument 검토 27건은 **전부 `grounded=true`**라고 답했습니다.

그중 **26건은 검토 대상의 실제 지지 관계가 무효**였습니다. 나머지 한 건도 검토 근거 목록에 무관한 노드가 섞였습니다. 따라서 검토 항목을 작성했다는 사실만으로 실제 검증을 수행했다고 볼 수 없습니다. [검토 대상과 실제 근거 대조](sandbox:/mnt/data/v04_forensic/report/failure_patterns.json)

### JSON이 정상인데 왜 이렇게 틀릴 수 있는가

현재 출력 제약은 JSON의 구조를 제한합니다. 하지만 문법적으로 허용된 문자열을 사용해 다음처럼 **의미적으로 틀린 연결**을 만드는 것은 별도 문제입니다.

```text
“부모 노드 ID를 문자열로 작성했다.”       형식 조건 충족
“그 노드가 규칙에 필요한 명제를 담았다.”  의미 조건 충족 여부는 별도
```

Ollama의 구조화 출력도 JSON 스키마를 통한 형식 제약 기능입니다. 이번에는 형식 단계는 통과했지만, 증명 의미 검사를 통과하지 못했습니다. ([docs.ollama.com](https://docs.ollama.com/capabilities/structured-outputs))

## 6. 관점을 나눠 대립시킨 결과

먼저 수행 범위를 분명히 하겠습니다. **별도 독립 심사자·서브에이전트를 실행할 수 있는 연결 도구는 확인되지 않아, 실제로 여러 에이전트를 호출하지는 않았습니다.** 아래는 같은 분석자가 네 심사 관점의 주장과 반례를 대조한 결과입니다. 별도 알고리즘에 의한 교차검사는 했지만, 이를 여러 사람이 독립 검토한 것으로 표현하지 않습니다.

| 검토 관점 | 우선 제기한 의심 | 반박·대조 증거 | 채택한 판단 |
|---|---|---|---|
| **형식 검증기 감사** | 검증기가 정상 증명을 과도하게 거부하는가? | 실제 부모 명제가 규칙 전제와 다르며 별도 검사도 거부 | 이번 근거 연결 거부는 정당함 |
| **모델·런타임 감사** | 모델·모드·템플릿·잘림 문제가 반복됐는가? | Instruct 설정 적합, 정상 종료, 템플릿 해당 경로 일치 | 과거 모드 문제를 재적용하지 않음 |
| **모델 행동 분석** | 분기·합류와 역할 지시를 유지하지 못하는가? | 잘못된 연결·동일 응답·거짓 grounded 판정이 반복됨 | 현재 조합의 관계 추적·지시 유지 실패는 관측됨 |
| **실험 설계 감사** | 여러 요소를 동시에 바꿔 원인을 구별하지 못했는가? | v0.4에서 모델·프롬프트·문제 구조를 동시 변경 | 전후 결과만으로 단일 원인을 지정할 수 없음 |

### 실제 쟁점은 세 가지였습니다

**“검증기를 완화하면 해결되는가?”**

아닙니다. `Eb`를 요구하는 규칙에 `Ec`를 연결한 것은 명백한 오류입니다. 다만 전체 제출물의 실패와 유효한 선택 부분은 별도 진단으로 남겨야 합니다.

**“4B 모델이라서 못 하는 것인가?”**

현재 조합의 수행은 부족합니다. 그러나 합류 증명에 성공한 반례가 있고, 프롬프트·출력 제약·양자화의 영향도 분리하지 않았습니다. 따라서 **모델 크기를 단독 근본 원인으로 채택할 근거는 부족합니다.**

**“그럼 프롬프트를 다시 바꾸면 되는가?”**

그 가능성은 있지만, 또 모델·프롬프트·문제를 한꺼번에 바꾸면 원인은 계속 불명확해집니다. **제가 v0.4에서 그렇게 여러 요소를 동시에 바꾼 것은 원인 분리 관점에서 잘못된 설계였습니다.**

따라서 가장 근거가 강한 결론은 다음입니다.

> **실제 증명 오류는 유지해서 기록하고, 반례로 확인된 하네스 결함만 고친다. 모델·프롬프트·디코딩의 원인은 동일 입력의 대응 조건으로 분리한다.**

이 결론은 지지하는 관점의 수가 많아서 선택한 것이 아니라, **확인된 사실을 설명하면서 반례와도 충돌하지 않기 때문에 선택**했습니다. 상세한 주장·반박은 [관점별 검토 보고서](sandbox:/mnt/data/v04_forensic/report/ANALYSIS.ko.md)에 남겼습니다.

## 2. K03 증명: 두 프롬프트가 같은 연결을 틀렸습니다

기존 프롬프트와 간결 프롬프트의 결과를 **노드 이름과 공백을 제외하고 비교**했습니다.

| 문제 | 기존 프롬프트 | 간결 프롬프트 | 실제 증명 구조 |
|---|---|---|---|
| K01 | 성공 | 성공 | 동일 |
| K02 | 성공 | 성공 | 동일 |
| K03 | 실패 | 실패 | 동일 |

**이번 간결화는 성공 여부도, 증명 구조도 바꾸지 못했습니다.** 따라서 현재 자료에서는 “프롬프트 길이만 줄이면 해결된다”는 방향을 지지하지 않습니다. [구조 대조 결과](sandbox:/mnt/data/v041_forensic/report/proof_pairs.json)

K03의 핵심 관계는 다음과 같습니다.

```text
Ea → Eb
     ├→ Ec ─┐
     └→ Ed ─┴→ Ee
             Ec와 Ed가 모두 필요
```

그런데 두 응답 모두 다음처럼 연결했습니다.

| 생성한 명제 | 실제로 연결한 부모 명제 | 규칙이 요구하는 부모 명제 |
|---|---|---|
| `Ed` | **`Ec`** | **`Eb`** |
| `Ee` | **`Ed` 하나** | **`Ec`, `Ed` 둘 다** |

분기·합류 관계를 직렬 연결처럼 작성한 것입니다. core는 실제 부모 노드의 명제를 규칙의 전제와 대조하므로 이 두 항목을 거부하는 것이 맞습니다. fileciteturn16file0L214-L218

### 원인 위치를 복사본 변경으로 확인했습니다

원문을 보존한 상태에서 복사본에만 다음 변경을 적용했습니다.

| 복사본의 변경 | 결과 |
|---|---|
| 변경 없음 | 실패 |
| `Ed`의 부모만 수정 | 실패 |
| `Ee`의 부모만 수정 | 실패 |
| **두 부모 연결을 모두 수정** | **통과** |

두 프롬프트의 응답에서 모두 같은 결과였습니다. **거부를 발생시킨 연결 오류 두 곳을 특정한 것**입니다. 수정한 복사본을 모델의 성공으로 집계하지 않았고, 새 런타임에도 부모를 자동 보충하는 처리를 넣지 않았습니다. [변경 대조 기록](sandbox:/mnt/data/v041_forensic/report/counterfactuals.json)

다만 K02에서는 합류를 포함한 증명을 성공했습니다. 따라서 **“이 모델은 AND를 전혀 처리하지 못한다”**가 아니라, **현재 조건에서 근거 연결을 안정적으로 수행하지 못했다**는 결론이 맞습니다.

## 3. 도식: 네 규칙은 맞았지만, 시작 사실 하나를 빠뜨렸습니다

이 부분은 이전의 포괄적인 “도식 의미 오류”보다 훨씬 구체적으로 좁혀졌습니다.

`schema_K03_union`과 `schema_K03_schema_only`는 **원문 응답이 바이트 단위로 같습니다.** 두 응답 모두 원자 다섯 개의 대응, 사용한 규칙 네 개, 결론 변수를 맞췄습니다. 그런데 **최초 사실 `Ea`를 선언하는 절 하나가 없습니다.** [원문과 누락 절 대조](sandbox:/mnt/data/v041_forensic/report/v041_reaudit/task_evidence.json)

예를 들어 `x`가 `Ea`에 대응한다면 다음 절이 필요합니다.

```json
{"if": [], "then": "x"}
```

`if: []`는 내용이 비었다는 뜻이 아니라 **“추가 전제 없이 이 사실이 주어져 있다”**는 뜻입니다. core도 실제 사실을 빈 전제의 절로 포함하여, 사용된 사실·규칙 집합과 반환된 도식을 대조합니다. fileciteturn16file0L252-L272

### 단순히 형식이 까다로운 문제가 아닙니다

모델이 제출한 네 규칙만 놓고 **모든 변수를 false로 설정**하면, 네 함의는 모두 참이면서 결론은 거짓일 수 있습니다.

즉, **실제 논리 반례가 있습니다.** core의 보편 도식 검사는 이런 진리값 배정을 검사하도록 작성돼 있습니다. fileciteturn16file0L273-L279

두 정규 형식 응답의 복사본에 **빠진 최초 사실절 하나만 추가하면 통과**했습니다. 따라서 이번 실패를 “추상화가 전부 틀렸다”고 설명하면 과장입니다. 구체적인 결함은 **도식에 원래의 초기 사실을 보존하지 않은 것**입니다.

### JSON-only는 두 문제가 겹쳤습니다

JSON-only 응답은 `bindings`를 요구된 **배열**이 아니라 **객체**로 작성했고, 최초 사실절도 빠뜨렸습니다.

| 복사본의 변경 | 결과 |
|---|---|
| `bindings` 자료형만 수정 | 의미 오류로 실패 |
| 최초 사실절만 추가 | 형식 오류로 실패 |
| 두 항목 모두 수정 | 통과 |

기존 메시지는 `view가 허용된 형식과 맞지 않는다`는 수준에서 끝났지만, 수정본은 추가 진단에 **`$.node_views[0].view.bindings`의 자료형 오류**를 표시합니다. 원문을 자동으로 배열로 변환해 통과시키지는 않습니다. [형식·의미 분리 검사](sandbox:/mnt/data/v041_forensic/report/counterfactuals.json)

## 4. 기준 판정: ‘도출 가능성을 오해했다’만으로 설명되지 않습니다

세 요청의 실제 응답은 모두 다음과 같습니다.

```text
answer_only_accepts       = true
proof_and_goal_accepts    = true
gap_detected              = false
```

하지만 정답은 달라야 합니다.

| 입력 | 정확한 판정 | 모델의 판정 |
|---|---|---|
| 목표와 같지만 초기 사실은 아닌 `Cc` | **T, F, T** | T, T, F |
| 초기 사실이지만 목표와 다른 `Ca` | **F, F, F** | T, T, F |
| 목표와 같고 초기 사실에도 있는 `Cc` | **T, T, F** | T, T, F |

정의는 목표 문자열의 동일성, 초기 사실 목록의 소속 여부, 두 조건의 결합입니다. core에도 그대로 구현돼 있습니다. fileciteturn16file0L313-L320

**세 번째 성공만으로 입력을 제대로 검토했다고 판단할 수 없습니다.** 이번에는 같은 출력 패턴이 세 번째 조건의 정답과 일치한 것이기 때문입니다. 그렇다고 내부적으로 반드시 복사했다거나 캐시가 잘못 동작했다고 확정하는 것도 아닙니다. [입력·정답·실제값 비교](sandbox:/mnt/data/v041_forensic/report/criteria.json)

특히 두 번째가 중요합니다.

> `Ca`와 `Cc`는 다른데도 `answer_only_accepts=true`라고 답했습니다.

첫 번째 오류만 보면 “규칙으로 도출 가능한 목표를 초기 사실처럼 취급했다”는 가설을 세울 수 있습니다. **하지만 그 가설로는 두 번째의 문자열 동일성 오류까지 설명되지 않습니다.**

현재 출력만으로는 입력을 잘못 읽었는지, 동일성·소속 판정을 틀렸는지, 마지막 불리언 출력을 고정했는지 구별되지 않습니다. 그래서 새 소스는 모델에게 다음을 각각 작성하게 합니다.

```text
observed    : 입력에서 읽은 목표·주장·초기 사실
primitives  : 목표와 같은가 / 초기 사실에 포함되는가
finding     : 세 가지 최종 판정
```

**프로그램이 중간값을 대신 계산해 채우는 것이 아니라, 모델이 작성한 값들을 각각 검사**합니다. 이 역시 출력된 중간값의 오류 위치를 보는 진단이지, 비공개 내부 사고 과정을 확인했다는 의미는 아닙니다.

| **측정 설계** | 최종값만 받아 원인 구분이 안 되는가? | 그렇다. 입력 사본·기본 판정·최종 결합을 분리해 수집해야 한다. |
| **반증·인과 검토** | 프롬프트 간결화나 schema 종류 변경이 해결책인가? | 이번 대응 조건에서는 개선되지 않았다. 다른 요소까지 동시에 바꿔 원인을 확정해서는 안 된다. |

**가장 근거가 강한 결론은 다음입니다.**

> 기존 검증 기준은 유지한다. 실제 출력의 근거 연결·사실절 누락·입력별 판정 오류를 각각 기록한다. 상위 역할 실험을 더 반복하기 전에 기본 입력 민감도를 확인하고, 남은 요인은 동일 입력의 대응 조건으로 분리한다.

이는 여러 관점이 찬성해서 선택한 것이 아니라, **직접 반례와 성공 사례를 모두 설명하면서 확인되지 않은 원인을 덧붙이지 않는 판단**입니다. 자세한 주장·반박은 [분석 보고서](sandbox:/mnt/data/v041_forensic/report/ANALYSIS.ko.md)에 있습니다.
