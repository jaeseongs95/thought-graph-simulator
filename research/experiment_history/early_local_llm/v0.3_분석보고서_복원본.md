# v0.3 실험결과 분석보고서 복원본

> 상태: **복원본**
>
> 당시 상세 분석은 대화 원문 안에 보존돼 있으나 독립 `ANALYSIS.ko.md` 파일은 현재 Library에서 확인되지 않았다.
> 아래는 그 보존 기록의 수치와 판단만 재구성한 것이다.

## 1. 결론

v0.3은 v0.2의 과도한 smoke gate를 수정해 **실패도 끝까지 수집**하도록 만든 단계다.
39조건 pilot을 확보한 결과, 문제의 목표까지 가는 증명 자체보다
요청한 경로 선택·표현 보존·검토 구성요소 유지에서 실패가 집중됐다.

다만 사후 검토에서 실행 모델이 `Qwen3-4B-Thinking-2507`인데 요청은 `think:false`였다는
중대한 실행 전제 불일치가 확인됐다. 따라서 v0.3 성능을 정상 Qwen 4B 기준선으로 일반화하지 않는다.

중립 조건 3건은 마지막 역할 준수율의 분모에서 제외됐다.

## 3. D 관측

| 요청 | 요청에 맞는 실제 깊이 선택 |
|---|---:|
| deep | 18/18 |
| shallow | 2/18 |

따라서 모델이 얕은 경로를 전혀 생성할 수 없었던 것은 아니다.
그러나 현재 조건에서는 shallow/deep 지시에 따라 안정적으로 전환하지 못했다.

일부 서로 다른 D/M 지시 조건에서 응답 본문 자체가 동일했던 사례도 관측됐다.
이는 지시 변화가 실제 산출물에 반영되지 않은 사례이지만,
서버 캐시 오류 같은 내부 원인까지 입증하는 자료는 아니다.

## 4. A 관측

역할이 지정된 36건 모두 `view.kind`는 요청한 `instance` 또는 `universal_schema` 종류를 사용했다.

하지만 의미 정확도는 달랐다.

- 단순 `chain_2`, `chain_3` schema: 12/12 유효
- 복합 `conjunction_4` schema: 0/6 유효

즉 표현 종류 라벨을 맞추는 것과 실제 proof 의미를 schema로 보존하는 것은 별개였다.

## 5. M2 관측

M2 요청 12건 중:

- criterion review 자체를 제출: 7건
- 제출한 criterion review 판정 정확: 7/7
- criterion review를 생략하고 argument review만 제출: 5건

따라서 M2 실패를 “제출한 판정이 전부 틀렸다”고 표현하면 부정확하다.
주된 관측 중 하나는 구성요소 누락이었다.

## 6. 실험 설계상의 confound

사후 metadata 검토에서:

- 모델: `qwen3:4b`
- 실제 계열: `Thinking-2507`
- 실제 요청: `think:false`

조합이 확인됐다.

v0.1과 v0.2도 같은 계열/요청 조건이었다.
따라서 v0.1~v0.3의 결과는 보존하되,
정상적인 non-thinking Instruct 기준선과 동일한 성능 실험으로 합산하지 않는다.

또한 당시 예시는
`instance + shallow + M0`와 `schema + deep + M2`처럼 A/D/M을 묶어 제시해
축별 효과와 예시 모방을 분리하기 어려웠다.

## 7. v0.4로 넘어간 이유

v0.4에서는:

- 명시적 Instruct checkpoint 사용
- 모델 metadata와 실행 mode 사전 검사
- A/D/M 예시를 구성요소별로 분리
- 새 문제 구조 추가
- 다양한 criterion 판정 진단 추가
- 평가 불가와 역할 불일치 구분

을 적용해 새로운 기준선을 만들었다.
