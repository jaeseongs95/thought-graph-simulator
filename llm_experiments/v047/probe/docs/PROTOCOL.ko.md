# v047-R1 사전 실험 계약

## 1. 질문

같은 작은 로컬 모델, 같은 원문 지시·출력 계약·생성 설정에서 다음 세 경로의 결과가 같은 실행 배치에서도 달라지는가? 과거 실패한 `(a AND (NOT b))`와 성공한 두 경로를 모두 새로 실행한다. 과거 결과를 현재 배치의 대조군으로 대신 넣지 않는다.

| 조건 | 실제 요청 | 모델 호출 수/입력 | 관측 가능 값 |
|---|---|---:|---|
| original | `(a AND (NOT b))` | 1 | 최종 bool |
| commuted | `((NOT b) AND a)` | 1 | 최종 bool |
| pipeline | `(NOT b)` → 실제 반환값 c → `(a AND b)`의 b에 c 바인딩 | 2 | NOT bool, 실제 자식 입력, AND bool |

연결 구조는 호스트가 제공한다. 모델이 스스로 분해 그래프를 고안했다는 실험이 아니다. 진리표는 오프라인 평가에만 사용하며 LLM 요청에는 넣지 않는다.

## 2. 동결하는 것과 바꾸는 것

원본 v045/v046 manifest와 네 입력의 `request.wire.json`을 읽는다. 기존 system 문구와 스키마의 일치를 검사한 뒤 모델명·model digest·모델 정보/템플릿 해시·Ollama 버전·endpoint·옵션·think 생략 여부를 보존한다. 원본이 schema 방식이 아니거나 지원하는 v045/v046 계약과 다르면 임의로 고치지 않고 제외 사유를 기록한다.

원식/교환식은 expression만 바뀐다. 파이프라인은 expression과 두 번째 호출의 b 바인딩 및 호출 구조가 달라진다. 따라서 파이프라인 대조는 순수한 “호출 수 하나의 효과”가 아니라 하위 과제 분리·명시적 중간값 전달을 포함한 실행 구성의 대조다.

기본 실험의 생성 seed는 기존 값 그대로다. 순서 결정용 `order_seed=4701729`는 모델 sampling seed와 별개다. 입력 블록 순서는 무작위로 정하고, 각 a/b 조합에서 세 경로의 여섯 순열을 한 번씩 사용한다. 파이프라인 NOT와 AND는 연달아 실행하며 부모-자식 관계를 보존한다.

## 3. 기본 실행량

네 a/b 입력 × 6회 반복 = 24개 대응 블록이다. 각 블록에서 세 경로를 실행하므로 72개 경로 관측이 예정되어 있다. 한 블록은 1+1+2회 호출이므로 **최대 96회 새 추론**이다. 각 경로는 24개 관측, 양성 입력 `(true,false)`는 각 경로 6개 관측이다.

여섯 반복은 실행 순서를 균형 있게 배치하기 위한 공학적 선택이다. 특정 유의수준·검정력에서 가설을 확증하도록 계산한 표본 크기가 아니다. 동일한 식의 전수 입력 검사 여섯 번이지, 서로 다른 24개 논리 문제의 검사도 아니다.

NOT가 형식상 올바른 bool을 반환하면 오답이어도 그대로 자식에 전달한다. NOT에 사용할 수 있는 bool이 없으면 해당 자식은 blocked로 기록하고 파이프라인을 실패 처리한다. 이 경우 호출 수는 줄어도 할당된 비교 조건은 사라지지 않는다.

## 4. 단계별 절차

**보존:** 기존 local_llm과 과거 결과는 그대로 둔다. 새 모듈은 별도 폴더에서 실행한다. Git reset, checkout, pull, commit, push, 기존 결과 삭제는 수행하지 않는다.

**오프라인 자체 시험:** 엄격한 JSON, 진리표, 실제 원문 재생성, 데이터 연결, 오류 주입, 가짜 HTTP 서버, CLI 명령을 시험한다. 이 단계는 모델 성능 표본을 만들지 않는다.

**계획 생성:** source-root에서 적합한 v046을 우선 찾는다. 응답 정확도를 선택 기준으로 쓰지 않는다. 찾은 원문 경로와 제외 후보를 표시한다. 별도 experiments_v047 폴더에 계획을 동결한다. 기존 계획이 있으면 덮어쓰지 않는다.

**실행 전 식별:** 로컬 서버의 `/api/version`, `/api/tags`, `/api/show`를 읽고 기존 모델 digest·정보 해시·서버 버전과 일치하는지 검사한다. 불일치하면 새로운 추론으로 대조를 시작하지 않는다.

**실제 추론:** 저장한 HTTP 요청 바이트를 그대로 전송한다. original, commuted, pipeline의 순서는 동결 계획대로 진행한다. 응답을 원문 그대로 기록하고, 부모값은 형식 검사만 거쳐 전달한다. 정답 평가 결과를 다시 프롬프트에 넣거나 재시도하지 않는다.

**종료 식별:** 모델/서버 정보를 다시 읽어 변경을 검사한다. 전후 검사 일치는 기록할 수 있지만, 서버가 중간에 바뀌었다 원상복구한 일을 외부적으로 증명하거나 배제하는 시스템은 아니다. 실험 중 다른 모델 작업이나 설정 변경을 섞지 않는다.

**오프라인 감사:** 별도 동결 계획과 결과 폴더를 함께 읽어 요청 바이트·입력 조합·seed·순서·부모 해시·응답 원문을 검증한다. 기존 summary의 점수를 신뢰하지 않고 독립 파서 및 수동 진리표로 계산한다.

**해석:** 자료 수집의 완료·무결성과 모델 정확성을 별개로 본다. 유효한 자료라면 오답도 비교 결과에 포함한다. 통신 실패로 미완료인 경우 완결된 성공률·효과 차이를 계산하지 않는다.

## 5. 판정 지표

### 최종값

original·commuted·pipeline 모두 원래 입력의 `a AND NOT b`와 최종 bool을 비교한다. 형식 오류는 정답으로 처리하지 않는다. 전체 정확도, 입력별 정확한 수, 양성 조건 정확한 수, 균형 정확도, 네 입력이 모두 맞은 반복 횟수를 기록한다. 항상 false를 내는 모델은 전체 75%지만 양성 정확도 0%, 균형 정확도 50%다.

### 파이프라인 구조

파이프라인의 `trace_correct`는 다음 네 사항이 모두 맞아야 한다. 실제 NOT 반환값이 `NOT(original b)`의 정답이어야 한다. 그 원문 응답의 ID/해시와 자식 입력의 연결이 맞아야 한다. AND의 출력이 실제 공급된 a/c에 대해 맞아야 한다. 최종값이 원래 식의 정답이어야 한다.

최종값만 우연히 맞은 파이프라인은 최종값 지표에서는 맞지만 구조 지표에서는 실패다. 이 둘을 합치거나, 직접식에서 관측하지 않은 내부 중간값의 정확성을 가정하지 않는다.

### 비교

같은 seed·반복·입력 블록에서 원식과 대조식의 최종값 정답 여부를 짝지어 `둘 다 정답`, `원식만 정답`, `대조식만 정답`, `둘 다 오답`을 기록한다. seed별 차이도 별도로 제공한다. 같은 입력/seed의 반복을 독립적인 문제 표본으로 취급하는 p-value는 자동 생성하지 않는다.

### 비용

모든 실제 호출의 입력 토큰·캐시 입력 토큰·출력 토큰·서버 총시간·로딩시간·입력 처리시간·생성시간·클라이언트 경과시간을 보존한다. 파이프라인은 두 호출의 값을 더한다. 누락된 필드는 null로 두며 0으로 위장하지 않는다. warmup용 숨은 추론 호출은 없다. 처음 호출의 모델 로딩 비용도 기록한다.

`num_ctx`와 `num_predict`는 상한 설정이지 실제 사용량이 아니다. 같은 호출 수, 같은 토큰 상한, 같은 실제 토큰 수, 같은 지연시간, 같은 FLOPs는 서로 다른 비교 기준이다. 이번 실험은 관측한 비용을 보고할 뿐 동일 FLOPs 대조를 구현하지 않는다.

## 6. 미리 정한 중단·보존 규칙

실행/평가 코드가 계획 동결 후 변경되면 중단한다. 기존 결과 폴더에 대한 재실행은 거부한다. 원문 손상, 부모값 보정, 계획되지 않은 요청 변경, 식별 정보 변경은 성공으로 넘기지 않는다. HTTP 오류는 1회 기록 후 미완료 종료한다. 수집한 부분 자료를 그대로 남기고 성공할 때까지 자동으로 다시 돌리지 않는다.

해시 사슬과 스냅샷은 별도 동결 계획을 기준으로 일관성을 검사한다. 모든 자료와 해시를 동시에 다시 만든 위조나 실제 서버가 LLM이었다는 사실을 제3자가 암호학적으로 확인하는 보증은 제공하지 않는다. 신뢰 기준점이 필요한 배포에서는 계획 해시와 결과 해시를 별도 신뢰 위치에 먼저 보존한다.
