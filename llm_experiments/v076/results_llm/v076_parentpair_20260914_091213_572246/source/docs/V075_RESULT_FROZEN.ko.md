### T02: 시험한 조건 전체에서 종단 D 제어 성공

fact_only는 두 seed·두 후보 순서에서 작은 D 요구에 유효 D=1 증명, 큰 D 요구에 유효 D=4 증명을 만들었다. 본실험 8/8, 양방향 4/4쌍, 참조 4/4다. 후보를 고르기만 한 것이 아니라 각 규칙과 부모 연결, 최종 노드, 실제 의존 깊이를 모두 충족했다.

이는 T02의 이번 조건에서 완전한 성과다. 네 쌍을 네 개의 독립 문제로 표현하거나 전체 세 문제의 통과로 옮기지는 않는다.

### E01: 선택은 맞지만 다중 전제 연결이 불안정

작은 D 본실험은 4/4, 큰 D는 1/4다. 큰 D 본실험 실패 3건은 모두 `n37` 전제 연결에 오류가 있고, 그중 `t015_fact_only`는 더 앞에서 ID 중복·존재하지 않는 부모까지 발생했다.

`n37`이 요구하는 규칙은 다음과 같다.

```text
Ax AND Ay AND Ab → Ag
```

`t016_fact_only`와 `t019_fact_only`는 마지막 노드를 다음과 같이 냈다.

```json
{"node":{"atom":"Ag","id":"n05","parents":["n03","n04"],"rule":"n37"}}
```

여기서 `n03=Ax`, `n04=Ay`다. 초기 사실 `Ab`를 나타내는 `n02`가 전제에서 빠졌다. 마지막 문자열이 목표 `Ag`라는 이유로 이 증명을 유효하게 볼 수 없다.

`t015_fact_only`는 초기 사실 `Aa`의 ID를 `n08`로 정한 뒤 파생 노드도 같은 `n08`로 작성했다. 부모에는 실제 노드 ID가 아닌 원자 문자열 `Aa`를 썼다. 이 응답은 형식 JSON이 유효해도 논리 연결은 유효하지 않다.

**D=4의 T02는 통과했지만 D=2의 E01에서는 이런 실패가 남았다.** 이번 실패를 단순히 ‘깊이가 커서 생기는 문제’로 묶으면 맞지 않는다. 관찰된 오류 위치는 여러 전제를 한 규칙에 연결하는 부분이다. 이를 특정 내부 메커니즘으로 단정하지 않는다.

### E02: 본실험의 남은 실패는 선택 쪽이다

본실험 8개 조건에서 모델은 모두 짧은 경로 `m18 → m76`을 선택했다. fact_only 생성은 그 선택된 경로를 8/8로 정확히 완성했다. 결과는 모두 유효 D=2다.

따라서 작은 D 요구 4개는 성공했고, 큰 D 요구 4개는 실패했다. **생성기가 틀린 증명을 만든 것이 아니라, 틀린 경로 선택을 보정하지 않고 그대로 실행한 것**이다. 생성 충실성 21/24와 종단 17/24 사이의 4건 차이가 여기서 나온다.

긴 경로 `m33 → m05 → m84 → m41`은 본실험에서 선택되지 않았다. 긴 경로에 대한 새 방식의 생성 능력은 참조 2건에서만 측정됐다. 그중 1건은 유효 D=4 성공이며, 나머지 `t025_fact_only`는 `m05`에서 필요한 `Pb` 대신 `Pc`를 부모로 사용해 실패했다.

## 5. 무엇이 개선됐고, 무엇이 남았는가

### 관찰

새 방식의 초기 사실은 36/36으로 정확했다. Schema는 노드 수·`rule:null`·빈 부모 배열을 제한하지만, `atom`과 `id` 정답 문자열은 고정하지 않았다. 따라서 36/36은 단순 Schema 준수만 센 것이 아니라 실제 초기 사실 내용 및 ID 고유성도 충족한 결과다.

본실험의 새 방식은 작은 D 요구 12/12, 큰 D 요구 5/12다. 종단 실패 7개는 **E01 생성 오류 3개 + E02 선택 오류 4개**로 겹치지 않게 나뉜다. 참조군의 추가 실패는 E01 2개와 E02 1개다.

### 판단

이번 비교에서는 초기 사실 전용 Schema를 유지할 실무적·실험적 근거가 있다. 사실 단계에서 규칙 노드를 미리 만들어 버리는 행동을 사전에 차단한 설계가, 실제 유효한 최종 증명 수 증가와 함께 관측됐다. 출력 제약을 포함한 시스템 설계의 성과이며, 사후에 오답 노드를 삭제하거나 정답 부모를 넣은 결과가 아니다.

그러나 그 변경은 선택기를 개선한 실험이 아니다. 선택은 v074와 같은 20/24·8/12쌍이며, 두 군이 이를 공유했다. **현재 선택 결과를 그대로 사용하면 생성기가 완벽해져도 종단 성공의 상한은 20/24·8/12쌍**이다. 이번 fact_only의 17/24·5/12쌍에서 남은 생성 오류를 모두 없애더라도 이 선택 상한이 남는다.

또한 초기 사실을 잘 작성한다고 후속 부모 연결까지 자동 보장되지는 않는다. 참조 `t022`에서 두 군 모두 초기 사실은 정확했지만 legacy는 세 전제를 연결했고, fact_only는 잘못된 두 전제만 연결했다. 이 악화도 보존한다.

## 6. 실행 계약에서 별도로 발견한 점: 감사용 해시가 프롬프트에도 들어간다

현재 `source/design.py`는 이전 응답의 `message.content`뿐 아니라 **시각·시간 계수 등을 포함한 전체 응답 바이트의 SHA-256**을 후속 입력의 `history[].response_sha256` 및 선택 입력에 넣는다.

이번 첫 규칙 요청 중 8쌍은 앞선 초기 사실 `content`가 완전히 같은데도, 전체 응답 해시가 달라 후속 요청 바이트가 달랐다. 실제로 이 8쌍은 해시 문자열을 제외하면 동일한 요청이었다. 세부 요청·해시는 `ADDITIONAL_COMPARISONS.json`에 기록했다. 원본 요청에서는 어떤 값도 제거하거나 수정하지 않았다.

이는 확인된 구현 사실이다. **해시가 이번 실패나 개선을 일으켰다고 증명한 것은 아니다.** 첫 facts 요청 36쌍에서는 Schema 외의 차이가 없었고, 이번 점수를 바꿀 근거도 아니다. 다만 실행 시각이 다르면 과제 내용이 같은 후속 호출도 정확히 같은 프롬프트가 아닐 수 있다는 점은 이후 설계에서 고려할 필요가 있다.

다음 프로토콜에서 감사 메타데이터와 모델에 보여 주는 과제 데이터를 분리하는 방안을 검토할 수 있다. 원응답 원문과 전체 응답 해시는 evidence에 계속 보존하고, 모델 입력에 무엇을 노출할지는 실행 전에 별도 동결해야 한다. 이것은 기존 원문을 몰래 정규화하거나 기존 점수를 복구하는 조치가 아니다. 이번 분석에서 변경하거나 새 해시 진단을 실행하지 않았다.

## 7. 계획장부상 판단

r3의 기준은 각 군 본실험 24/24, 양방향 12/12, 참조 12/12이며, 생성만의 기준도 본실험 구성 24/24 및 참조 12/12다. 두 군 모두 미달이다. 미측정은 없으므로 gate는 `null`이 아닌 `false`이며, 결정은 `close_batch_partial_no_automatic_followup`이다.

|장부 단계|분석 후 상태|
|---|---|
|P00/P01|기존 종료·보존 유지|
|P02-A v074|이전 결과 그대로 유지|
|P02-B v075|실행·재검산 완료, 부분 개선 보존, 사전 기준 미달로 배치 종료|
|P03 확인용 문제|미실행, 자동 승인·실행 없음|

다음 설계 후보로 fact_only를 보존하는 것은 타당하지만, 이 버전을 ‘완성된 생성기’로 표시해서는 안 된다. 다음 판단에서는 E02의 경로 선택과 E01의 다중 전제 연결을 별개로 다루되, 실제 유효한 최종 구조를 측정하는 종단 평가를 유지하는 것이 중요하다. 또 다른 숫자·공백 진단으로 되돌리거나 같은 배치를 자동 반복하지 않는다.

현재 시험은 세 개발 문제와 두 seed·후보 순서의 반복이다. 성공한 조건만 확인 세트로 바꾸지 않으며, 규칙 수와 D가 엇갈리는 새 구조·모델 내부 상태·A/M·비용 우월성은 이번 결과로 측정한 것이 아니다.
