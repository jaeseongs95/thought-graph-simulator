# 설계·구현 재검토

별도 외부 심사자나 에이전트를 호출하지 않았다. 상충하는 검토 관점을 원문·코드·반례와 대조했으며, 기술적 검산은 생산 측정/보고 모듈을 import하지 않는 별도 구현이다. 두 구현은 고정된 실험 명세와 바이트 입출력 유틸리티, 검토된 이전 v064 감사기를 공유한다. 두 계산기의 일치가 명세 자체를 자동으로 정당화하지는 않는다.

## 연구 측정 관점

v064의 `logical_failures`는 strict 실패도 포함하는 이름이었다. 실제 12건은 모두 `proof_valid=true`이면서 `extra_unused_node`였다. 원 v064 summary는 변경하지 않았고, 분석과 v065 보고서는 `proof_failures`와 `strict_only_failures`를 분리한다.

지정 규칙을 알려주는 것은 이번 구성 검사에서는 명시적 과제 입력이다. 이를 '정답을 알려주지 않고 D를 제어했다'고 표현하지 않는다. 완전한 DAG의 규칙·부모·사실을 모델이 쓰며, 호스트는 마지막 규칙만 조건으로 준다. 그래프의 실제 깊이는 strict 유효일 때만 측정한다.

## 인과·정보 가치 관점

E01의 Ax/Ay와 E02의 Pu/Pv/Pw는 실제 원문에서 유효했으나, 최종 goal은 짧은 규칙에 연결됐다. 국소 규칙 적용 전체가 불가능하다는 설명은 관측과 맞지 않는다. 반대로 긴 최종 증명을 strict하게 구성한 관측도 없다. 이 차이를 구별하기 위한 작은 구성 검사를 선택했다.

v064와 v065는 같은 시간의 무작위 대조가 아니다. v065 성공은 해당 지정 과제를 수행한 관측이며, 전후 점수 차이를 특정 원인 효과로 과장하지 않는다. 이전 D 대응0/6은 보존한다. 이번 결과가 없던 깊은 구성을 제공하지 못하면 같은 진단을 반복하지 않는다.

## 구현·증거 관점

평가기 measure.py는 v064와 바이트 동일하다. 원 v064 배포 ZIP은 hash를 고정해 `prior/v064_source_r3.zip`에 감사 의존성으로 딱 한 판본만 포함한다. 실행 때 그 **배포 코드**로 원 v064 증거를 검사하며, 증거 안의 snapshot은 실행하지 않는다. 과거 전체 Python 체인을 새 소스 폴더에 복제하지 않는다.

이전 검산 영수증은 프로세스 안에서 원문 SHA/감사 코드 SHA가 같은 경우에만 재사용한다. 재사용 때도 현재 받은 baseline 바이트의 SHA와 manifest를 확인한다. 완성 보고서는 원문에서 생산·독립 계산을 각각 수행해 한국어 텍스트까지 일치시킨다.

원 run의 시작 표지·request/response·record·event 순서, 한 pending action의 미확정 원문 보존, 중단 후 후속 action 거부를 유지했다. 손상된 committed JSON이나 torn event를 복구해 성공으로 바꾸지 않는다. 악의적인 동일 OS 사용자에게 외부 실행을 인증하는 서명 체계는 아니다.

## 코드 변경과 검사

새 설계/요청/집계/독립 재계산을 추가했고, 공용 소스 파일 나열은 POSIX 상대경로 문자열로 정렬해 기존 Windows/Linux manifest 순서 차이를 제거했다. 동일 빌드 환경의 결정적 ZIP 재빌드를 검사한다. 모든 가능한 Python/zlib 버전의 압축 바이트 동일성을 주장하지 않는다.

전체 시험은 올바른 지정 구성, 짧은 경로 고정, 반대 경로, 규칙명만 이행한 틀린 증명, 무관 노드, 순서 위반, 형식 미측정, HTTP/모델/생성예산 오류, pending 보존, 재해시 변조, 기존 결과 충돌, 자동화 stderr/종료 코드, 별도 하위 프로세스 전체 합성 실행을 포함한다. 실행하지 않은 실패 재현을 한 것으로 적지 않는다. 실제 완료 수·로그·Windows 실행 여부는 별도 분석 검증서에 기록한다.
