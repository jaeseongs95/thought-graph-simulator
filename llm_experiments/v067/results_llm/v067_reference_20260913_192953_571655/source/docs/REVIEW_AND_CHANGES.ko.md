# 결과 기반 설계와 작성 후 검토

별도 외부 심사자나 독립 에이전트는 호출하지 않았다. 연구 타당성·원인 구별·실행/측정·증거 보존 관점의 반론을 대조했고, 생산 측정기와 독립 코드 및 합성 반례로 검증했다. 검토자 수나 테스트 개수 자체를 연구 가설의 근거로 세지 않는다.

## 후보 비교

|관점/후보|근거와 처분|
|---|---|
|v066 계획 문구를 더 강조해 반복|채택하지 않는다. 사전 종료 기준에 해당했고 두 호출 구조의 성과는0이다.|
|틀린 계획을 호스트가 바로잡아 후속에 전달|채택하지 않는다. 모델 원출력 제어라는 실험의 책임 분담을 바꾸면서 성공으로 위장할 위험이 있다.|
|v066 실패 분석만 제공|원문 분석과 분기 종료를 확정하는 데 필요하다. 다만 정상 입력의 생성기 동작은 여전히 미관측이다.|
|정상 참조를 명시적으로 주는 양성 대조|채택한다. 입력 자체가 정답임을 공개하고, 해당 입력에서 출력 계약을 수행하는지만 한 번에12회 검사한다.|
|정답 제공이므로 연구 핵심 성과 아닌가?|맞다. 이것은 D 본 가설의 성공 검사가 아니라 생성기 구성요소의 양성 대조다. 보고서와 필드에서 D/A/M 성공 승격을 금지한다.|
|계속 지엽적인 진단을 늘리는 것 아닌가?|한 번의 검사 이후 문구 튜닝 반복을 허용하지 않는다. 결과별로 구성요소 가용성 또는 분기 종료만 판정하고 새 모델/출력 계약/독립축은 별도 결정으로 둔다.|

## 실제 v066에서 남은 식별 한계

v066 planner12개는 형식상 모두 유효하지만, 한 목표의 완전한 사용 규칙 목록으로는 모두 무효였다. 엄격한 계획 준수와 strict 증명을 동시에 요구하므로, 그 입력으로 종단 성공은 이미 막혀 있었다. 후속 graph가 실패했다고 해서 정상 입력의 constructor도 실패한다고 추정하면 안 된다. v066 설계에는 그 능력을 분리해 확인할 정상계획 입력 대조가 없었다.

v067에는 일부러 잘못된 참조를 실제 모델에 다시 주는 추가12회를 넣지 않았다. 그 경우 strict+완전 계획 이행의 동시 성공은 구조적으로 불가능하며, 여기서 필요한 최소 정보는 정상 입력의 수행 여부다. 정상/비정상 입력 간 효과 크기 또는 유의한 개선율을 계산하지 않는다. 과거 결과와 새 결과의 인과 비교라는 주장도 하지 않는다.

## 구현 경계

실제 사용자 v066 source snapshot의24개 파일에서 배포 ZIP을 복원했고, 기존 Library 분석 문서가 기록한 원 배포 SHA-256 `375d5fd79bc81a4b547d07567a97eb33d8e8176256b24d013c87c54f97785331`과 완전히 같음을 확인했다. 이 동일 배포본을 `prior/v066_source.zip`으로 고정한다. 임의의 evidence snapshot을 신뢰해 실행하거나 원래 배포본을 가진 것처럼 추측하지 않는다.

`measure.py`는 기존 평가기와 바이트 동일하다. 호출/기록/종료/부분 실행 뼈대는 검증된 v065 실행기를 재사용했고 baseline·contract·version만 새 모듈에 맞췄다. v066의 동적 모델 계획 전달은 이 단일 생성기 양성 대조에 필요하지 않으므로 넣지 않았다. reference.py는 prepare에서 정답 입력의 타당성을 검사하며 실제 응답을 고쳐 다음 요청에 쓰는 데 호출되지 않는다.

## 작성 후 검토

정적 검토에서 요약문 '0/12이면 종료'가 미측정이 있는 경우까지 의미할 수 있어 '12건이 모두 측정됐는데0/12'로 명확히 했다. 기계 판독용 next_decision도 미완료/참조 입력 재구성 가능/부분/종료로 분리했다. 수정 전 실행 실패를 재현한 것처럼 적지 않는다. 실제 모델 응답이나 과거 판정을 변경한 수정은 없다.

합성 검사는 정상 참조 완성, 항상 짧은 경로, 반대 경로, 규칙명만 이행한 오답, 잘못된 부모·final, 불필요 노드, 독립 가지 순서 변경, 형식 미측정, HTTP/identity/예산 중단, pending 원문, 입력·출력·출처·한국어 요약 재해시 변조를 포함한다. 정답을 제공했다고 무조건 성공시키거나 실제 경로 선택 성과로 승격하지 않는지를 검사한다.

최종 배포 ZIP을 새 빈 폴더에 풀어 같은 소스 바이트로 다시 검증하고 실제 결과는 별도 분석 ZIP의 VALIDATION_RESULT.json에 기록한다. Windows PowerShell 실기 검사와 Linux 합성 하위프로세스 검사는 구분한다. source hash 일치는 외부 물리적 실행의 전자서명 보증이 아니다.
