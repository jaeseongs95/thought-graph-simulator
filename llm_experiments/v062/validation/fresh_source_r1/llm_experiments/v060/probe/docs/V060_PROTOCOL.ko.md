# v060 사전 프로토콜: k10 후치 배열의 선택 위치 진단

## 질문과 조작

v059에서 같은 예측을 했던 ‘첫 목표 도출 규칙’과 ‘전체 배열의 두 번째 규칙’이 서로 다른 규칙을 가리키면 어떤 선택 패턴을 관측하는가? 두 조건에서 같은 선택을 반복하는가?

|항목|고정 내용|
|---|---|
|모델·문제·방향·형식|기준선 candidate identity, K01/original/shallow/choice|
|원요청 출처|완료·무결성과 독립 검산을 통과한 v058의 전체 10개 seed choice 요청|
|후속 질문의 근거|v059 원자료 재분석. 과거 응답은 새 관측에 합산하지 않음|
|A: deep_first|rules `[k17,k03,k10]`|
|B: shallow_first|rules `[k03,k17,k10]`|
|고정값|facts·goal·규칙의 ID와 내용·지시·schema·전체 옵션·모델 identity|
|A/B 조작값|첫 두 목표 도출 규칙의 배열 순서|
|공통 새 배치|k10은 마지막. 원래 v059의 첫 위치와 다름|
|표본과 반복|원래 10개 seed 모두, seed마다 각 조건 2회|
|일정|schedule_seed `6002026`, SHA-256 assignment 순위 앞 5개 ABBA, 나머지 BAAB; blocks 순위로 블록 배치|
|예산|40회 추론, 블록 전후 metadata 20개, warmup 0|

두 목표 도출 규칙의 상대 순서와 전체 위치는 v060에서도 함께 바뀐다. 모든 위치 기제의 순수 효과를 분리하는 설계는 아니다. k10 후치는 두 조건에서 같지만, k17이 그 전제 Cb의 생산 규칙보다 앞에 나오게 한다. 따라서 v059에서 사용한 기제를 직접 식별했다거나 역사적 실행과의 차이가 k10 위치만의 효과라고 주장하지 않는다.

## 결과를 보기 전 예측과 판정

|가설의 관측 예측|A|B|남는 동치 설명|
|---|---|---|---|
|첫 terminal|k17|k03|첫 전체 항목|
|절대 두 번째|k03|k17|마지막 terminal|
|항상 shallow 규칙|k03|k03|규칙을 한 번 읽어 현재 적용 가능한 goal 규칙 선택 등|
|항상 deep 규칙|k17|k17|ID·깊은 경로·기타 고정 선호|

seed별 A0/A1/B0/B1의 실제 선택 ID를 표의 예측과 비교한다. 두 반복이 어긋나면 그 seed를 안정적인 패턴으로 분류하지 않는다. 후보 외 ID나 파싱 불가를 가장 가까운 가설에 억지로 배정하지 않는다. 완전한 패턴 일치도 내부 기제의 확인으로 표현하지 않는다. 위 예측과 일치하지 않는 결과는 미리 정한 실패가 아니라 별도 관측 패턴이다.

주 분석 단위는 seed 블록 10개다. 문제 표본은 하나이며, 40개 호출이나 조건 간 20쌍을 독립 문제 표본으로 세지 않는다. 조건 내 반복·조건 간 선택 변화·seed별 평균 B−A와 sequence/period/직전 조건/반복 간격별 분포를 기술한다. 효과의 p값이나 모델 전체 성능을 자동 판정하지 않는다.

## 측정 계약

형식 유효성, `goal_reachable_choice`, `instruction_fulfilled`, `selected_rule_id`, `selected_rule_position`(0기준), `terminal_rank`(목표를 결론으로 갖는 규칙 중 0기준 순위), `implied_depth`, `shallow_success`를 분리한다. `k03`의 implied_depth는 1이고 `k17`은 2다. k10 후치에서도 논리적 도달 가능성은 전체 규칙의 고정점으로 계산하며 배열을 한 번만 훑어 판정하지 않는다.

유효한 ID 형식으로 `k10`이나 알 수 없는 ID를 선택하면 형식은 유효하지만 목표 도달 가능 선택과 shallow 지시 이행은 false다. 형식이 유효하지 않으면 두 지표는 null이다. 미실행도 별도로 기록한다. `actual_D`, `D`, `proof_valid`, `strict_valid`는 choice-only 과제에서 계속 null이다.

조건별 위치 집계와 terminal 순위 집계는 선택 기준을 검토하기 위한 관측값이다. 논리적으로 유효한 선택을 전체 지시 이행으로 오해하지 않도록 v059의 `task_valid` 대신 좁은 이름을 사용한다. 전체 해당 비율은 실행 완료와 비교의 측정 분모가 충족돼야 계산하고, 부족하면 null을 둔다.

## 실행·증거·중단

prepare는 신뢰하는 로컬 v058 감사 코드와 독립 계산기로 기준선 ZIP을 확인하고 원요청을 선택한다. 증거에 동봉된 소스 스냅샷은 실행하지 않는다. 요청 생성기는 정답이나 채점 결과를 import하지 않으며 규칙 배열의 확인된 바이트 구간만 바꾼다. 같은 조건의 두 요청은 seed별로 바이트가 같다.

실행 전 소스 지문·모델 identity·옵션·요청 해시·일정·예산을 계획에 고정한다. 실제 실행에서는 원요청·원응답, metadata, event chain, 상태와 소스 스냅샷을 보존한다. metadata 조회와 블록 경계는 캐시 초기화가 아니다. 첫 호출도 외부 이력을 가질 수 있다.

transport·모델 identity 오류는 즉시 중단한다. 자동 재시도·재개·응답 교정·모델 다운로드는 없다. 형식이나 선택 오류를 정상 HTTP로 받으면 그대로 관측하고 다음 계획 호출로 진행한다. 부분 실행은 보존하고 감사한다. 새 계획·결과·ZIP은 기존 경로를 덮어쓰지 않는다.

## 검증과 다음 결정

소스는 정상 mock 실행과 누락·변조·중복·잘못된 참조·transport 중단의 반례로 검사한다. 생산 채점기를 import하지 않는 독립 검산기는 요청 변환, 고정 일정, 원응답 측정, 집계와 한국어 요약을 다시 계산한다. 배포 manifest를 확인하고 ZIP을 새 위치에 풀어 자체시험한다. 구현에 참여하지 않은 감사자는 최종 봉인 소스와 검증 근거를 확인한다.

실제 결과가 안정된 첫 terminal 또는 절대 두 번째 예측과 맞으면 해당 새 배치의 관측 일치로 보고한다. 한 규칙 고정, 반복 불일치 또는 부분 실행이면 그 상태를 보존하고 동치 설명을 가르는 다음 조작을 별도 설계한다. v060의 결과를 본 뒤 현재 계획의 성공 기준이나 seed를 변경하지 않는다.
