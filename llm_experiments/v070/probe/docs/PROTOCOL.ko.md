# v070 사전 동결 명세 — D 지시 기반 후보 경로 선택

## 1. v069에서 출발하는 이유
v069 실제 기록은 지정 경로·단계별 규칙 안내 아래 12/12 종단 증명 성공이다. 사실 노드 28개, 규칙 적용 노드 30개, 최종 ID 호출 12개를 검사했다. 이 기준선을 보존하며 같은 구성 계약의 문구 변형은 반복하지 않는다.

이번 질문은 **동일 문제·목표·후보 목록에서 D 요구만 바꾸면 모델이 적절한 경로를 선택하는가**다. 전체 계획을 자유 생성하거나 graph를 작성하는 실험이 아니다. 구성 호출의 비용을 다시 지출하기 전에 새 선택 인터페이스 자체를 검증한다. v069 성공과 v070 선택 성공을 합쳐 종단 연결 성공이라고 보고하지 않는다.

## 2. 입력과 출력
입력에는 원래 facts/rules/goal, 깊이 정답 라벨이 없는 후보 규칙 배열 두 개, 작은/큰 D 중 하나를 요구하는 문장이 들어간다. 후보 순서를 두 방향으로 교차하며 같은 문제/seed/후보 순서의 짝에서는 요구 문장만 다르다. 문제 ID, expected D, reference_short/reference_long 라벨, 정답 후보 index는 요청에 넣지 않는다. JSON Schema는 답을 enum으로 강제하지 않는다.

모델은 `{"rule_ids":["실제로 선택한 규칙 ID", ...]}`를 출력한다. 후보 하나의 배열을 그대로 선택해야 한다. 규칙 이름 수정, 순서 복구, 후보에 강제 맞춤, 두 경로 혼합, 누락 규칙 보충은 하지 않는다. 원응답 문자열과 HTTP envelope를 보관한다.

## 3. 측정과 의미
D는 initial fact=0, derived atom=1+max(premise depths)이다. 규칙 개수나 총 단계 수가 아니다. 선택 목록의 실행 순서, 모든 전제의 가용성, 중복 도출, 최종 goal, 사용되지 않는 규칙을 검사하고 goal의 실제 지지 의존 구조에서 깊이를 계산한다.

`candidate_member`, `route_valid`, `route_D`, `selection_success`를 별도로 기록한다. 다른 topological ordering이라 논리적으로 유효해도 제시한 후보 배열과 다르면 이 선택 인터페이스에서는 실패다. 다른 모델이 생성한 graph의 parent ID를 평가한 값이 아니라 **선택 규칙 목록을 입력 규칙 관계로 검산한 깊이**다.

형식상 읽을 수 있으나 잘못된 경로는 논리/선택 실패다. JSON/스키마 오류, 응답 길이 종료, HTTP/transport/model identity 오류, 미실행은 별도로 기록한다. 미측정을 D=0이나 오답으로 채우지 않는다. 누락 usage는 0이 아니라 null이다.

## 4. 40회 고정 배정
5문제 × 2seed × 2후보 순서 × shallow/deep = 40회, 20짝이다. 10개 block에 metadata before/after 20개 action을 넣어 전체 60개 action이다. metadata action마다 version/tags/show를 조회하지만 이는 모델 추론 3회로 세지 않는다. 각 block의 네 선택 요청 순서는 두 seed 사이에서 반전한다.

|문제|얕은 경로 D / 규칙 수|깊은 경로 D / 규칙 수|역할|
|---|---|---|---|
|T02|1 / 1|4 / 4|v069에서 구성 확인한 기존 문제|
|E01_shared_fork|1 / 1|2 / 3|v069에서 구성 확인한 기존 문제|
|E02_two_vs_four|2 / 2|4 / 4|v069에서 구성 확인한 기존 문제|
|C01_equal_count|2 / 3|3 / 3|규칙 개수 동률 대조|
|C02_count_reversal|2 / 4|3 / 3|규칙 개수와 깊이의 방향이 반대인 대조|

C01/C02는 이 단계에서 직접 설계한 진단 대조다. 독립적으로 표집한 holdout이 아니다. 이 두 문제의 실제 Qwen graph 생성 능력은 v069에서 측정되지 않았다. 모든 조건을 결과와 무관하게 고정 배정한다. seed를 독립 표본 보장의 증거로 취급하지 않는다.

기존 세 문제만 사용하면 규칙 개수가 깊이와 같은 방향으로 움직인다. 그러므로 C01/C02 없이 높은 정확도를 얻어도 단순 목록 길이 선택을 배제하기 어렵다. 이 대조는 특정 단순 설명을 구분하기 위한 것이지 모델 내부 알고리즘을 규명하기 위한 것이 아니다.

## 5. 사전 성공·종료 기준
완료 40회 및 측정 40회 상태에서 선택 40/40, shallow/deep 짝 20/20이면 **이 후보 목록 내 D 선택 계약의 기준선**이다. 다음은 별도 동결된 selector→constructor 연결 실험을 설계하는 것이며 자동으로 실행하지 않는다. 두 모듈이 각각 성공했다는 사실로 연결 성공을 미리 판정하지 않는다.

일부/전체 실패면 문제·seed·후보 위치·D별 범위를 보존하고 이 선택 계약을 종료한다. 같은 문구나 seed 변경으로 자동 반복하지 않는다. 미완료/미측정이면 전체 gate=null이다. 관측된 성공 개수는 보존하지만 전체 비율/gate를 정상 완료와 섞지 않는다.

## 6. 실행 경계
모델은 고정 `qwen3:4b-instruct` 및 v069 digest/metadata와 대조한다. 생성 상한은 호출당 기존 4096, 전체 163840 token의 계획상 상한이다. 기대 소비량이라는 뜻이 아니다. 동결된 로컬 HTTP endpoint만 허용한다. 다운로드·갱신·서버 시작·warmup·자동 재시도·자동 다음 실험은 없다.

각 action 시작 표지, 요청 바이트, 원응답, event hash chain, 상태, 소스 snapshot, 기준 v069 evidence, 한국어 보고서를 보존한다. 시작 표지 수와 수신/완료 응답 수를 분리한다. interrupted action의 원문은 보존하지만 성공으로 채점하지 않는다.

자동화는 batch 시작 표지를 독점 생성한다. 이미 시작한 v070은 새 RunName으로 반복하지 않는다. 중단 원문을 분석하거나 offline finalize를 사용한다. `-CheckOnly`는 모델 조회/추론 없이 소스 시험과 계획 생성만 한다.

## 7. 독립 검산의 범위
생산 선택 채점은 forward dependency propagation, 독립 검산은 producer 관계 구성 후 goal에서 recursive depth/ancestry 계산을 한다. 검산기는 생산 design/selection/reference/measure/report/run을 import하지 않는다. 바이트/JSON/ZIP 유틸리티와 사전 동결 명세 및 보고서 문구 계약은 공유한다.

해시와 재계산은 번들 내부 일관성을 확인한다. 외부 PC/GPU에서 실제로 실행되었음을 독립 인증하지 않는다. 합성 HTTP 시험과 실제 모델 성능은 별도다.
