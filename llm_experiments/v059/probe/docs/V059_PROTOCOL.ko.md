# v059 사전 프로토콜: K01 규칙 배열 순열 진단

## 질문과 고정 조건

Gemma `K01` choice가 목표를 도출하는 두 규칙의 목록 순서에 따라 다른 선택을 보이는가? 같은 조건에서 반복한 선택도 달라지는가? v058 결과를 본 뒤 선정한 탐색적 질문이며 일반 모델 비교나 A/D/M 전체 제어 시험은 아니다.

|항목|고정 내용|
|---|---|
|모델·문제|v058 candidate identity, K01/original/shallow/choice|
|generation seed|v058의 서로 다른 10개 전체|
|A: original|rules `[k10,k17,k03]`|
|B: terminal_swap|rules `[k10,k03,k17]`|
|고정값|facts·goal·규칙 ID와 내용·지시·schema·옵션·모델 identity|
|조작값|원문 요청의 rules 배열 안 두 규칙 위치만 교환|
|블록|seed별 4회, ABBA 또는 BAAB|
|배정|schedule_seed `5902026`; SHA-256의 `assignment` 순위 앞 5 seed=ABBA, 나머지=BAAB; `blocks` 순위로 실행 순서 고정|
|예산|40추론, 블록 전후 metadata 20개(각 3 HTTP 조회), warmup 0|

SHA-256 정렬에 사용하는 문자열은 `5902026:assignment:<seed>`와 `5902026:blocks:<seed>`다. 암호학적 무작위 표본 추출이나 외부 무작위화 인증을 뜻하지 않는다. generation seed 숫자나 결과에 맞춰 실행 배정을 조정하지 않는 재현 가능한 배치다. 이 배치 자체를 seed 모집단의 일반성을 보장하는 근거로 쓰지 않는다.

요청 생성기는 채점 결과를 참조하지 않는다. A는 원래 요청 바이트를 사용하고 B는 확인된 고유 rules 문자열 구간만 치환한다. 요청 해시를 계획에 미리 동결한다. 기준선의 반대 과제순서 요청도 seed별로 동일한지 확인한다. 과거 응답은 결과값으로 복사하지 않는다.

## 기록과 측정

`period`는 블록 안 0~3, `repeat`는 해당 조건의 첫·둘째 관측 0~1, `position`은 전역 순서다. 직전 호출 ID·variant와 같은 조건의 이전 슬롯·반복 간격도 기록한다. 블록의 시작이나 metadata 조회는 상태·캐시 초기화가 아니다. 첫 호출도 외부 이력의 영향을 받을 수 있다.

제공된 10개 seed의 동결 일정에서 A의 직전 조건은 미기록 1회·A 7회·B 12회, B의 직전 조건은 A 13회·B 7회다. 블록 내부의 균형이 전역 이력의 완전한 균형을 뜻하지 않는다. A0/B0와 A1/B1도 같은 period가 아니라 각 조건의 발생 차수로 대응시킨다. 개별 대응쌍을 직접적인 인과효과로 해석하지 않는다.

형식 유효성, goal을 도출할 수 있는 규칙 선택의 유효성, selected_rule_id, 선택한 규칙의 목록 위치(0기준), implied_depth, shallow_success를 분리한다. `k03` 선택의 implied_depth는 1, `k17`은 2다. 이 값은 문제의 경로와 규칙을 대응시킨 채점값이며 실제 생성한 증명의 D가 아니다. `D`, `actual_D`, `proof_valid`, `strict_valid`는 null이다.

seed별 A0/B0·A1/B1 조건 비교 20개와 A0/A1·B0/B1 반복 비교 20개를 별도 기록한다. 주 분석 단위는 seed 블록 10개다. seed별 B 성공 평균−A 성공 평균을 기록하고 그 10개 값의 평균을 기술한다. 호출 40개 또는 대응 비교 20개를 독립 문제 표본으로 계산하지 않는다. p값이나 일반화된 효과 판정은 자동 생성하지 않는다.

`stable_within_both`는 두 조건에서 각각 출력 ID가 반복해서 같았다는 뜻이다. 유효한 선택이나 올바른 방향을 보증하지 않는다. `choice_valid`와 `shallow_success`를 함께 확인한다. 선택 규칙의 목록 위치는 각 trial의 measurement에 보존한다.

## 결과 이후의 결정

- 원래 배열의 k17 선택과 교환 배열의 k03 선택이 함께 늘고 같은 조건 반복이 안정적이면, 이 두 배열에서의 선택이 목록 순열에 민감하다는 설명과 양립한다. 내부적으로 ‘첫 terminal rule을 택한다’는 원인을 확정하지 않는다.
- 순열이 달라도 k17 선택이 유지되면, 이 조작으로 안정된 깊은 선택이 바뀌었다는 근거는 없다. 지시 해석·규칙 ID·문제 특성 등 다른 가설은 남는다.
- 같은 조건 반복 불일치가 크거나 ABBA/BAAB·period·직전 조건·반복 간격에 따라 차이의 방향이 다르면, 순열만으로 설명하지 않고 이력 포함 변동으로 보고한다. 서로 다른 분모의 변화율을 단순 비교해 유의성으로 해석하지 않는다.
- 일부만 실행되거나 측정할 수 없는 값이 있으면 관측 분모를 공개하고 전체 해당 비교율을 null로 둔다. 사후 성공 seed 선별이나 실패 후 자동 재실행은 하지 않는다.

순열 외 요청 바이트, 모델 identity, 예산, 실행표 또는 측정 계약을 바꿔야 하면 새 소스에서 새 계획을 만들어 별도 실험으로 실행한다. 실행 후 원래 계획을 고치지 않는다.

## 실패와 증거 보존

HTTP·transport·응답 모델·metadata identity 오류는 즉시 중단하고 부분 실행을 보존한다. 정상 HTTP로 받은 형식·논리 오류는 해당 관측으로 기록한 뒤 다음 예정 호출을 실행한다. 파싱 불가나 미실행을 실패 또는 0으로 대체하지 않는다. unknown rule ID는 형식 유효지만 선택 유효성 실패로 구분한다.

모델 다운로드, 추론 자동 재시도·재개, 정답 추가와 응답 교정은 없다. 원문, 요청·응답 해시, event chain, 상태, 모델 metadata, 계획과 소스 스냅샷을 감사한 뒤 evidence ZIP을 만든다. 독립 계산기는 생산 요청·채점·집계 모듈을 import하지 않고 ZIP에서 재계산한다. 해시는 기록 일관성의 검사이며 외부 실행 전자서명이 아니다.
